# Hunting OWAReaper Implant C2 and CDN-Proxied Exfiltration

The Proofpoint article "Cleaning Out Inboxes: TA488 Comes for Outlook with Another Half-Click Exploit" (https://www.proofpoint.com/us/blog/threat-insight/cleaning-out-inboxes-ta488-comes-outlook-another-half-click-exploit) details a sophisticated JavaScript implant called OWAReaper. This implant gains persistence within Outlook Web Access (OWA) sessions, making it particularly difficult to detect through standard endpoint monitoring. We have designed a hunt focused on the network behavior that remains visible when this implant interacts with its command-and-control infrastructure.\n\nThe hypothesis assumes that an active OWAReaper implant is polling GitHub for commands and using legitimate image CDNs or DNS tunneling to exfiltrate stolen data. Because the implant runs within the browser context of an OWA session, the traffic often blends in with legitimate web usage. Traditional domain-based blacklisting is often insufficient because the actor leverages high-reputation services to mask their relay servers.\n\nThe hunt begins with scoping, using vulnerability data to identify Exchange servers exposed to CVE-2026-42897. We then pivot to authentication logs to identify specific user workstations that have authenticated against these vulnerable servers. This allows us to focus the subsequent high-volume network analysis on a subset of potentially compromised hosts, reducing the risk of false positives from the broader estate.\n\nIn the command-and-control phase, the hunt examines HTTP telemetry for browser processes (Chrome, Edge, Safari) that are polling the GitHub Commit Search API. While developers use GitHub frequently, they typically do so via CLI tools or IDEs. Continuous browser-based polling of the commit search endpoint, especially from non-technical users, is a strong indicator of the implant's retrieval mechanism.\n\nFor exfiltration, we monitor for HTTP requests directed at high-reputation CDNs—such as images.weserv.nl, i3.wp.com, or slack-imgs.com—that contain specific URI patterns like /assets/v1_. These CDNs act as proxies to the actor's relay domain, acocdn.com. If the implant cannot reach these CDNs, it falls back to DNS tunneling. We look for long, high-entropy subdomains under the actor-controlled domain to catch this fallback behavior.\n\nThere are significant blind spots to consider. Without SSL/TLS inspection, the specific URI paths used for exfiltration are invisible, leaving only the destination domain as a signal. Additionally, legitimate developer activity on GitHub can create noise that requires manual filtering based on department or typical host behavior. This is why the process is a hunt: it requires an analyst to differentiate between a developer searching for code and an implant searching for instructions.\n\nThis hunt is available as an open hunt.md playbook. It is designed to be imported into Huntbase or any other runtime that supports the hunt.md format, allowing for the automated execution of the scoping and network analysis steps described above.
