# Hunting TeamFiltration Service Account Compromise and M365 Data Exfiltration

Recent research by Proofpoint, Ghost Service Accounts Enable M365 Data Theft in Chile (https://www.proofpoint.com/us/newsroom/news/ghost-service-accounts-enable-m365-data-theft-chile), describes a campaign where attackers use the TeamFiltration toolkit to target service accounts. These accounts are often ghost identities—functional accounts created for specific tasks but left without multifactor authentication (MFA). Because these accounts are not tied to a human user, their compromise often goes unnoticed. This hunt provides a systematic way to find these vulnerabilities and the subsequent data theft. ### Hypothesis An adversary compromises functional service accounts via credential spraying to bypass MFA, then uses these ghost identities to exfiltrate bulk data from M365 and discover administrative portals. ### The Scoping Phase The hunt begins by identifying the attack surface. The first query scans the user directory for accounts containing keywords like svc, bot, payment, or admin that do not have MFA enabled. This step provides the list of candidate ghost accounts that the adversary is likely to target. By narrowing the scope to these high-risk identities, we reduce the noise in subsequent authentication and API queries. ### Authentication Triage Once we have a list of vulnerable accounts, the hunt pivots to authentication logs. It runs two queries in parallel. The first query looks for patterns of credential spraying, specifically identifying accounts that receive a high volume of login failures from multiple distinct IP addresses. This matches the rotation strategy used by the TeamFiltration toolkit. The second query looks for successful logons to the same accounts from rare or new IP addresses. An analyst then compares these two results to confirm if a spray attempt resulted in a successful compromise. ### Identifying Cloud Impact After identifying a potential compromise, the hunt examines cloud API activity. It searches for high-volume operations associated with data exfiltration, such as accessing mail items, downloading files, or starting Teams sessions. It also flags any activity involving administrative portals. Service accounts rarely need to browse the Azure portal or the M365 admin center; such activity strongly suggests an adversary is performing discovery to find higher-privilege targets or additional data sources. This correlation of identity vulnerability with cloud impact is why this is a hunt, not a simple detection rule. ### Review and Containment The hunt concludes with a tiered review. An automated agent evaluates the correlation between the authentication anomalies and the cloud API activity. If the agent confirms malicious behavior, the playbook routes the case to a containment action. This action disables the compromised account and revokes all active sessions. A final task directs a human analyst to perform a forensic audit of the specific files and emails accessed, ensuring the organization meets any regulatory disclosure requirements. ### Blind Spots The primary blind spot is the latency of the Microsoft 365 Unified Audit Log (UAL). Logs can take up to 24 hours to appear in the telemetry stream, meaning an active exfiltration event might not be visible until a day after it starts. Additionally, this hunt only sees VPN activity if the VPN logs are integrated into the normalized authentication surface. ### How to run this hunt This hunt is packaged as an open hunt.md playbook. You can import it into Huntbase or any hunt.md-aware runtime. The playbook uses standard SQL queries against normalized surfaces like hb_users, hb_auth_signin, and hb_cloud_api_activity. Because it is environment-agnostic, you can implement these logic steps in any tool that supports SQL-like queries against your audit logs.
