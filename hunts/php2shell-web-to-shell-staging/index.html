PHP2Shell: Web-to-Shell Staging

High severity TLP:CLEAR Part 1 of 2 Research by Elastic Security Labs Published 22 Oct 2026

Hypothesis

An attacker is exploiting PHP core RCE vulnerabilities (CVE-2026-109618/19) to force web server processes to spawn shells or interpreters, which then perform system discovery and payload staging.

Brief

Why hunt for PHP2Shell

Recent research from Elastic Security Labs, titled php2shell: Assessing Elastic detection coverage relevant to CVE-2026-109618 and CVE-2026-109619, details critical vulnerabilities in the PHP core. These flaws allow unauthenticated attackers to execute arbitrary code. While static detection rules often catch known web shells, this hunt focuses on the broader behavioral footprint of a compromised web worker. We want to find the transition from a web server process to a shell or interpreter, even if the specific exploit payload is new or obfuscated.

How the Hunt Flows

The hunt begins by identifying vulnerable assets. The first query searches the vulnerability surface to find hosts where the target CVEs remain unpatched. This scoping step ensures analysts prioritize high-risk servers, though the hunt can also run across the entire estate to find undocumented or shadow PHP deployments.

The second phase analyzes early execution in two parallel paths. One path looks for direct shell launches from web server processes like nginx, apache2, or php-fpm. The second path performs a frequency analysis of all children spawned by web processes. By stack-counting these relationships across the fleet, the hunt highlights rare pivots—such as a single web server launching an unusual binary—that traditional rules might miss due to their low volume or lack of a known-bad signature.

An analyst then triages these execution hits. They evaluate the command lines to distinguish legitimate administrative scripts from malicious activity. Once a suspicious host is identified, the hunt searches for follow-on staging behavior. This query looks for discovery tools and downloaders like wget, python, or hostname on the targeted systems. The hunt concludes by correlating the initial shell launch with these staging actions to provide a final verdict.

Why this is a hunt, not a detection

Detection rules for web-to-shell activity often generate high noise in environments where administrators run maintenance scripts or backups directly through web worker contexts. This hunt uses fleet-wide prevalence and human triage to separate that administrative noise from an actual exploit. It looks for the convergence of a vulnerability, a rare process pivot, and follow-on discovery, rather than just a single process event.

Blind Spots and Limitations

This hunt relies heavily on process telemetry. If a web server is not enrolled in endpoint monitoring, it remains a complete blind spot. Additionally, sophisticated attackers might execute code entirely within the PHP worker process memory without spawning a child process. Such memory-only exploitation is invisible to the process-launch telemetry used here and requires specialized engine-level tracing to detect.

    Web workers spawning shells

    Detect the most direct indicator of RCE: a web worker process spawning a shell.

    What a hit looks like. A shell running as a child of a web server. Benign hits include maintenance scripts or scheduled backups.

  3. Query, baseline

    Rare web server children

    Stack-count children of web processes to identify rare pivots across the fleet that behavior rules might miss.

    sql, reads hb_process_activity
    SELECT LOWER(parent_process_name) AS parent, LOWER(process_name) AS child, COUNT(DISTINCT device_hostname) AS hosts, MIN(time) AS first_seenFROM hb_process_activityWHERE (instr(',' || '{{web_server_parents}}' || ',', ',' || LOWER(parent_process_name) || ',') > 0 OR LOWER(parent_process_name) LIKE 'php-fpm%' OR LOWER(parent_process_name) LIKE 'lsphp%')  AND time >= datetime('now', '-{{lookback_days}} days')GROUP BY 1, 2HAVING hosts <= 2

    What a hit looks like. One or two hosts where a web process spawns an unusual child. Silence means the web tier behaves uniformly across the fleet.

  4. Agent triage

    Triage early execution

    Evaluate whether the shells or rare children found represent legitimate administrative tasks or high-risk post-exploitation.

  5. Query, triage

    Follow-on discovery and staging

    Search for follow-on actions (enumeration and downloading) on the hosts identified in the early triage.

    sql, reads hb_process_activity
    SELECT device_hostname, parent_process_name, process_name, process_cmd_line, timeFROM hb_process_activityWHERE ('{{scope_hosts}}' = '' OR instr(',' || '{{scope_hosts}}' || ',', ',' || device_hostname || ',') > 0)  AND (instr(',' || '{{staging_tools}}' || ',', ',' || LOWER(process_name) || ',') > 0 OR LOWER(process_cmd_line) LIKE '%/etc/os-release%' OR LOWER(process_cmd_line) LIKE '%/etc/shadow%')  AND time >= datetime('now', '-{{lookback_days}} days')

  6. Agent triage

    Correlate end-to-end execution

    Combine the early execution patterns with follow-on staging evidence to reach a final verdict.

  7. Decision

    Route on final verdict

    Direct confirmed compromises to immediate containment.

  8. Response action

    Isolate compromised host

    Sever the attacker's staging path by isolating the host.

  9. Analyst task

    Manual forensic review

    Verify the entry point and assess the extent of the staging.

  10. Analyst task

    Patch and remediate

    Apply long-term fixes to prevent re-exploitation.

# PHP2Shell: Web-to-Shell Staging

This hunt targets the convergent post-exploitation footprint of PHP core vulnerabilities, where unauthenticated requests trigger a PHP worker to execute arbitrary code. The hunt begins by identifying vulnerable assets and then uses a phased approach to detect the transition from web server processes (like php-fpm or nginx) to shells and language interpreters. By stack-counting unusual parent-child relationships and corroborating them with discovery commands and staging tools, the hunt identifies active compromises where traditional static rules might be bypassed.
