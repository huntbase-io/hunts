# Hunting for Shai-Hulud Developer Environment Poisoning

The release of "Shai-Hulud open source framework static analysis" by Datadog Security Labs (https://securitylabs.datadoghq.com/articles/shai-hulud-open-source-framework-static-analysis/) highlights a sophisticated approach to developer environment compromise. Shai-Hulud is not a simple payload; it is an open-source framework designed to propagate through repository poisoning, specifically targeting the tools engineers use to write and test code.\n\nOur hypothesis for this hunt assumes that an adversary has already compromised a part of the supply chain—perhaps an internal library or a popular public repo—and is now using poisoned configuration files to move laterally to developer workstations. The focus is on VS Code and Claude Code, where automated hooks can be configured to execute commands immediately upon opening a folder.\n\nHow the hunt flows:\n\nThe process begins with scoping. We identify workstations that have VS Code, Git, or the Bun runtime installed. This is not just about finding developer boxes; it is about establishing a baseline of systems where the framework's propagation vectors are viable. Without these tools, Shai-Hulud cannot execute its automated hooks.\n\nNext, we look for the poisoning events. We query file activity for writes to .vscode/tasks.json or .claude/settings.json. We specifically look for writes where the actor process is Git or a local AI agent. This is a high-noise surface because developers modify these files frequently. However, by looking for specific attributes associated with the framework's behavior, we can narrow the results significantly.\n\nThe hunt then pivots to execution. We search for Node.js, Bun, or Bash processes that are running characteristic loader scripts like setup.mjs or config.mjs. Because these filenames are generic, we apply a prevalence stacking filter. We calculate how many hosts in the environment have executed a specific command line within the lookback period. We are looking for the uniqueness of the execution; a malicious loader will typically appear on very few hosts compared to a legitimate company-wide build script.\n\nFinally, we correlate the findings. A workstation that shows a Git-driven write to a configuration hook followed by a rare execution of a setup script represents a high-confidence lead. This behavioral stack is what allows us to identify the infection without the high false-positive rate of a static detection rule.\n\nWhat the hunt cannot see:\n\nVisibility is a major factor here. If your endpoint telemetry does not include process command lines or the contents of written files, you may see the activity but be unable to distinguish it from a benign update. Furthermore, this hunt relies on organization-level logging. If a developer clones a malicious repository from a personal account or a shadow-IT instance that is not onboarded to your central logging, the initial hook-writing event will be invisible to our queries.\n\nHow to run it:\n\nThis hunt is designed as a hunt.md playbook. This format allows you to import the entire logic—including the scoping, queries, and triage steps—directly into Huntbase or any other hunt.md-aware runtime. Because this is a hunt rather than a detection, it is intended to be run periodically or in response to a suspected breach, allowing for the manual oversight needed to validate rare setup scripts.
