# Hunting for Post-Phishing Command and Control via Multi-Hop Proxies

The evolution of phishing lures often moves faster than static detection rules. In the recent article "Train, triage, repeat: The AI agent changing how we fight phishing" (https://redcanary.com/blog/threat-detection/phishing-ai-agent/), the focus is on how automation can help manage the volume of these threats. This hunt design takes a similar approach to the aftermath of a successful lure, focusing on how a payload establishes long-term access through stealthy network channels. We specifically look for the pivot from an initial user-driven execution to command-and-control (C2) traffic masked by multi-hop proxies or the Tor network.\n\n### The Hypothesis\nWe hypothesize that an intruder has gained initial access via a phishing lure and executed a malicious payload. This payload is now communicating with a multi-hop proxy or Tor network to mask its command-and-control traffic, utilizing uncommon ports and DNS patterns to evade standard web filtering and logging.\n\n### How the Hunt Flows\nThe hunt begins with scoping through the `hb_software_inventory` surface. We look for software packages present on three or fewer devices. Malicious payloads dropped via phishing often appear as unique or rare software installations before they begin their execution phase. This narrows our focus to hosts with anomalous software footprints.\n\nNext, we concurrently examine three telemetry surfaces. In `hb_dns_activity`, we look for resolutions of suspicious top-level domains (TLDs) like .top, .zip, or .bid, alongside keywords such as "login" or "verify." This helps identify the initial infrastructure used for the lure or the C2. Simultaneously, we query `hb_process_activity` for productivity applications like Outlook, Word, or Chrome spawning shells or scripting engines. We specifically look for indicators of injected code or off-disk binaries, which are high-confidence signals of exploitation.\n\nFinally, we pivot to `hb_network_connection` to identify rare outbound connections to known proxy ports (e.g., Tor's 9001 or 9050). These connections are correlated by process name to the activity found in the previous steps. An automated agent then synthesizes these signals per host to determine if they form a coordinated attack chain.\n\n### Blind Spots\nThis hunt has two primary blind spots. First, we lack visibility into the email content itself as the `hb_email_activity` surface is currently unavailable; we cannot see the original lure or sender reputation. Second, if a phishing payload uses ephemeral processes that terminate before telemetry snapshots occur, the execution phase may be missed. High-frequency process logging is required to mitigate this risk.\n\n### How to Run This Hunt\nThis hunt is provided as a `hunt.md` playbook. It is designed to be imported into Huntbase or any other `hunt.md`-aware runtime. Because it correlates signals across four different surfaces—inventory, DNS, processes, and network—it functions as a defense-in-depth mechanism rather than a single detection alert. You can adjust the `lookback_days` or `tor_ports` parameters to match your specific environment and threat profile.
