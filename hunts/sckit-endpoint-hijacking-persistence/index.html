SCKit Endpoint Hijacking and Persistence

Brief

Why

Now Recent research by Huntress titled "SCKit Worm Installs Rogue ScreenConnect Clients" (https://www.huntress.com/blog/sckit-worm-rogue-screenconnect) describes a new worm designed to hijack remote management tools. An adversary exploits extensions such as RMM+ to install a rogue toolkit that allows them to take control of the victim's management channel.

The

Hypothesis An intruder exploits vulnerable ScreenConnect extensions to deploy the SCKit toolkit. The adversary hijacks legitimate management sessions through aggressive scheduled tasks and registry persistence to maintain control and facilitate lateral movement across the network.

How the Hunt

Flows The first phase scopes the environment by querying the hb_software_inventory surface. This query identifies every host running ScreenConnect, allowing the hunt to focus its resources on potentially vulnerable systems. By narrowing the scope early, we reduce the volume of data processed in subsequent investigative steps. In the second phase, the hunt searches for early infection leads using hb_process_activity and hb_dns_activity. One query looks for process command lines containing known loaders like Stage0Loader.ps1 or specific SCKit-related strings. Simultaneously, another query checks DNS logs for resolutions to known attacker domains like mo7sen.dev or relaytrap.cs. An automated agent then triages these leads to confirm which hosts show signs of an active infection. The third phase focuses on persistence mechanisms via the hb_scheduled_job and hb_registry_activity surfaces. The hunt specifically searches for the "TrapWatch" scheduled task, which the worm uses to reclaim the ScreenConnect relay slot every 10 seconds. It also inspects registry run keys for entries like "RelayTrapLiteAlert" that launch alerting scripts at user logon. These structural changes are difficult for an adversary to hide without losing control of the hijacked session. In the final phase, an agent synthesizes the evidence from the previous stages to provide a definitive verdict for each host. If the agent confirms a hijack, it provides instructions for host isolation and forensic review. An analyst then confirms the verdict and performs manual remediation, such as examining the ProgramData directory and capturing system memory.

What the Hunt Cannot

See This hunt cannot directly observe the initial exploit payload because it is delivered within an HTTP POST body, which standard hb_http_activity telemetry does not capture. We infer the exploit from the subsequent loader execution and network traffic. Additionally, the hunt is blind to any ScreenConnect instances running on hosts that lack an endpoint agent, as we cannot collect the necessary process, task, or registry data from those systems.

# SCKit Endpoint Hijacking and Persistence

An adversary exploits vulnerable ScreenConnect extensions to deploy the SCKit toolkit, which hijacks legitimate management sessions through aggressive scheduled tasks and registry persistence. This hunt identifies the ScreenConnect estate and then searches for initial scripted loaders and C2 communication. A first agent evaluates these early infection leads. The hunt then examines high-frequency scheduled tasks and registry entries used to suppress legitimate clients. An agent synthesizes the early leads with the persistence evidence to confirm if a host has been successfully hijacked and is being used for further propagation. Finally, an analyst confirms the findings and isolates the affected endpoints.
