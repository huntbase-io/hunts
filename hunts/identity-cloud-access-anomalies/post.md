# Hunting Identity Compromise and Cloud Exfiltration Anomalies

### Why this hunt ￊThe recent discussion in Reports of SIEM's Death Have Been Greatly Exaggerated (https://www.huntress.com/blog/reports-that-siem-is-dead-are-exaggerated) highlights the necessity of centralizing telemetry to find complex attack chains. A single alert for a new inbox rule or a failed login often lacks the context required for a high-confidence verdict. We published this hunt to bridge those gaps, connecting identity-level pressure to cloud-based exfiltration and endpoint-level sabotage.ￊￊ### The Hypothesis ￊAn adversary gains access to a corporate account using credential stuffing or MFA fatigue. Once inside, they establish persistence or exfiltrate data by creating unauthorized mailbox forwarding rules. To secure their position, they may also attempt to dump credentials or inhibit system recovery on accessible endpoints.ￊￊ### How the Hunt Flows ￊThe hunt begins with a scoping phase focused on authentication telemetry. The first query identifies users experiencing high failure rates—suggesting brute-force or MFA fatigue—and service accounts performing interactive logins. This step narrows the investigation from the entire user base to a specific set of high-risk accounts.ￊￊOnce we identify these leads, the hunt fans out into parallel investigations. First, it evaluates geographic rarity. By baselining typical login locations, the hunt flags accounts connecting from countries that are statistically rare for the organization. This helps identify the use of attacker-controlled infrastructure that bypassed identity protections.ￊￊThe second parallel phase pivots to cloud API activity. Specifically, the query searches for the creation or modification of Microsoft 365 inbox rules. It looks for ForwardTo or RedirectTo parameters, which adversaries use to silently collect sensitive correspondence. By scoping this to the accounts flagged in the first phase, we separate legitimate administrative changes from malicious exfiltration.ￊￊThe final phase checks for impact on the local endpoints associated with those users. It looks for commands that delete shadow copies, disable recovery, or attempt to dump the LSASS process. Linking a suspicious cloud login to local host sabotage provides high assurance of a successful compromise, helping the analyst determine a final verdict.ￊￊ### What the Hunt Cannot See ￊThis hunt relies on specific telemetry sources. If the identity provider does not provide geolocation data, the geographic rarity check returns no signal. Furthermore, the hunt is limited by cloud log retention. If an adversary established an inbox rule months ago and your logs only go back thirty days, the current lookback will miss the initial persistence event.ￊￊ### How to Run it ￊThis hunt is an open hunt.md playbook. You can import it directly into Huntbase or any runtime that supports the hunt.md standard. The playbook includes the logic to join authentication, cloud API, and process telemetry into a single investigative flow. You use the provided parameters to tune failure thresholds and geographic rarity to your environment.
