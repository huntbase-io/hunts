Brief

Why this hunt ￊThe recent discussion in

Reports of SIEM's Death Have Been Greatly Exaggerated (https://www.huntress.com/blog/reports-that-siem-is-dead-are-exaggerated) highlights the necessity of centralizing telemetry to find complex attack chains. A single alert for a new inbox rule or a failed login often lacks the context required for a high-confidence verdict. We published this hunt to bridge those gaps, connecting identity-level pressure to cloud-based exfiltration and endpoint-level sabotage.ￊￊ

The

Hypothesis ￊAn adversary gains access to a corporate account using credential stuffing or MFA fatigue. Once inside, they establish persistence or exfiltrate data by creating unauthorized mailbox forwarding rules. To secure their position, they may also attempt to dump credentials or inhibit system recovery on accessible endpoints.ￊￊ

How the Hunt

Flows ￊThe hunt begins with a scoping phase focused on authentication telemetry. The first query identifies users experiencing high failure rates—suggesting brute-force or MFA fatigue—and service accounts performing interactive logins. This step narrows the investigation from the entire user base to a specific set of high-risk accounts.ￊￊOnce we identify these leads, the hunt fans out into parallel investigations. First, it evaluates geographic rarity. By baselining typical login locations, the hunt flags accounts connecting from countries that are statistically rare for the organization. This helps identify the use of attacker-controlled infrastructure that bypassed identity protections.ￊￊThe second parallel phase pivots to cloud API activity. Specifically, the query searches for the creation or modification of Microsoft 365 inbox rules. It looks for ForwardTo or RedirectTo parameters, which adversaries use to silently collect sensitive correspondence. By scoping this to the accounts flagged in the first phase, we separate legitimate administrative changes from malicious exfiltration.ￊￊThe final phase checks for impact on the local endpoints associated with those users. It looks for commands that delete shadow copies, disable recovery, or attempt to dump the LSASS process. Linking a suspicious cloud login to local host sabotage provides high assurance of a successful compromise, helping the analyst determine a final verdict.ￊￊ

What the Hunt Cannot

See ￊThis hunt relies on specific telemetry sources. If the identity provider does not provide geolocation data, the geographic rarity check returns no signal. Furthermore, the hunt is limited by cloud log retention. If an adversary established an inbox rule months ago and your logs only go back thirty days, the current lookback will miss the initial persistence event.ￊￊ

How to

Run it ￊThis hunt is an open hunt.md playbook. You can import it directly into Huntbase or any runtime that supports the hunt.md standard. The playbook includes the logic to join authentication, cloud API, and process telemetry into a single investigative flow. You use the provided parameters to tune failure thresholds and geographic rarity to your environment.

Steps

  1. Authentication Anomaly Lead

    Query · scoping

    Identify users with high failure rates or service accounts logging into interactive services.

    reads hb_auth_signinsql
    SELECT LOWER(actor_user_name) AS user, COUNT(CASE WHEN activity_id = 5 THEN 1 END) AS failures, COUNT(CASE WHEN activity_id = 1 AND (LOWER(actor_user_name) LIKE '%svc-%' OR LOWER(actor_user_name) LIKE '%service%') THEN 1 END) AS service_logons, MIN(time) AS first_attempt, MAX(time) AS last_attempt FROM hb_auth_signin WHERE time >= datetime('now', '-{{lookback_days}} days') GROUP BY LOWER(actor_user_name) HAVING failures >= {{mfa_failure_threshold}} OR service_logons > 0 ORDER BY failures DESC

    What a hit looks like. Rows identify users targeted by brute-force or service accounts acting as users. Silence suggests no detected identity-level hammering.

  2. Geographic Rarity Check

    Query · baseline

    Identify logins from countries that are rare for the organization or identified users.

    reads hb_auth_signinsql
    SELECT src_location_country, COUNT(DISTINCT actor_user_name) AS distinct_users, MIN(time) AS first_seen FROM hb_auth_signin WHERE activity_id = 1 AND ('{{scope_users}}' = '' OR instr(',' || '{{scope_users}}' || ',', ',' || LOWER(actor_user_name) || ',') > 0) AND time >= datetime('now', '-{{lookback_days}} days') GROUP BY src_location_country HAVING distinct_users <= {{rare_country_threshold}}

    What a hit looks like. A list of countries associated with very few users, suggesting attacker infrastructure.

  3. Mailbox Rule Forwarding

    Query · detection candidate

    Search for Microsoft 365 inbox rule creations that redirect mail to external recipients.

    reads hb_cloud_api_activitysql
    SELECT time, actor_user_name, api_operation, target_modified_property_new_values FROM hb_cloud_api_activity WHERE provider = 'm365' AND LOWER(api_operation) IN ('new-inboxrule', 'set-inboxrule') AND (instr(LOWER(target_modified_property_new_values), 'forwardto') > 0 OR instr(LOWER(target_modified_property_new_values), 'redirectto') > 0) AND ('{{scope_users}}' = '' OR instr(',' || '{{scope_users}}' || ',', ',' || LOWER(actor_user_name) || ',') > 0) AND time >= datetime('now', '-{{lookback_days}} days')

    What a hit looks like. Cloud API records of users modifying inbox rules to redirect email. Silence is evidence of absence if logs are complete.

  4. Endpoint Impact Check

    Query · triage

    Check for LSASS memory access or recovery inhibition on the scoped hosts.

    reads hb_process_activitysql
    SELECT device_hostname, process_cmd_line, user_name, time FROM hb_process_activity WHERE (LOWER(process_cmd_line) LIKE '%vssadmin%delete%shadows%' OR LOWER(process_cmd_line) LIKE '%wbadmin%delete%catalog%' OR LOWER(process_cmd_line) LIKE '%bcdedit%/set%recoveryenabled%no%' OR LOWER(process_name) LIKE '%mimikatz%' OR LOWER(process_name) LIKE '%procdump%') AND ('{{scope_hosts}}' = '' OR instr(',' || '{{scope_hosts}}' || ',', ',' || device_hostname || ',') > 0) AND time >= datetime('now', '-{{lookback_days}} days')

    What a hit looks like. Any row indicates an attempt to sabotage recovery or dump credentials on a host involved in the authentication anomalies.

# Identity and Cloud Access Anomalies

This hunt detects accounts under brute-force or MFA fatigue pressure and links them to rare geographic logins and unauthorized inbox forwarding. It connects identity compromise to data collection by joining authentication telemetry with cloud API logs. The flow evaluates authentication anomalies alongside geographic rarity and endpoint impact indicators like LSASS memory access or system recovery inhibition.

## auth-anomaly-lead
<!-- Authentication Anomaly Lead -->
Identify users with high failure rates or service accounts logging into interactive services.

```sqlite target=identity role=scoping params=(lookback_days=lookback_days, mfa_failure_threshold=mfa_failure_threshold)
~~~yaml

  users. Silence suggests no detected identity-level hammering.

- actor_user_name
- activity_id
- time
silence: not_evidence_of_absence
source: hb_auth_signin
```
