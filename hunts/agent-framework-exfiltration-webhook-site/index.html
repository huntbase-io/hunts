Agent-Framework Exfiltration to Webhook.site

High severity TLP:CLEAR Part 2 of 2 Research by Elastic Security Labs Published 19 Nov 2026

Hypothesis

An intruder is exfiltrating harvested cloud and developer credentials from Python runtimes to a malicious webhook.site endpoint following the agent-framework PyPI compromise.

Brief

Why This Hunt Matters

Elastic Security Labs recently detailed a supply-chain attack in their article, "We caught the agent-framework PyPI compromise six minutes after it published" (https://www.elastic.co/security-labs/threat-command/we-caught-the-agent-framework-pypi-compromise-six-minutes-after-it-published). The compromise involved malicious Python packages that harvest Azure and GitHub credentials from developer environments. This hunt focuses on the exfiltration phase where the adversary moves stolen secrets to a malicious endpoint.

Phase 1: DNS Lead Lookups

The hunt begins by identifying every host where a Python process resolves the webhook.site domain. While developers use this domain for testing, resolutions coming from CI/CD runners or production build servers provide a high-confidence lead. The query filters for the Python executable name to narrow the scope to relevant runtime activity across the enterprise.

Phase 2: Correlating HTTP and Network Evidence

Once the hunt identifies a lead host, it performs a parallel check across HTTP and network surfaces. It searches for POST requests that contain specific malicious metadata, such as the af-runtime-diagnostics User-Agent or the unique UUID fragment d381fd80-ec62-42ad-8f5c-d1b15103c9bb in the URL path. Simultaneously, the hunt analyzes outbound network flows from Python processes to public IP addresses. This step provides visibility even when the traffic is encrypted or when HTTP headers are unavailable, by highlighting rare or unusual connection patterns from the runtime. It looks for Python processes making infrequent outbound connections to public endpoints that do not match internal CIDR blocks.

Phase 3: Evidence Weighing and Triage

An automated agent or an analyst weighs the collected evidence to produce a verdict. A match on both the custom User-Agent and the known malicious domain triggers a high-severity malicious verdict. If the hunt only identifies rare network connections to the domain without HTTP metadata, it flags the host as suspicious for manual review. This multi-layered approach ensures that legitimate developer traffic does not drown out the actual theft. The analyst confirms the verdict by reviewing the specific rows of telemetry before initiating containment or secret rotation.

Blind Spots

The hunt faces two primary blind spots. First, if the environment does not use TLS inspection or proxy logging, the HTTP metadata check cannot see the User-Agent or the URL path for encrypted traffic. In this scenario, the hunt relies on DNS and network flow metadata, which may increase the false positive rate. Second, exfiltration occurring from ephemeral containers or short-lived build runners may be lost if the logs are not persisted outside the container lifecycle. Security teams should ensure that CI/CD pipeline logs are forwarded to a central repository to maintain visibility.

# Agent-Framework Exfiltration to Webhook.site

This hunt targets the network-based exfiltration stage of the agent-framework supply-chain compromise. It identifies Python processes resolving and connecting to webhook.site infrastructure used by the stealer. The hunt uses a funnel flow to find DNS leads, then corroborates them with HTTP metadata (specific User-Agents and URL paths) and network flow patterns. By checking for the specific af-runtime-diagnostics User-Agent and the zlib-compressed POST behavior, it differentiates malicious exfiltration from legitimate developer testing of webhook endpoints.

## dns-lead-lookups
<!-- Python DNS lookups for webhook.site -->
Find hosts where a Python runtime resolved the exfiltration infrastructure, acting as the primary lead for the funnel.

```sqlite target=endpoint role=baseline params=(exfil_domains=exfil_domains, lookback_days=lookback_days)
~~~yaml

  compare: first_seen
  window: '{{lookback_days}}d'

  from build agents or servers are high-confidence indicators of potential compromise.
```
