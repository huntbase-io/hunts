# Hunting for Agent-Framework PyPI Exfiltration to Webhook.site

### Why This Hunt Matters Elastic Security Labs recently detailed a supply-chain attack in their article, "We caught the agent-framework PyPI compromise six minutes after it published" (https://www.elastic.co/security-labs/threat-command/we-caught-the-agent-framework-pypi-compromise-six-minutes-after-it-published). The compromise involved malicious Python packages that harvest Azure and GitHub credentials from developer environments. This hunt focuses on the exfiltration phase where the adversary moves stolen secrets to a malicious endpoint. ### The Hypothesis The adversary exfiltrates harvested cloud and developer credentials from Python runtimes to a malicious webhook.site endpoint. This activity occurs immediately after the package installation or during the execution of infected scripts. The stealer specifically targets Azure and GitHub authentication tokens stored in environment variables or configuration files. ### Phase 1: DNS Lead Lookups The hunt begins by identifying every host where a Python process resolves the webhook.site domain. While developers use this domain for testing, resolutions coming from CI/CD runners or production build servers provide a high-confidence lead. The query filters for the Python executable name to narrow the scope to relevant runtime activity across the enterprise. ### Phase 2: Correlating HTTP and Network Evidence Once the hunt identifies a lead host, it performs a parallel check across HTTP and network surfaces. It searches for POST requests that contain specific malicious metadata, such as the af-runtime-diagnostics User-Agent or the unique UUID fragment d381fd80-ec62-42ad-8f5c-d1b15103c9bb in the URL path. Simultaneously, the hunt analyzes outbound network flows from Python processes to public IP addresses. This step provides visibility even when the traffic is encrypted or when HTTP headers are unavailable, by highlighting rare or unusual connection patterns from the runtime. It looks for Python processes making infrequent outbound connections to public endpoints that do not match internal CIDR blocks. ### Phase 3: Evidence Weighing and Triage An automated agent or an analyst weighs the collected evidence to produce a verdict. A match on both the custom User-Agent and the known malicious domain triggers a high-severity malicious verdict. If the hunt only identifies rare network connections to the domain without HTTP metadata, it flags the host as suspicious for manual review. This multi-layered approach ensures that legitimate developer traffic does not drown out the actual theft. The analyst confirms the verdict by reviewing the specific rows of telemetry before initiating containment or secret rotation. ### Blind Spots The hunt faces two primary blind spots. First, if the environment does not use TLS inspection or proxy logging, the HTTP metadata check cannot see the User-Agent or the URL path for encrypted traffic. In this scenario, the hunt relies on DNS and network flow metadata, which may increase the false positive rate. Second, exfiltration occurring from ephemeral containers or short-lived build runners may be lost if the logs are not persisted outside the container lifecycle. Security teams should ensure that CI/CD pipeline logs are forwarded to a central repository to maintain visibility. ### Running the Hunt The hunt imports into Huntbase or any hunt.md-aware runtime as a playbook. Because it is a hunt rather than a static detection, it allows you to explore the relationship between the runtime and the network before making a containment decision. This is critical for environments where webhook.site is a common tool for legitimate testing. The playbook approach provides a repeatable structure for verifying that no credentials were stolen during the active window of the agent-framework compromise.
