Ransomware Recovery Inhibition and Encryption

An adversary is inhibiting system recovery by deleting volume shadow copies using standard tools or scripts before performing mass file encryption with rare extensions.

Brief

Recovery Inhibition Correlation

In the recent article Microsoft VSS: Still Essential, But Not the Whole Story (https://www.huntress.com/blog/microsoft-vss-limits-and-best-practices), the team explores the limits of volume shadow copies. Building on those insights, we developed a hunt that focuses on the moment an adversary turns a system's recovery tools against it. An adversary inhibits system recovery by deleting volume shadow copies using standard tools or scripts before performing mass file encryption with rare extensions. This strategy ensures that even if the encryption is detected, the victim cannot simply roll back to a previous state. While VSS is a standard feature of Windows, its fragility makes it a primary target during the impact phase of an intrusion. Detecting the deletion of a shadow copy in isolation often yields too much noise, as backup agents and administrators perform these actions regularly. This hunt solves that by looking for the sequence of inhibition followed by impact.

How the Hunt Flows

The hunt starts by scoping the environment for process activity. The initial query identifies hosts where the adversary is actively dismantling recovery options by looking for specific command-line arguments in vssadmin.exe, wmic.exe, and PowerShell that indicate a delete shadow operation. Once the hunt identifies a potential lead, it fans out to gather corroborating evidence. The second phase monitors for script-based deletions using WMI calls like Win32_ShadowCopy. This catches attackers who avoid the command line by calling the WMI methods directly through script blocks. Simultaneously, the hunt checks for the creation of common ransom notes such as readme.txt or decrypt.txt and calculates a baseline of file rename activity. The final phase of the hunt uses an agent to evaluate the combined evidence. It specifically looks for a high volume of file renames to extensions that are rare across the rest of the fleet. The agent evaluates if the deletion and encryption processes share the same parent or user context, which is a high-confidence indicator of a compromise. It also checks for the prevalence of these actions across the fleet to ensure that a site-wide backup job isn't misidentified as an attack. By matching the process responsible for VSS deletion with the process performing the renames, the hunt distinguishes a live ransomware event from scheduled maintenance. An analyst reviews the cited evidence to confirm the final verdict before initiating isolation.

Blind Spots

This hunt has two primary blind spots. If an adversary uses a custom binary to call VSS APIs directly without using the CLI or script engines, the initial scoping query will not see the activity. Additionally, some endpoint sensors truncate event logs when they detect high-volume file activity. This can mask the full scale of the encryption, though the presence of rare extensions usually remains visible.

    Query · enrichment

    Find programmatic shadow copy deletion in script blocks that might bypass process monitoring.

    reads hb_script_activitysql

    What a hit looks like. Script blocks calling the WMI Delete method on shadow objects. Silence proof of absence depends on script block logging coverage.

  3. Ransom Note Creation

    Query · enrichment

    Find creation of files matching a known list of ransom-note names.

    reads hb_file_activitysql

    What a hit looks like. Creation of files like readme.txt or decrypt.txt in multiple directories.

  4. Mass Renames to Rare Extensions

    Query · baseline

    Stack-count file renames to identify anomalous volume of extensions that are rare across the fleet.

    reads hb_file_activitysql
    SELECT device_hostname, process_name, actor_user_name AS user_name, LOWER(SUBSTR(file_name, INSTR(file_name, '.') + 1)) AS extension, COUNT(*) AS event_count, MIN(time) AS first_seen FROM hb_file_activity WHERE activity_id = 5 AND file_name LIKE '%.%' AND time >= datetime('now', '-{{lookback_days}} days') AND ('{{scope_hosts}}' = '' OR instr(',' || '{{scope_hosts}}' || ',', ',' || device_hostname || ',') > 0) GROUP BY device_hostname, process_name, user_name, extension HAVING event_count > 500

    What a hit looks like. A high volume of renames to a single extension that is not common across the fleet.

# Ransomware Recovery Inhibition and Encryption

This hunt identifies the destructive impact phase of a ransomware intrusion by looking for recovery inhibition and data encryption. It lead-scopes the estate for the use of VSS-manipulation tools, then fans out to corroborate this with scripted shadow copy deletion, the creation of known ransom-note filenames, and fleet-wide anomalous file rename activity. An agent evaluates the combined evidence to distinguish between legitimate administrative maintenance and a live ransomware event.

