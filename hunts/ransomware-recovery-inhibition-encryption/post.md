# Finding Ransomware Recovery Inhibition and Mass File Encryption

### Recovery Inhibition Correlation. In the recent article Microsoft VSS: Still Essential, But Not the Whole Story (https://www.huntress.com/blog/microsoft-vss-limits-and-best-practices), the team explores the limits of volume shadow copies. Building on those insights, we developed a hunt that focuses on the moment an adversary turns a system's recovery tools against it. An adversary inhibits system recovery by deleting volume shadow copies using standard tools or scripts before performing mass file encryption with rare extensions. This strategy ensures that even if the encryption is detected, the victim cannot simply roll back to a previous state. While VSS is a standard feature of Windows, its fragility makes it a primary target during the impact phase of an intrusion. Detecting the deletion of a shadow copy in isolation often yields too much noise, as backup agents and administrators perform these actions regularly. This hunt solves that by looking for the sequence of inhibition followed by impact. ### How the Hunt Flows. The hunt starts by scoping the environment for process activity. The initial query identifies hosts where the adversary is actively dismantling recovery options by looking for specific command-line arguments in vssadmin.exe, wmic.exe, and PowerShell that indicate a delete shadow operation. Once the hunt identifies a potential lead, it fans out to gather corroborating evidence. The second phase monitors for script-based deletions using WMI calls like Win32_ShadowCopy. This catches attackers who avoid the command line by calling the WMI methods directly through script blocks. Simultaneously, the hunt checks for the creation of common ransom notes such as readme.txt or decrypt.txt and calculates a baseline of file rename activity. The final phase of the hunt uses an agent to evaluate the combined evidence. It specifically looks for a high volume of file renames to extensions that are rare across the rest of the fleet. The agent evaluates if the deletion and encryption processes share the same parent or user context, which is a high-confidence indicator of a compromise. It also checks for the prevalence of these actions across the fleet to ensure that a site-wide backup job isn't misidentified as an attack. By matching the process responsible for VSS deletion with the process performing the renames, the hunt distinguishes a live ransomware event from scheduled maintenance. An analyst reviews the cited evidence to confirm the final verdict before initiating isolation. ### Blind Spots. This hunt has two primary blind spots. If an adversary uses a custom binary to call VSS APIs directly without using the CLI or script engines, the initial scoping query will not see the activity. Additionally, some endpoint sensors truncate event logs when they detect high-volume file activity. This can mask the full scale of the encryption, though the presence of rare extensions usually remains visible. ### Running the Playbook. You can run this hunt as a hunt.md playbook. It imports directly into Huntbase or any other runtime that supports the hunt.md standard. This allows you to parameterize the lookback period and the list of known ransom notes to fit your environment. Because this is a hunt.md playbook, it remains portable. You can run it manually against a single host if you suspect an ongoing incident, or schedule it as a periodic check across your entire estate. The parameters allow you to add custom ransomware extensions or exclude specific administrative accounts that perform legitimate shadow copy deletions.
