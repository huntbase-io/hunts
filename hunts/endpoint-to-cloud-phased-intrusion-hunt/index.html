Endpoint-to-Cloud Phased Intrusion Hunt

An adversary establishes a beachhead on an endpoint, moves laterally to obtain administrative access, and pivots to cloud services while maintaining C2 via a multi-hop proxy.

Brief

The Cost of Complex Intrusions

The source article, "Inside Elastic InfoSec's agentic SOC: When to inline your agent's skills for a 5× cost reduction" (https://www.elastic.co/security-labs/blog/agentic-soc-token-budget-architecture), discusses the need for cost-efficient analysis in complex environments. This hunt implements those principles by using a phased workflow to identify adversaries who transition from local host compromise to cloud-based lateral movement. This type of multi-surface activity is difficult to capture with static detection rules alone.

How the Hunt Flows

The hunt starts with a scoping phase to identify recently active hosts. The first query searches the hb_devices surface to build a list of targets for deeper investigation. This ensures the hunt focuses on relevant, active systems rather than the entire historical fleet. Next, the hunt enters a parallel forensics phase. One query scans hb_process_activity for binaries running from user-writable or temporary paths, such as ProgramData or Public. It specifically looks for fileless execution or anomalies where the process name does not match the on-disk binary. A second query monitors hb_network_connection for outbound traffic on ports 22, 445, 3389, and proxy ports like 9001 or 1080. By stack counting these connections across the fleet, the hunt identifies outliers—individual hosts making rare administrative or proxy-bound connections. An early-triage agent then processes these forensics and network results. The agent evaluates the severity of the findings and decides which hosts represent a likely beachhead. Crucially, the agent extracts the source IP addresses of these suspicious hosts. These IPs become the primary filter for the next phase of the hunt. The hunt then pivots to identity and command-and-control obfuscation. It queries hb_auth_signin for successful cloud logins, but only for those sessions originating from the previously identified suspicious IPs. At the same time, it checks hb_dns_activity for lookups to multi-hop proxy domains or Tor Onion addresses. This approach connects the local forensic evidence of a compromise to the subsequent cloud activity. A final synthesis agent reviews the entire chain. It combines the host-level alerts, the lateral movement patterns, and the cloud authentication data into a single verdict. If the agent confirms a high-confidence intrusion, it triggers a routing decision to isolate the host and alert an analyst.

Blind Spots

Analysts must account for two primary blind spots. First, while the hunt detects the use of multi-hop proxies via DNS and port activity, the specific content of those communications is often encrypted. Without TLS decryption at the network gateway, we cannot see the adversary's intent or the stage-two payloads. Second, the hunt currently lacks file-level visibility on macOS systems. This means we cannot verify local data staging or credential harvesting on non-Windows endpoints through this specific playbook.

How to Run the Hunt

This hunt is structured as a hunt.md playbook. It imports directly into Huntbase or any compatible runtime that understands the hunt.md specification. Because the hunt is phased, you can run the scoping and early forensic steps as a regular health check and only trigger the identity pivots and agent triage when the first indicators appear.

    Query · detection candidate

    Find processes running from temporary paths or in-memory.

    What a hit looks like. A process with no file on disk or a binary executing from a user-writable path. Silence suggests an absence of simple fileless execution.

  3. Admin and Proxy Egress Stack Counting

    Query · baseline

    Stack outbound connections by port to find rare administrative or proxy egress.

    reads hb_network_connectionsql
    SELECT device_hostname, src_endpoint_ip, dst_endpoint_ip, dst_endpoint_port, process_name, COUNT(DISTINCT device_hostname) AS hosts, COUNT(*) AS connections, MIN(time) AS first_seen FROM hb_network_connection WHERE direction = 'outbound' AND (instr(',' || '{{admin_ports}}' || ',', ',' || CAST(dst_endpoint_port AS TEXT) || ',') > 0 OR instr(',' || '{{proxy_ports}}' || ',', ',' || CAST(dst_endpoint_port AS TEXT) || ',') > 0) AND time >= datetime('now', '-{{lookback_days}} days') AND ('{{scope_hosts}}' = '' OR instr(',' || '{{scope_hosts}}' || ',', ',' || device_hostname || ',') > 0) GROUP BY device_hostname, src_endpoint_ip, dst_endpoint_ip, dst_endpoint_port, process_name HAVING hosts <= 3

    What a hit looks like. Outbound connections on administrative or proxy ports. Rarity identifies single-host outliers amidst normal network traffic.

  4. Early Intrusion Triage

    Agent triage

    An agent weighs the forensic process data and lateral movement rows to confirm a beachhead.

  5. Cloud Identity Success from Beachheads

    Query · enrichment

    Filter sign-in events by the IP addresses identified in the early-triage-agent step.

    reads hb_auth_signinsql
    SELECT actor_user_name, src_endpoint_ip, dst_endpoint_name, provider, auth_protocol, time FROM hb_auth_signin WHERE status_id = 1 AND time >= datetime('now', '-{{lookback_days}} days') AND ('{{suspected_src_ips}}' = '' OR instr(',' || '{{suspected_src_ips}}' || ',', ',' || src_endpoint_ip || ',') > 0)

    What a hit looks like. Successful authentications correlated with suspected compromised source IPs. Silence means no cloud logins were recorded for the identified hosts.

  6. Proxy and ORB Domain Lookups

    Query · triage

    Detect DNS resolutions to known proxy domains or Tor gateways.

    reads hb_dns_activitysql
    SELECT device_hostname, query_hostname, process_name, COUNT(*) as lookup_count FROM hb_dns_activity WHERE (instr(',' || '{{c2_domains}}' || ',', ',' || LOWER(query_hostname) || ',') > 0 OR query_hostname LIKE '%.onion%') AND time >= datetime('now', '-{{lookback_days}} days') AND ('{{scope_hosts}}' = '' OR instr(',' || '{{scope_hosts}}' || ',', ',' || device_hostname || ',') > 0) GROUP BY device_hostname, query_hostname, process_name

    What a hit looks like. Any lookup to an ORB domain or Tor gateway.

  7. Full Chain Synthesis Agent

    Agent triage

    A second agent synthesizes the entire intrusion path by linking host compromise to follow-on cloud and network signals.

  8. Routing Decision for Intrusion Chain

    Decision

    Route the hunt based on the synthesized full-chain verdict.

  9. Isolate Compromised Endpoint

    Response action

    Isolate the confirmed host to stop further lateral movement and C2 communication.

  10. Analyst Intrusion Verification

    Analyst task

    An analyst verifies the full-chain evidence and confirms the incident findings.

  11. Hunt Closure

    Analyst task

    Record a negative result and archive the hunt.

# Endpoint-to-Cloud Phased Intrusion Hunt

This hunt implements a cost-efficient specialized agent workflow to identify long-chain intrusions. It begins by scoping the host environment and identifying early forensic anomalies and lateral movement. A second phase investigates follow-on identity pivots and command-and-control obfuscation through multi-hop proxies and ORB networks. By phasing the hunt, the agentic triage focuses only on high-confidence leads that connect host compromise to cloud exposure.
