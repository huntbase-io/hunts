# Hunting Intrusion Chains from Endpoint Beachheads to Cloud Pivots

### The Cost of Complex Intrusions The source article, "Inside Elastic InfoSec's agentic SOC: When to inline your agent's skills for a 5× cost reduction" (https://www.elastic.co/security-labs/blog/agentic-soc-token-budget-architecture), discusses the need for cost-efficient analysis in complex environments. This hunt implements those principles by using a phased workflow to identify adversaries who transition from local host compromise to cloud-based lateral movement. This type of multi-surface activity is difficult to capture with static detection rules alone. ### The Hypothesis An adversary establishes a beachhead on an endpoint, moves laterally to obtain administrative access, and pivots to cloud services while maintaining C2 via a multi-hop proxy. The attack path follows a predictable chain: initial execution in a temporary directory, internal network propagation using admin ports, and eventually the use of stolen cloud credentials from the same source IP. ### How the Hunt Flows The hunt starts with a scoping phase to identify recently active hosts. The first query searches the hb_devices surface to build a list of targets for deeper investigation. This ensures the hunt focuses on relevant, active systems rather than the entire historical fleet. Next, the hunt enters a parallel forensics phase. One query scans hb_process_activity for binaries running from user-writable or temporary paths, such as ProgramData or Public. It specifically looks for fileless execution or anomalies where the process name does not match the on-disk binary. A second query monitors hb_network_connection for outbound traffic on ports 22, 445, 3389, and proxy ports like 9001 or 1080. By stack counting these connections across the fleet, the hunt identifies outliers—individual hosts making rare administrative or proxy-bound connections. An early-triage agent then processes these forensics and network results. The agent evaluates the severity of the findings and decides which hosts represent a likely beachhead. Crucially, the agent extracts the source IP addresses of these suspicious hosts. These IPs become the primary filter for the next phase of the hunt. The hunt then pivots to identity and command-and-control obfuscation. It queries hb_auth_signin for successful cloud logins, but only for those sessions originating from the previously identified suspicious IPs. At the same time, it checks hb_dns_activity for lookups to multi-hop proxy domains or Tor Onion addresses. This approach connects the local forensic evidence of a compromise to the subsequent cloud activity. A final synthesis agent reviews the entire chain. It combines the host-level alerts, the lateral movement patterns, and the cloud authentication data into a single verdict. If the agent confirms a high-confidence intrusion, it triggers a routing decision to isolate the host and alert an analyst. ### Blind Spots Analysts must account for two primary blind spots. First, while the hunt detects the use of multi-hop proxies via DNS and port activity, the specific content of those communications is often encrypted. Without TLS decryption at the network gateway, we cannot see the adversary's intent or the stage-two payloads. Second, the hunt currently lacks file-level visibility on macOS systems. This means we cannot verify local data staging or credential harvesting on non-Windows endpoints through this specific playbook. ### How to Run the Hunt This hunt is structured as a hunt.md playbook. It imports directly into Huntbase or any compatible runtime that understands the hunt.md specification. Because the hunt is phased, you can run the scoping and early forensic steps as a regular health check and only trigger the identity pivots and agent triage when the first indicators appear.
