EvilTokens Client-Side Phishing Interaction

An intruder has delivered an AI-tailored phishing lure that, when opened, initiates high-frequency background polling to a malicious Node.js endpoint while redirecting the user to the Microsoft device login portal.

Brief

Why Now

The Microsoft Security Blog recently detailed the mechanics of EvilTokens in the article Unmasking EvilTokens: Getting to the root of device code phishing (https://www.microsoft.com/en-us/security/blog/2026/09/22/unmasking-eviltokens-getting-to-the-root-of-device-code-phishing/). This PhaaS platform has already compromised thousands of organizations by automating the capture of session tokens through device code phishing. Because the platform uses AI to tailor lures and frequently rotates its infrastructure, traditional indicator-based detections often fail to catch the initial interaction. This hunt addresses that gap by focusing on the persistent behavioral patterns inherent to the platform's operation.

How the Hunt Flows

The first phase targets the initial delivery mechanism. A query searches the hb_file_activity surface for the creation of new files in user-writable directories such as Downloads or the Desktop. It specifically looks for HTML, HTM, or PDF files that use lure themes identified in the research, including invoices, RFPs, proposals, or compensation benefits. While the presence of these files is not definitive proof of an attack, they provide the necessary context for the subsequent behavioral checks. The second phase pivots to network behavior to identify the characteristic 3-5 second polling interval used by the EvilTokens background script. The hunt queries the hb_http_activity surface for requests containing a /state path sent to non-trusted domains. By grouping these requests by host and calculating the average time between pings, the hunt identifies the automated polling behavior of the checkStatus function. A consistent gap of less than six seconds over multiple requests strongly suggests a phishing kit loop rather than manual user activity. The third phase checks for concurrent navigation to the legitimate Microsoft device login portal. The EvilTokens script redirects users to this portal to complete the device code entry. The hunt looks for hits on the /devicelogin path on microsoft.com that occur in the same timeframe as the suspicious background polling. This correlation is the key to identifying a high-confidence phishing interaction. Finally, an analyst or automated agent triages these combined signals. The agent reviews the file touches, the frequency of the background pings, and the portal redirection to assign a verdict of malicious, suspicious, or benign for each host. This multi-surface approach ensures that the hunt finds active phishing sessions even when the specific URLs or file hashes are previously unseen.

What This Hunt Cannot See

This hunt has two primary blind spots. First, it requires visibility into the HTTP path to identify the /state polling endpoint. If the environment only provides SNI-level visibility into encrypted traffic, the timing pattern remains visible but the specific endpoint path does not. Second, the hunt may miss lures that never touch the disk. If a user interacts with a phishing link directly within their browser without downloading a file, the file activity surface will not record any lure creation.

# EvilTokens Client-Side Phishing Interaction

EvilTokens is a PhaaS platform that specializes in device code phishing. This hunt identifies the early stages of an attack by detecting the characteristic 3-5 second polling interval of the background script ('checkStatus') and the concurrent user redirection to microsoft.com/devicelogin. By correlating these behaviors with the presence of suspicious invoice or RFP-themed lure files, we can identify sessions that are actively being phished before token theft is completed. This behavioral approach bypasses rotating domains and AI-generated lures that evade standard signature-based controls.
