Advanced Persistence and Payload Staging

High severity TLP:CLEAR Part 2 of 2 Research by Rapid7 Published 18 Nov 2026

Hypothesis

An intruder is staging non-standard architecture payloads using multi-protocol fetch adapters and establishing persistence via Linux ELF binary injection or privileged Docker containers with host root mounts.

Brief

Why this hunt?

Recent updates in the Metasploit Wrapup: Unauth RCE modules in Network Perimeter Devices and much more (https://www.rapid7.com/blog/post/pt-metasploit-wrapup-unauth-rce-modules-in-network-perimeter-devices-and-much-more) highlight a move toward more robust post-exploitation modules for perimeter devices. Adversaries are moving beyond simple commands to drop specialized payloads and secure their foothold on non-standard architectures.

How the hunt flows

The hunt begins with a broad search for execution leads on the endpoint. It identifies mentions of the LoongArch64 architecture in command lines, the use of chmod to prepare binaries in temporary directories, and the creation of Docker containers with privileged access or host filesystem mounts. This step acts as a low-cost filter to identify potentially compromised hosts.

Once the lead query identifies a suspect host, the hunt opens two parallel investigations. The first examines network activity, looking for rare outbound connections on FTP, TFTP, or HTTP from common utilities like curl and wget. The query focuses on destinations that appear on three or fewer hosts to find attacker-controlled staging infrastructure.

Simultaneously, the hunt audits the integrity of system-critical binaries and staging paths. It identifies file creations or modifications in standard binary directories like /bin and /usr/bin. This surfaces cases where an attacker replaces a legitimate utility with a malicious ELF binary to ensure persistence.

The final phase triages these results. An analyst or agent correlates the initial execution behavior with the subsequent network and file evidence. By linking the staging process with the resulting persistent state, the hunt provides a high-confidence verdict for containment.

What this hunt cannot see

This hunt relies on EDR process and file telemetry. If an adversary modifies an ELF binary via direct disk writes that bypass standard system calls, the file activity surface may not capture the change. Additionally, if the initial staging occurs on a device without process auditing, the lead query will remain silent, and the hunt will not progress to the deeper audit phases.

Blind spots

  • Needs EDR process logging on every endpoint. A host without process auditing will never trigger the lead query, allowing the intrusion to proceed unseen. It would answer: whether the initial fetch or chmod commands were executed
  • Needs Full network and file auditing across the estate. The fan-out queries depend on file and network surfaces; missing telemetry here prevents corroboration of the lead. It would answer: whether the follow-on staging activity occurred on hosts without deep auditing
  • Needs Kernel-level file integrity monitoring. Sophisticated persistence that writes directly to disk blocks may not appear in hb_file_activity. It would answer: whether an ELF binary was modified via direct disk access bypassing standard syscalls

# Advanced Persistence and Payload Staging

This hunt examines tradecraft associated with recent Metasploit releases, focusing on post-exploitation staging and persistence. It targets the delivery of LoongArch64 payloads via FTP, TFTP, and HTTP, the modification of system-critical ELF binaries on Linux, and the use of Docker containers to mount host filesystems for high-privilege persistence. The hunt uses a gated flow, starting with a cheap lead query for suspicious process behavior before opening detailed network and file-level audits for corroboration.

## network-fetch-audit
<!-- Audit fetch protocol activity -->
Corroborate staging leads with rare outbound connections on FTP, TFTP, or HTTP from fetch-related binaries.

```sqlite target=network role=baseline params=(lookback_days=lookback_days, scope_hosts=scope_hosts)
~~~yaml

  window: '{{lookback_days}}d'
```
