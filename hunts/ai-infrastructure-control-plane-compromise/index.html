Brief

Microsoft's recent analysis, "When AI infrastructure becomes the target" (https://www.microsoft.com/en-us/security/blog/2026/08/26/when-ai-infrastructure-becomes-target-securing-gateways-control-points/), highlights a shift in adversary focus. As organizations deploy AI gateways like LiteLLM or RAGFlow to manage model access, these services become high-value control planes. A single compromise here grants access to API keys for multiple LLM providers and the backend databases where sensitive RAG data resides.\n\nOur hypothesis is that an adversary exploits exposed AI gateway services to harvest runtime environment secrets, dump backend model databases, and establish persistence or resource hijacking via cryptomining.\n\nThe hunt begins by scoping the environment. We look for specific AI orchestration software like LiteLLM, RAGFlow, and Kestra within the software inventory. Identifying these hosts allows us to focus subsequent, noisier queries on the relevant infrastructure and containerized workloads.\n\nThe first triage step examines HTTP activity for signs of exploitation. Specifically, we look for POST requests to the Model Context Protocol (MCP) rest endpoints. These endpoints were recently identified as part of an RCE chain (CVE-2026-42271). While we cannot always see the payload body, the presence of these requests to testing endpoints on internal gateways is a strong indicator of unauthorized interest.\n\nOnce initial access is suspected, the hunt pivots to corroborate post-exploitation behavior across multiple surfaces. We monitor process activity for attempts to read the container environment block, specifically /proc/1/environ. In many containerized AI deployments, this is where provider API keys and database connection strings are stored for the application to function.\n\nSimultaneously, we analyze DNS activity for rare lookups to database hosts. If an AI gateway that usually communicates with a specific model endpoint suddenly starts resolving external or anomalous database patterns, it suggests potential data exfiltration or credential testing against production backends.\n\nThe hunt also looks for resource hijacking indicators. We monitor for the loading of the msr (Model-Specific Register) kernel module with allow_writes=1. This is a specific tuning step used by cryptominers like XMRig to optimize CPU performance for the RandomX algorithm—an activity that is highly atypical for standard AI application runtimes.\n\nFinally, we look for persistence via SSH. We check for modifications to authorized_keys files belonging to service accounts, which would allow an attacker to maintain access even if the initial gateway vulnerability is patched.\n\nThere are two primary blind spots to consider. First, without full HTTP body capture, we cannot distinguish between a legitimate connectivity test and a successful RCE injection; we only see the intent. Second, EDR visibility into the /proc filesystem across container namespaces can vary. If the agent only monitors host-level process launches, it may miss direct reads of the environment block.\n\nThis hunt is provided as a hunt.md playbook. It can be imported directly into Huntbase or any compatible runtime to automate the data collection and triage steps.

# AI Infrastructure Control Plane Compromise

This hunt targets the exploitation of AI orchestration layers including LiteLLM, RAGFlow, and Kestra. It identifies vulnerable AI infrastructure, tracks the transition from initial web-based exploitation of gateway endpoints to the harvesting of provider API keys from the container environment, and monitors for the exfiltration of backend database records. Finally, it corroborates these activities with the deployment of cryptominers that use specialized Model-Specific Register (MSR) tuning and unauthorized SSH key modifications.
