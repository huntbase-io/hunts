# Knight Office Token Theft and Rogue Device Persistence

### Why this hunt. Huntress recently analyzed the Knight Office phishing kit (https://www.huntress.com/blog/inside-knight-office-m365-aitm-attack), a toolset that bypasses MFA using the Microsoft device-code flow. Unlike standard Adversary-in-the-Middle (AiTM) kits that proxy traffic, Knight Office tricks users into authorizing a code. This grants the attacker a session token. The adversary then secures persistence by enrolling a rogue device into the victim's Entra ID tenant. This hunt targets that specific transition from token theft to persistence. ### The Hypothesis. An adversary steals Microsoft 365 session tokens via a device-code phishing flow and secures persistence by enrolling an unauthorized rogue device into the Entra ID tenant. ### How the Hunt Flows. The first phase scopes the environment for signs of kit interaction using the hb_http_activity surface. The query identifies any internal host or identity visiting the Microsoft device login endpoint or known kit management infrastructure. This step filters the noise, focusing the investigation on users who potentially engaged with the phishing prompt. By looking for the devicelogin path specifically, the hunt narrows the leads to the exact authentication flow the kit exploits. The second phase runs two investigations in parallel. One query stacks User-Agents seen in traffic to authentication endpoints like login.microsoft.com. Automated tools used by the kit, such as the python-requests library, often appear as rare outliers compared to standard browser strings in a corporate environment. The hunt looks for User-Agents that appear on three or fewer hosts to find these automated signatures. Simultaneously, the hunt checks the hb_devices surface for newly enrolled devices where the provider is azure_ad. A rogue host registration provides the attacker a foothold that survives password resets and MFA changes because the device itself is trusted. The final phase uses an agent to correlate these leads. It settles a verdict by matching users who visited the kit infrastructure with those who have a corresponding rare User-Agent and a newly registered cloud device. This correlation separates successful compromises from harmless visits to the login page. If the agent confirms both the kit interaction and the rogue device enrollment, we proceed to remediation. ### What it Cannot See. The hunt faces two primary blind spots. First, endpoint-based HTTP telemetry only captures the victim's initial interaction. The subsequent token replay and API activity from the attacker’s own infrastructure remain invisible to these sensors. Capturing that behavior requires native Entra ID sign-in logs which record all global auth attempts and User-Agents. Second, cloud inventory sync delays can create a temporary gap between the moment an attacker registers a device and when it appears in the hb_devices surface. A successful enrollment might not show up for several minutes or hours depending on the inventory collector's cycle. ### Running the Hunt. This hunt is an open-source playbook in the hunt.md format. You can import it into Huntbase or any runtime that supports the hunt.md standard. It provides a structured path from network leads to cloud identity verification, allowing practitioners to verify the integrity of their Entra ID tenant against this specific AiTM kit. The playbook includes specific steps for session revocation and manual verification of Windows Hello persistence to ensure no backdoors remain.
