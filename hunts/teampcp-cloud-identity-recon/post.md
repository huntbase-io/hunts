# Hunting TeamPCP Post-Compromise Cloud Identity Reconnaissance

Recent research by the Wiz team in their article, Tracking TeamPCP: post-compromise attacks seen in the wild (https://www.wiz.io/blog/tracking-teampcp-investigating-post-compromise-attacks-seen-in-the-wild), details a campaign targeting supply-chain tools to harvest cloud secrets. The threat actor, TeamPCP, targets software like Trivy, KICS, and LiteLLM to exfiltrate credentials, followed by rapid environment mapping. This hunt design focuses on the reconnaissance phase, specifically where stolen secrets are validated and used to discover cloud resources.\n\nThe hypothesis is that adversaries are using these stolen credentials via automated tools like TruffleHog, often originating from a specific set of VPN and VPS exit nodes, to perform broad cloud service discovery. This transition from theft to mapping is a critical window for intervention.\n\nThe hunt flow begins with scoping in the hb_software_inventory surface. We identify hosts running the specific scanners and libraries that TeamPCP is known to target, such as Trivy and LiteLLM. This narrows the investigation to identities most likely to have had their secrets harvested from CI/CD pipelines or local developer environments.\n\nNext, we pivot to network telemetry. We look for offensive User-Agents within hb_http_activity, specifically searching for substrings associated with TruffleHog or Kali-based Boto3 configurations. This helps identify the moment an adversary validates that a stolen key is still active and can be used for further discovery.\n\nIn parallel, we corroborate this with authentication and management plane data. We search hb_auth_signin for successful sign-ins to cloud providers or GitHub originating from known TeamPCP IP addresses. Simultaneously, we use the aws_iam_access_advisor surface to find IAM principals that have suddenly accessed an unusually high number of distinct services in a short window. This bursty behavior is a hallmark of automated environment mapping and stands out against regular automation patterns.\n\nThere are specific blind spots to consider. Standard cloud provider logs often omit the full User-Agent string, meaning you may need proxy or WAF telemetry to see the TruffleHog signatures. Additionally, while Access Advisor shows that a service was accessed, it does not always provide the resource-level granularity needed to confirm exactly which secrets or files were touched without full resource-level CloudTrail data. Furthermore, administrative actions like GitHub workflow log deletion remain invisible without specific enterprise audit logs.\n\nThis is an open hunt.md playbook. You can run it by importing it into Huntbase or any other hunt.md-aware runtime. It is designed as a hunt rather than a detection because individual actions like a single GetCallerIdentity or DescribeInstances call are frequently benign; it is the contextual combination of source infrastructure, tool signatures, and service enumeration bursts that provides the necessary confidence for credential revocation.
