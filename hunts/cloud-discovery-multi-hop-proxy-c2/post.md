# Hunting for Multi-hop Proxies and Cloud Resource Discovery

### Background
Cloud assets are frequently repurposed by adversaries as operational relay boxes (ORBs). These instances provide a trusted IP reputation for masking command-and-control (C2) traffic or scanning other environments. Recent research from Elastic Security Labs, [Inside Elastic InfoSec's agentic SOC: When to inline your agent's skills for a 5&times; cost reduction](https://www.elastic.co/security-labs/blog/agentic-soc-token-budget-architecture), highlights how automated analysis can handle the high volume of signals generated by complex cloud environments. This hunt applies that logic to the detection of proxy behavior and cloud-plane discovery.

### The Hypothesis
We hypothesize that an adversary is using compromised EC2 instances to perform resource discovery while simultaneously masking their outbound traffic through multi-hop proxies and long-lived tunnels. This behavior leaves a specific footprint: sustained outbound network flows on non-standard ports and rare DNS queries for onion or hidden services.

### How the Hunt Flows

The hunt begins by scoping the environment to active AWS cloud instances. We establish a baseline of running devices to ensure we are only analyzing the infrastructure relevant to cloud-plane attacks. This step focuses the subsequent queries on high-value ingress and egress points.

Next, the hunt moves into a parallel analysis phase. We look for behavioral network signals, specifically targeting high-volume outbound connections on common proxy ports like 9001, 9050, or 1080. Simultaneously, we stack-count DNS resolutions for rare C2 domains and hidden services (like .onion addresses) that appear on a very small number of hosts across the estate.

Finally, we correlate these network signals with cloud authentication events. By pivoting on the IP addresses identified in the network phase, we look for AWS sign-in attempts from those same IPs. This join allows us to see if a suspected proxy node is also being used to authenticate against the cloud control plane for discovery purposes.

### Blind Spots
While this hunt is effective at identifying the 'where' and 'when' of a proxy, it has two primary limitations. First, it relies on authentication sign-in logs rather than full CloudTrail data events. This means we can see the login, but not the specific resources (like S3 buckets or IAM policies) being enumerated. Second, without TLS inspection, we cannot see the payload of the encrypted tunnels; we are relying entirely on volume, port, and duration as behavioral indicators.

### How to Run This Hunt
This hunt is provided as a `hunt.md` playbook. It can be imported directly into Huntbase or any runtime compatible with the `hunt.md` specification. It is designed to be run periodically to catch infrastructure that has been slowly repurposed for malicious use over time.
