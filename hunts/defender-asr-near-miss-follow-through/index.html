ASR Near-Misses: Blocked Attempts and the Route Around Them

High severity TLP:CLEAR Part 4 of 5 Research by Protokol-7 Published 19 Nov 2026

Hypothesis

An intruder triggered a Defender attack surface reduction rule, such as LSASS credential theft, an Office child process or PsExec/WMI process creation, and then reached the same objective by a route the rule does not cover; or the rule was only auditing and the action went ahead.

Brief

Why This Hunt Matters

Attack surface reduction rules stop specific attack steps. Examples include reading LSASS memory, Office starting child processes, PsExec or WMI creating processes, and scripts launching downloaded executables. Every block is a record of an attempt, and in audit mode every event is a record of an attempt that went ahead. In most organisations without Defender for Endpoint nobody reads these records: they stay in the local Defender event log, which is rarely forwarded.

Defender also stores them in its encrypted database, mpenginedb.db, in a table called ProcessBlockHistory. That table keeps about 90 days, much longer than the roughly two weeks the rest of the database holds. The open-source osquery-defender-extension, built on Protokol-7's research, exposes the table with each rule's name attached. That puts three months of attack attempts, across the whole fleet, one query away.

How the Hunt Flows

The first query reads the ASR history on every Windows host and groups it by rule, triggering process, target and mode. Stacked across the fleet, the line-of-business application that trips the Office rule on 400 hosts stands apart from the binary in a user's temp folder that tried to read LSASS on one. An agent separates near-misses from noise. It records each near-miss's time, the objective the blocked action served, and whether the rule was in audit mode. It also suggests confirmed noise for the asr_noise_processes parameter, which keeps those processes out of later runs.

A blocked attacker usually tries another way, so four queries look for that route on the near-miss hosts:

  • Credential theft without touching LSASS directly: comsvcs MiniDump, procdump, reg save of the SAM, SECURITY and SYSTEM hives, and NTDS or shadow-copy access.
  • Indirect launch: a script host or LOLBin started through WMI, COM, MMC or the task scheduler instead of from Word.
  • New services: services running cmd /c, PowerShell or a binary from a user-writable folder, the alternative to PsExec.
  • New scheduled tasks: tasks that run script hosts or user-space binaries.

A second agent puts each host's rows in time order from the ASR event and decides whether the attacker got through. Hosts where they did go to an approval-gated isolation. Where the target was credentials, the action also treats every account that logged on to the host as exposed. Anything unclear goes to an analyst.

What the Hunt Cannot See

The follow-through steps depend on process creation with command lines, plus service and task creation events. Without them the hunt finds the near-miss but cannot say what happened next, and it routes to a person. Rules that are off record nothing. Events older than about 90 days, and events on rebuilt hosts, are gone. Persistence moved into a WMI event subscription is not covered by any source the hunt reads. The action and taint_reason codes are undocumented.

Steps

  1. Query, triage

    ASR blocks and audits per host

    Read every attack surface reduction event the engine kept: rule, the process that triggered it, its target, and whether the rule was in block or audit mode. In block mode the event is an attempt that was stopped; in audit mode it is an attempt that went ahead. Without Defender for Endpoint these events stay on the host.

    sql, reads defender_mpengine_process_block_history
    SELECT (SELECT hostname FROM system_info) AS device_hostname, asr_rule_name, rule_id, process_path, target_path, is_audit, COUNT(*) AS events, MIN(time) AS first_event, MAX(time) AS last_event, MAX(process_integrity) AS process_integrity, MAX(process_taint_reason) AS taint_reason, MAX(action) AS actionFROM defender_mpengine_process_block_historyWHERE time >= (CAST(strftime('%s', 'now') AS INTEGER) - {{asr_lookback_days}} * 86400)  AND NOT (instr(',' || LOWER('{{asr_noise_processes}}') || ',', ',' || LOWER(process_path) || ',') > 0)GROUP BY asr_rule_name, rule_id, process_path, target_path, is_audit

    What a hit looks like. A line-of-business app tripping the same rule on hundreds of hosts is noise to tune. Blind spots

  • Needs the defender_mpengine osquery extension loaded by osqueryd (running as SYSTEM) on every Windows host, with Microsoft Defender Antivirus as the active engine and defender_mpengine_status.error empty. Those hosts return no rows, which looks the same as a clean host. An attacker who has removed or stopped Defender also leaves an empty or stale database. It would answer: Did Defender record anything on hosts where the extension is missing, cannot decrypt the database, or Defender is passive behind another antivirus? Remediation: Deploy the extension through extensions.load on all Windows hosts and alert on defender_mpengine_status rows with a non-empty error.
  • Needs process creation with parent and command line (Sysmon 1 or 4688 with command line), service creation (7045) and task creation (4698) events in hb_ surfaces for the window. Without them the hunt finds the near-miss but cannot say whether the attacker got through, and the decision routes to an analyst. It would answer: What did the attacker do after the ASR event?
  • Needs ASR rules configured in block or audit mode. A rule that is off records nothing in ProcessBlockHistory. It would answer: What would a rule that is not configured have recorded?
  • Needs ProcessBlockHistory younger than about 90 days and a host not rebuilt. Older events and those on rebuilt hosts are gone. It would answer: Did anything trigger ASR before the history starts?
  • Needs WMI event subscription telemetry (Sysmon 19-21). No hb_ surface in this hunt sees WMI subscriptions. It would answer: Did persistence move to a WMI subscription after the rule fired?

# ASR Near-Misses: Blocked Attempts and the Route Around Them

An ASR block is a record of an attack attempt that was stopped, and an ASR audit event is a record of one that was not. Most organisations without Defender for Endpoint never see either: the events stay in the local Defender event log, which is rarely forwarded. Defender also keeps them in mpenginedb.db, in ProcessBlockHistory, for about 90 days.

This hunt reads that history on every Windows host through the defender_mpengine osquery extension, stacks each rule and process pair across the fleet so that line-of-business noise drops out, and lets an agent pick the near-misses and the objective each one served.

An attacker who is blocked usually tries another way. For each near-miss host the hunt looks for that route: credential theft without touching LSASS directly, a script host started through WMI or COM instead of from Word, a service or a scheduled task instead of PsExec. It then decides whether the attacker got through.

## credential-theft-alternatives
<!-- Credential theft by other means -->
If the LSASS rule stopped a dump, look for the other ways to the same credentials: comsvcs MiniDump, procdump, renamed dumpers, saving the SAM, SECURITY and SYSTEM hives, NTDS copies and shadow copies.

```sqlite target=endpoint role=triage params=(lookback_days=lookback_days, scope_hosts=scope_hosts)
~~~yaml

  kept going for credentials.

- integrity_level
```
