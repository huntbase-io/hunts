Brief

Identity-as-a-service for microservices often relies on the infrastructure providing verifiable proof of a process's identity. In Kubernetes, SPIFFE/SPIRE is a common choice, where a node-local agent issues identities (SVIDs) based on selectors like Pod names or UIDs. However, as detailed by Unit 42 in their article "The Machine With Many Faces," these selectors are not immutable secrets; they are often observable in the Linux /proc filesystem by any process with sufficient privileges. Our new hunt focuses on the post-exploitation phase where an attacker, having already gained root on a Kubernetes node, attempts to harvest identities to move laterally or access sensitive secrets. The hypothesis is that the attacker must first discover the correct workload metadata by interrogating /proc/cgroups or /proc/mountinfo before they can successfully spoof an identity to the SPIRE agent socket.\n\nHow the hunt flows:\n\nThe first phase is scoping. We identify nodes within the environment that are actually running SPIRE agents or relevant container runtimes like the kubelet and containerd. This limits the data volume and focuses the analysis on the infrastructure where this specific attack surface exists.\n\nThe second phase monitors for discovery and interrogation. We look for non-standard processes—those not belonging to the kubelet, containerd, or the spire-agent itself—that are reading the cgroup or mount metadata for other processes. Ad-hoc use of shell utilities or unknown binaries reading these paths is a strong indicator of an attacker trying to map out the available identities on the host.\n\nThe third phase involves pivoting to identify the actual harvesting attempt. We look for rare processes across the fleet that contain keywords related to SVID fetching or cgroup manipulation. This is then corroborated with file activity telemetry showing these same processes interacting with the SPIRE agent's Unix domain socket. By combining the "how" (discovery) with the "what" (socket interaction), we can isolate unauthorized identity requests.\n\nThis hunt has specific blind spots. If an attacker uses a custom binary that performs direct syscalls to read /proc without spawning child processes or using standard shell commands, it may bypass command-line monitoring. Additionally, if the endpoint telemetry does not capture Unix domain socket access specifically, we are forced to rely on process behavioral indicators alone.\n\nWe have published this as a hunt.md playbook. Because legitimate sidecars and service meshes frequently perform similar actions, this activity is best approached as a hunt rather than a static detection rule. The use of fleet-wide prevalence allows us to distinguish between standard deployment patterns and isolated, malicious harvesting attempts. The playbook can be imported into Huntbase or any hunt.md-aware runtime. \n\nUnit 42 — The Machine With Many Faces: Post-Exploitation Identity Misuse in SPIFFE/SPIRE

    What a hit looks like. A list of hostnames belonging to Kubernetes nodes and SPIRE agent hosts. Silence here suggests SPIRE is not deployed using standard package names.

  2. Detect suspicious /proc interrogation

    Query · detection candidate

    Identify non-standard processes reading cgroup or mount metadata, which are the selectors used for SPIRE workload attestation.

    reads hb_process_activitysql
    SELECT device_hostname, process_cmd_line, process_path, user_name, time FROM hb_process_activity WHERE ('{{scope_hosts}}' = '' OR instr(',' || '{{scope_hosts}}' || ',', ',' || device_hostname || ',') > 0) AND (LOWER(process_cmd_line) LIKE '%/proc/%/cgroup%' OR LOWER(process_cmd_line) LIKE '%/proc/%/mountinfo%') AND NOT (LOWER(process_path) LIKE '%/kube%' OR LOWER(process_path) LIKE '%/spire-agent%' OR LOWER(process_path) LIKE '%/containerd%' OR LOWER(process_path) LIKE '%/containerd-shim%') AND time >= datetime('now', '-{{lookback_days}} days')

    What a hit looks like. Ad-hoc interrogation of /proc by shell utilities or unknown binaries. This is a high-confidence signal for manual discovery of workload metadata.

  3. Identify rare processes and SPIRE indicators

    Query · baseline

    Find rare processes whose command lines contain spoofing keywords like 'Spooffe' or SVID fetching operations.

    reads hb_process_activitysql
    SELECT process_name, process_cmd_line, COUNT(DISTINCT device_hostname) AS hosts, MIN(time) AS first_seen FROM hb_process_activity WHERE ('{{scope_hosts}}' = '' OR instr(',' || '{{scope_hosts}}' || ',', ',' || device_hostname || ',') > 0) AND (LOWER(process_cmd_line) LIKE '%spooffe%' OR LOWER(process_cmd_line) LIKE '%fetchx509svid%' OR LOWER(process_cmd_line) LIKE '%fetchjwtsvid%' OR LOWER(process_cmd_line) LIKE '%kubepods.slice%') AND time >= datetime('now', '-{{lookback_days}} days') GROUP BY process_name, process_cmd_line HAVING hosts <= 3 ORDER BY hosts ASC

    What a hit looks like. Processes or scripts referencing SVID fetching that are not fleet-wide sidecars.

  4. File activity on SPIRE agent sockets

    Query · enrichment

    Confirm which processes are directly opening the SPIRE socket to request identities.

    What a hit looks like. A list of processes that touched the SPIRE socket. Combined with the prevalence query, this isolates unknown actors from legitimate sidecars.

# SPIFFE/SPIRE Identity Spoofing and Harvesting

This hunt identifies post-exploitation activity where an attacker attempts to impersonate Kubernetes workloads by spoofing Linux control group (cgroup) information used during SPIRE workload attestation. By identifying ad-hoc interrogation of /proc/cgroups and /proc/mountinfo and correlating this with rare processes accessing the SPIRE agent's Unix domain socket, the hunt detects attempts to harvest short-lived X.509 and JWT identities (SVIDs).

```sqlite target=endpoint role=baseline params=(scope_hosts=scope_hosts, lookback_days=lookback_days)
~~~yaml
```
