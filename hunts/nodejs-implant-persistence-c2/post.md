# Hunting Node.js Implant Persistence and C2 in IT Impersonation Campaigns

### Why Now\n\nMicrosoft recently detailed a campaign titled [Impersonating IT support: how threat actors turn a remote session into enterprise-wide access](https://www.microsoft.com/en-us/security/blog/2026/09/02/impersonating-it-support-threat-actors-turn-remote-session-into-enterprise-wide-access/) involving social engineering and the deployment of Node.js-based implants. Once an attacker gains a foothold via a remote session, they establish persistence to ensure long-term access, often using lures that mimic legitimate software updates.\n\n### The Hypothesis\n\nWe hypothesize that an adversary has established persistence for a Node.js-based implant by placing it in user-writable paths (specifically AppData\\Local). They maintain this persistence using update-themed Run keys or Startup shortcuts and maintain command-and-control (C2) communication via randomized HTTPS long-polling. This behavior is distinct from standard enterprise software, which typically installs to privileged directories.\n\n### How the Hunt Flows\n\nThe hunt begins with scoping. We first examine the software inventory to identify hosts where Node.js is officially installed. This creates a baseline for sanctioned development activity. In many corporate environments, the presence of Node.js execution on a non-developer workstation—especially a 'portable' version not found in the inventory—is a significant red flag.\n\nNext, we pivot to registry and file activity to find the persistence mechanism. We look specifically for Run and RunOnce keys that point to any binary or script located in the `AppData\\Local` directory. While the source article highlights the 'EdgeUpdate' keyword, this behavioral approach ensures we capture the activity even if the threat actor changes the name of the persistence key or the binary.\n\nWe then run a parallel investigation into network and HTTP telemetry. We look for rare network connections originating from processes running out of those same user-writable paths. By stack-counting these connections across the estate, we can identify external destinations that are unique to a small number of hosts. This is then correlated with high-frequency HTTP requests to identify the repetitive long-polling pattern typical of the implant's C2 mechanism.\n\nFinally, an agent triages these combined signals. It weighs the presence of registry persistence, the location of the binary, and the rarity of the network traffic to provide a verdict. This multi-surface correlation is what distinguishes this hunt from a simple detection rule.\n\n### Blind Spots\n\nThis hunt has two primary blind spots. First, without full TLS inspection or host-based HTTP visibility, we cannot see the specific JavaScript tasks (such as screen captures or discovery commands) sent from the C2 to the implant. Second, if the enterprise software inventory does not track 'portable' binaries, our initial scoping step may not effectively distinguish between sanctioned and unsanctioned Node.js installations, making us more dependent on behavioral logs.\n\n### How to Run it\n\nThis hunt is provided as an open `hunt.md` playbook. It can be imported directly into Huntbase or any hunt.md-aware runtime. Because it relies on behavioral patterns rather than just static hashes or IPs, it is best run as a proactive check across the entire estate to confirm the absence of these persistent interactive channels.
