BiTB Phishing to Rogue RMM Persistence

An adversary has used browser-in-the-browser phishing to deceive a user into installing a rogue ScreenConnect instance, which established service-based persistence and executed evasion tools to hide its activity.

Brief

Why this hunt matters

Recently, Huntress published a report titled Phishing Attacks Serve Browser-in-the-Browser Pages, Rogue RMM Persistence (https://www.huntress.com/blog/phishing-bitb-rmm-attacks). The article describes a multi-stage chain where an adversary uses deceptive browser overlays to install rogue ScreenConnect instances. This hunt identifies the transition from initial phishing access to long-term persistence. Because browser-in-the-browser techniques bypass traditional visual training, security practitioners must focus on the behavioral artifacts of the payload delivery and the RMM services that follow.

Scoping the Environment

The hunt starts by identifying every host running ScreenConnect software using the software inventory surface. This scoping phase establishes a list of systems where remote management tools are present. While many organizations use these tools for legitimate administration, identifying every instance is the first step in finding unauthorized versions that deviate from the corporate standard.

Access and Delivery

After scoping, the hunt searches for early-stage access signals. It queries DNS logs for resolutions to known phishing and relay domains. At the same time, the hunt monitors process activity for the use of curl to fetch MSI or EXE files. This specific combination of a browser process initiating a domain lookup followed by a command-line fetch of an installer represents the typical delivery flow. It captures the moment the adversary pulls the second-stage RMM payload onto the system.

Persistent RMM Services

Once the installer executes, it establishes a persistent service. The hunt uses process stacking to identify rare ScreenConnect process names across the fleet. Legitimate tools typically appear on many hosts with consistent naming conventions. Attacker-controlled instances often use unique identifiers or rare version strings. These stand out when the analyst baselines the process names against the rest of the environment. Finding a ScreenConnect process that only exists on one or two hosts suggests an unauthorized installation.

Defense Evasion

To maintain access without alerting the user, the adversary executes tools that suppress interactive indicators. The hunt looks for the execution of binaries like HideCursor.exe and HideUL.exe. It also monitors for any process activity within the ScreenConnect temporary directories, such as Documents\ScreenConnect\Temp. Attackers use these folders to stage scripts and evasion tools that hide the remote session from the logged-in user. This phase helps confirm that the RMM tool is being used for malicious purposes rather than legitimate support.

Synthesis and Triage

An automated agent or a manual analyst triages the findings by correlating the delivery and persistence signals. A host that resolved a phishing domain, executed a curl fetch, and now runs a rare ScreenConnect service is a target for isolation. The hunt weighs the early access signals against the persistence evidence to provide a final verdict for each endpoint. This phased approach ensures that the analyst focuses on the most likely intrusions first.

Blind Spots

This hunt relies on telemetry that may be limited by environmental configurations. It cannot see the actual browser rendering of a BiTB overlay. If the network does not use a TLS-decrypting proxy, the DNS logs only show the top-level domain resolution. The specific phishing content remains invisible. Additionally, if the endpoint agent truncates long command lines, the hunt might miss the malicious URL or file extension in the curl payload retrieval.

Blind spots

  • Needs Complete process command-line logging. If the command line is truncated, the malicious domain and file extension might not be visible, causing the fetch query to miss the activity. It would answer whether the curl command line included the malicious URL. Remediation: Increase the command-line capture limit on the endpoint agent.

It would answer whether the BiTB HTML template was served to the browser. Remediation: Enable TLS inspection on the forward proxy for unauthenticated traffic to scan for BiTB HTML patterns.

# BiTB Phishing to Rogue RMM Persistence

This hunt follows the full lifecycle of a Browser-in-the-Browser (BiTB) attack. It begins by identifying users interacting with phishing infrastructure and subsequent payload retrieval via curl. The second phase pivots to detect the aftermath: rare or unauthorized ScreenConnect service processes and the execution of activity-hiding tools like HideCursor.exe. By weighing the early-stage access signals against the persistence evidence, the hunt distinguishes between authorized RMM software and attacker-controlled footholds.
