After Defender Remediates: What Changed and Where Else It Is

Medium severity TLP:CLEAR Part 5 of 5 Research by Protokol-7 Published 19 Nov 2026

Hypothesis

Malware that Microsoft Defender remediated on one host also reached other hosts where Defender did not detect it or where the attacker deleted it first, and its persistence and file hashes are recoverable from Defender's remediation and hash caches.

Brief

Why This Hunt Matters

When Defender reports a threat as remediated, the ticket usually closes. But malware rarely lands on one machine only. On other hosts a slightly different variant, an exclusion, or the attacker's own clean-up may have kept it from being detected. The remediated host is the best lead available, and it is rarely used.

Defender's encrypted database, mpenginedb.db, holds what is needed to follow that lead. Protokol-7 showed that its hash cache keeps SHA-256, SHA-1 and MD5 values with MFT references for files real-time protection scanned, and that these entries outlive the files. That makes the cache useful when an attacker has deleted their tools. The database also holds the engine's threat records, plus two remediation caches: the registry values and the system files Defender changed during remediation, with the values before and after. The value before is what the malware wrote. The open-source osquery-defender-extension exposes all of these as osquery tables.

How the Hunt Flows

The hunt starts from Defender's remediations in the window, taken from forwarded detections. On those hosts, three queries read what the malware changed. The first reads the engine's threat records and the executables it saw dropped and run. The second reads the registry values remediation put back, with the malicious data. The third reads the system files remediation replaced, with infected and clean hashes. An agent turns these into a list of hashes and registry value names. It also flags any host where a restored value carries the malicious data again, which means remediation did not hold.

The analyst pastes those values in, and four queries sweep the whole estate:

  • Defender's hash cache on every host, which finds hosts that held the file even after it was deleted.
  • Process telemetry, for hosts where the file ran.
  • Registry telemetry, for the same persistence values.
  • A count of rare autostart values across the fleet, which catches persistence that was renamed.

A second agent sorts each host into present, past or none. Hosts where the malware is still present go to an approval-gated action that isolates and rescans them. Hosts found only in the hash cache go to an analyst to trace through the MFT and USN journal.

What the Hunt Cannot See

The two remediation caches were empty on every host the extension has been tested on. Their columns follow the live schema, but no real row has been decoded yet, so those steps are best effort. The hash cache stores a volume serial and MFT entry, not a path. It covers only files real-time protection scanned, and only for about two weeks. Without Defender detections in the SIEM, the scoping step is empty, and the threat-record step should run across the estate instead.

Steps

  1. Query, scoping

    Defender remediations in the window

    Start from what Defender cleaned: its detections in the window, with the threat, the file and the outcome. These hosts are the starting point.

    sql, reads hb_detection_finding
    SELECT device_hostname, time, malware_name, finding_title, file_path, process_path, disposition, finding_status, user_nameFROM hb_detection_findingWHERE time >= datetime('now', '-{{lookback_days}} days')  AND (LOWER(COALESCE(metadata_product, '')) LIKE '%defender%' OR LOWER(COALESCE(provider, '')) LIKE '%defender%')

    What a hit looks like. Detections with a remediated or quarantined disposition. Paste their hosts into scope_hosts. Empty when Defender detections are not forwarded; run the next step across the estate instead.

  2. Query, enrichment

    Threats and dropped executables on the host

    Read the engine's own threat records and the executables it saw dropped and run, which name the process images involved even when the detection did not.

    sql, reads defender_mpengine_rolling_queues
    SELECT (SELECT hostname FROM system_info) AS device_hostname, queue_type, entry_key, pid, process_start, CASE WHEN json_valid(entry_value) THEN json_extract(entry_value, '$.Process_Img') END AS image, insert_timeFROM defender_mpengine_rolling_queuesWHERE queue_type IN ('recent_threats', 'dropped_executable')  AND insert_time >= (CAST(strftime('%s', 'now') AS INTEGER) - {{lookback_days}} * 86400)  AND ('{{scope_hosts}}' = '' OR instr(',' || '{{scope_hosts}}' || ',', ',' || (SELECT hostname FROM system_info) || ',') > 0)

    What a hit looks like. Behavior:Win32/... names with the image they were raised against, and dropped paths. Images other than the detected file are part of the chain.

  3. Query, enrichment

    Registry values Defender put back

    Read the registry values remediation changed, before and after. The value before is what the malware wrote: its persistence or configuration.

    sql, reads defender_mpengine_system_registry_cache
    SELECT (SELECT hostname FROM system_info) AS device_hostname, instance_time, reg_path, reg_operation, old_type_name, old_data, old_data_hex, new_type_name, new_dataFROM defender_mpengine_system_registry_cacheWHERE instance_time >= (CAST(strftime('%s', 'now') AS INTEGER) - {{lookback_days}} * 86400)  AND ('{{scope_hosts}}' = '' OR instr(',' || '{{scope_hosts}}' || ',', ',' || (SELECT hostname FROM system_info) || ',') > 0)

    What a hit looks like. Run keys, services, Winlogon or policy values with the malicious data in old_data. reg_operation is an undocumented code.

  4. Query, enrichment

    System files Defender restored

    Read the system files remediation replaced, with the infected and clean hashes.

    sql, reads defender_mpengine_system_file_cache
    SELECT (SELECT hostname FROM system_info) AS device_hostname, instance_time, system_file_path, infected_file_sha, clean_file_shaFROM defender_mpengine_system_file_cacheWHERE instance_time >= (CAST(strftime('%s', 'now') AS INTEGER) - {{lookback_days}} * 86400)  AND ('{{scope_hosts}}' = '' OR instr(',' || '{{scope_hosts}}' || ',', ',' || (SELECT hostname FROM system_info) || ',') > 0)

    What a hit looks like. A patched or replaced Windows binary, with the infected hash to search for elsewhere.

  5. Agent triage

    Extract the artefacts to sweep for

    Turn the remediated hosts' records into values to search the fleet for.

  6. Query, triage

    Defender's hash cache across the fleet

    Search every host's real-time protection hash cache for the artefact hashes. The cache keeps hashes of files Defender scanned even after the file is deleted, so it finds hosts where the attacker cleaned up.

    sql, reads defender_mpengine_file_hashes
    SELECT (SELECT hostname FROM system_info) AS device_hostname, sha256, sha1, md5, volume_serial, mft_entry, mft_sequence, usn, instance_timeFROM defender_mpengine_file_hashesWHERE instr(',' || LOWER('{{artefact_hashes}}') || ',', ',' || LOWER(sha256) || ',') > 0  OR instr(',' || LOWER('{{artefact_hashes}}') || ',', ',' || LOWER(sha1) || ',') > 0  OR instr(',' || LOWER('{{artefact_hashes}}') || ',', ',' || LOWER(md5) || ',') > 0

    What a hit looks like. Hosts other than the remediated ones that held an artefact. mft_entry and volume_serial locate the file in the MFT; there is no path.

  7. Query, triage

    Artefact hashes executing across the fleet

    Find hosts where an artefact ran, from process telemetry.

    sql, reads hb_process_activity
    SELECT device_hostname, time, user_name, parent_process_name, process_name, process_cmd_line, process_hash_sha256FROM hb_process_activityWHERE time >= datetime('now', '-{{lookback_days}} days')  AND instr(',' || LOWER('{{artefact_hashes}}') || ',', ',' || LOWER(process_hash_sha256) || ',') > 0

    What a hit looks like. Execution on a host Defender did not remediate.

  8. Query, triage

    The malware's registry values across the fleet

    Find hosts where the same persistence value names were written.

    sql, reads hb_registry_activity
    SELECT device_hostname, time, reg_key_path, reg_value_name, reg_value_data, process_name, actor_user_nameFROM hb_registry_activityWHERE time >= datetime('now', '-{{lookback_days}} days')  AND instr(',' || LOWER('{{persistence_value_names}}') || ',', ',' || LOWER(reg_value_name) || ',') > 0

    What a hit looks like. The same value names on other hosts. Silence means only that these names were not reused; see rare-autostart-values.

  9. Query, baseline

    Rare autostart values

    Stack every autostart value written in the window by name and data across the fleet, so renamed persistence from the same family still stands out.

    sql, reads hb_registry_activity
    SELECT LOWER(reg_value_name) AS value_name, reg_value_data, COUNT(DISTINCT device_hostname) AS hosts, GROUP_CONCAT(DISTINCT device_hostname) AS host_list, MIN(time) AS first_seenFROM hb_registry_activityWHERE time >= datetime('now', '-{{lookback_days}} days')  AND (LOWER(reg_key_path) LIKE '%\currentversion\run%' OR LOWER(reg_key_path) LIKE '%\winlogon%' OR LOWER(reg_key_path) LIKE '%\image file execution options\%' OR (LOWER(reg_key_path) LIKE '%\system\currentcontrolset\services\%' AND LOWER(reg_value_name) IN ('imagepath', 'servicedll')))GROUP BY LOWER(reg_value_name), reg_value_dataHAVING COUNT(DISTINCT device_hostname) < 3

    What a hit looks like. Values whose data has the same shape as the restored ones (same folder, same launcher, random-looking names) on other hosts.

    Spread verdict

    Decide where else the malware is or was.

  11. Decision

    Route on verdict

    Act on hosts where the malware is still present.

  12. Response action

    Isolate and rescan

    Stop the spread and clean the hosts Defender missed.

  13. Analyst task

    Analyst review

    Confirm and find the entry point.

  14. Analyst task

    Close out

    Record results.

Blind spots

  • Needs the defender_mpengine osquery extension loaded by osqueryd (running as SYSTEM) on every Windows host, with Microsoft Defender Antivirus as the active engine and defender_mpengine_status.error empty. Those hosts return no rows, which looks the same as a clean host. An attacker who has removed or stopped Defender also leaves an empty or stale database. It would answer: Did Defender record anything on hosts where the extension is missing, cannot decrypt the database, or Defender is passive behind another antivirus? Remediation: Deploy the extension through extensions.load on all Windows hosts and alert on defender_mpengine_status rows with a non-empty error.
  • Needs SystemRegistryCache and SystemFileCache rows from real remediations, and a decoder checked against them. These tables were empty on every host the extension was tested on; their columns follow the live schema but no real row has been decoded yet, and reg_operation is undocumented. Treat the step as best effort. It would answer: What did the malware change that Defender put back?
  • Needs MFT or USN journal data to resolve volume serial and MFT entry to a path. The hash cache proves a host held the file, not where or when it went, and covers only files real-time protection scanned in about the last two weeks. It would answer: Where on disk was the file the hash cache remembers?
  • Needs Defender detections (events 1116/1117 or MDE alerts) in hb_detection_finding. Without forwarding the scoping step is empty; run threat-records-on-host across the estate instead. It would answer: Which hosts did Defender remediate?

# After Defender Remediates: What Changed and Where Else It Is

When Defender reports a threat as remediated, the usual response stops there. But the same file often arrived on other hosts, where a different variant, an exclusion or the attacker's own clean-up kept it from being detected. Defender's database, mpenginedb.db, holds what is needed to check: the registry values and system files remediation changed, with the malicious values and hashes, the engine's threat records, and a hash cache of files it scanned that keeps entries after the file is deleted.

This hunt starts from Defender's remediations, reads those records on the remediated hosts through the defender_mpengine osquery extension, and has an agent turn them into hashes and registry values. It then sweeps the fleet for them: the hash cache on every host, process telemetry, registry telemetry, and a count of rare autostart values for persistence that was renamed.

The outcome is a list of hosts where the malware is still present, hosts where it was and is gone, and remediated hosts where it came back.

<!-- Defender's hash cache across the fleet -->
Search every host's real-time protection hash cache for the artefact hashes. The cache keeps hashes of files Defender scanned even after the file is deleted, so it finds hosts where the attacker cleaned up.

```osquery target=hb-endpoint-control role=triage params=(artefact_hashes=artefact_hashes)
~~~yaml
expected: Hosts other than the remediated ones that held an artefact. mft_entry and
  volume_serial locate the file in the MFT; there is no path.
reads:
- instance_time
- volume_serial
- mft_entry
- mft_sequence
- usn
- md5
- sha1
- sha256
silence: not_evidence_of_absence
source: defender_mpengine_file_hashes
verified: dry-run
verified_at: '2026-11-19'
~~~
SELECT (SELECT hostname FROM system_info) AS device_hostname, sha256, sha1, md5, volume_serial, mft_entry, mft_sequence, usn, instance_time FROM defender_mpengine_file_hashes WHERE instr(',' || LOWER('{{artefact_hashes}}') || ',', ',' || LOWER(sha256) || ',') > 0 OR instr(',' || LOWER('{{artefact_hashes}}') || ',', ',' || LOWER(sha1) || ',') > 0 OR instr(',' || LOWER('{{artefact_hashes}}') || ',', ',' || LOWER(md5) || ',') > 0
```

## fleet-process-hash-sweep
<!-- Artefact hashes executing across the fleet -->
Find hosts where an artefact ran, from process telemetry.

```sqlite target=endpoint role=triage params=(lookback_days=lookback_days, artefact_hashes=artefact_hashes)
~~~yaml
expected: Execution on a host Defender did not remediate.
reads:
- time
- device_hostname
- process_name
- process_cmd_line
- process_hash_sha256
- parent_process_name
- user_name
silence: not_evidence_of_absence
source: hb_process_activity
verified: dry-run
verified_at: '2026-11-19'
~~~
SELECT device_hostname, time, user_name, parent_process_name, process_name, process_cmd_line, process_hash_sha256 FROM hb_process_activity WHERE time >= datetime('now', '-{{lookback_days}} days') AND instr(',' || LOWER('{{artefact_hashes}}') || ',', ',' || LOWER(process_hash_sha256) || ',') > 0
```

## fleet-persistence-sweep
<!-- The malware's registry values across the fleet -->
Find hosts where the same persistence value names were written.

```sqlite target=endpoint role=triage params=(lookback_days=lookback_days, persistence_value_names=persistence_value_names)
~~~yaml
expected: The same value names on other hosts. Silence means only that these names
  were not reused; see rare-autostart-values.
reads:
- time
- device_hostname
- actor_user_name
- reg_key_path
- reg_value_name
- reg_value_data
- process_name

```

## rare-autostart-values
<!-- Rare autostart values -->
Stack every autostart value written in the window by name and data across the fleet, so renamed persistence from the same family still stands out.

```sqlite target=endpoint role=baseline params=(lookback_days=lookback_days)
~~~yaml
baseline:
  compare: first_seen
  window: '{{lookback_days}}d'
expected: Values whose data has the same shape as the restored ones (same folder,
  same launcher, random-looking names) on other hosts.
prevalence:
  by: device_hostname
  key:
  - value_name
  - reg_value_data
  rare_below: 3
reads:
- time
- device_hostname
- reg_key_path
- reg_value_name
- reg_value_data
silence: not_evidence_of_absence
source: hb_registry_activity
verified: dry-run
verified_at: '2026-11-19'
~~~
SELECT LOWER(reg_value_name) AS value_name, reg_value_data, COUNT(DISTINCT device_hostname) AS hosts, GROUP_CONCAT(DISTINCT device_hostname) AS host_list, MIN(time) AS first_seen FROM hb_registry_activity WHERE time >= datetime('now', '-{{lookback_days}} days') AND (LOWER(reg_key_path) LIKE '%\currentversion\run%' OR LOWER(reg_key_path) LIKE '%\winlogon%' OR LOWER(reg_key_path) LIKE '%\image file execution options\%' OR (LOWER(reg_key_path) LIKE '%\system\currentcontrolset\services\%' AND LOWER(reg_value_name) IN ('imagepath', 'servicedll'))) GROUP BY LOWER(reg_value_name), reg_value_data HAVING COUNT(DISTINCT device_hostname) < 3
```

## analyst-review
<!-- Analyst review -->
```manual target=analyst

Decrypt the collected Scans folders with Protokol-7's mpenginedb_parser, which recovers rows Defender has since dropped. Find the earliest host and how the malware got there.
```
→ close-out
