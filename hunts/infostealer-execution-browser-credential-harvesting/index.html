Brief

Identifying the infostealer lifecycle

Recent research from Talos (https://blog.talosintelligence.com/the-story-behind-the-intelligence/) details the lifecycle of modern infostealer campaigns. These attacks often bypass traditional detections by using obfuscated scripts and rotating file hashes. We have published a new hunt.md playbook to help practitioners find this activity on their endpoints.

Hunt Flow

The hunt begins by scoping the environment for common browser installations like Chrome and Edge. This establishes a baseline of potential targets for the harvesting phase. The next phase queries process activity for specific hashes and filenames identified in the Talos report. This lead indicator phase acts as a gate for more resource-intensive behavioral analysis. The hunt only proceeds if it confirms the presence of these specific malware variants. If the hunt finds evidence of malicious execution, it fans out into behavioral queries. One branch looks for rare, non-browser processes reading files like "Login Data" or "Cookies" within user profiles. The query for file activity uses a prevalence filter to identify processes that access the browser store but do not have the high volume of a legitimate browser process. This identifies the "read-once" behavior typical of credential stealers. Another branch checks DNS activity for lookups to sandbox-associated domains like those ending in "sbx.tg". These domains often escape static blocklists because they are generated dynamically. A combined triage step then weighs the evidence from all surfaces. An analyst or automated agent reviews the results to reach a final verdict. If confirmed, the hunt initiates host isolation and password resets to prevent stolen cookie use.

Why this is a hunt

We categorize this as a hunt rather than a simple detection because of the noise inherent in browser profile access. Legitimate updates, profile migrations, and synchronization tools often touch these SQLite databases. The hunt provides the necessary context—connecting the initial execution lead to the rare file access—to allow an analyst to confirm the verdict without being overwhelmed by false positives from standard browser activity.

Blind Spots

This hunt relies on endpoint process and file visibility. It cannot see activity on unmanaged hosts or legacy systems without an agent. Additionally, while the hunt identifies the content.js script drop, it does not analyze the internal commands of obfuscated JavaScript in memory. Organizations should ensure script block logging is enabled to supplement this visibility.

Running the Hunt

This hunt is an open hunt.md playbook. You can import it into Huntbase or any compatible runtime. The flow includes parameters for lookback periods and specific indicator lists from the Talos research. Practitioners can adjust the prevalence thresholds in the file activity step to suit their environment's baseline.

    Query · scoping

    Identify hosts that serve as primary targets for infostealer harvesting by locating Chrome and Edge installations.

    What a hit looks like. A list of hosts with installed browsers. Silence means no browsers are inventoried, which is unlikely in an enterprise environment.

  2. Lead infostealer hash execution

    Query · triage

    Identify hosts where known malicious binaries from the Talos report have executed.

    What a hit looks like. Rows mapping known malicious hashes to execution on specific hosts. Silence means these specific variants did not run.

  3. Evaluate lead evidence

    Agent triage

    Determine if the findings in the lead query are sufficiently suspicious to warrant expensive behavioral analysis.

  4. Gate the behavioral investigation

    Decision

    Stop the hunt early if no malicious execution is found, or open behavioral queries if it is.

  5. Rare processes reading browser stores

    Query · detection candidate

    Identify processes other than the browser itself reading sensitive SQLite databases containing passwords and session cookies.

    reads hb_file_activitysql
    SELECT device_hostname, process_name, file_path, COUNT(*) AS access_count, MIN(time) AS first_seen FROM hb_file_activity WHERE (LOWER(file_path) LIKE '%\\user data\\default\\login data%' OR LOWER(file_path) LIKE '%\\user data\\default\\cookies%') AND activity_id = 2 AND ('{{scope_hosts}}' = '' OR instr(',' || '{{scope_hosts}}' || ',', ',' || device_hostname || ',') > 0) AND time >= datetime('now', '-{{lookback_days}} days') GROUP BY device_hostname, process_name, file_path HAVING access_count < 15

    What a hit looks like. A process (like a dropped executable or script) reading browser database files. Normal browser use generates high access counts; rare processes with low counts stand out.

  6. DNS activity to sandbox domains

    Query · enrichment

    Identify network communication with the sandbox-derived C2 domains named in the report.

    What a hit looks like. DNS queries for sandbox-generated domains (e.g., w32.c4dd...sbx.tg). Silence says nothing if indicators have rotated.

# Infostealer execution and browser credential harvesting

This hunt targets the endpoint-centric phase of infostealer campaigns, where initial malware execution leads to local credential theft. It uses a gated flow: first identifying systems with vulnerable browser targets, then looking for known malware execution. If confirmed, it expands to behavioral queries that identify rare processes accessing browser login data or communicating with sandbox-associated C2 infrastructure. This sequence identifies the activity before stolen session cookies are used to bypass MFA in subsequent SSO takeovers.
