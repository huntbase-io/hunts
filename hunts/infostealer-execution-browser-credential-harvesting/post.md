# Infostealer execution and browser credential harvesting

### Identifying the infostealer lifecycle Recent research from Talos (https://blog.talosintelligence.com/the-story-behind-the-intelligence/) details the lifecycle of modern infostealer campaigns. These attacks often bypass traditional detections by using obfuscated scripts and rotating file hashes. We have published a new hunt.md playbook to help practitioners find this activity on their endpoints. ### The Hypothesis An adversary phishes a user and executes an infostealer. The malware then harvests credentials and session cookies from local browser SQLite databases for exfiltration to a command-and-control server. ### Hunt Flow The hunt begins by scoping the environment for common browser installations like Chrome and Edge. This establishes a baseline of potential targets for the harvesting phase. The next phase queries process activity for specific hashes and filenames identified in the Talos report. This lead indicator phase acts as a gate for more resource-intensive behavioral analysis. The hunt only proceeds if it confirms the presence of these specific malware variants. If the hunt finds evidence of malicious execution, it fans out into behavioral queries. One branch looks for rare, non-browser processes reading files like "Login Data" or "Cookies" within user profiles. The query for file activity uses a prevalence filter to identify processes that access the browser store but do not have the high volume of a legitimate browser process. This identifies the "read-once" behavior typical of credential stealers. Another branch checks DNS activity for lookups to sandbox-associated domains like those ending in "sbx.tg". These domains often escape static blocklists because they are generated dynamically. A combined triage step then weighs the evidence from all surfaces. An analyst or automated agent reviews the results to reach a final verdict. If confirmed, the hunt initiates host isolation and password resets to prevent stolen cookie use. ### Why this is a hunt We categorize this as a hunt rather than a simple detection because of the noise inherent in browser profile access. Legitimate updates, profile migrations, and synchronization tools often touch these SQLite databases. The hunt provides the necessary context—connecting the initial execution lead to the rare file access—to allow an analyst to confirm the verdict without being overwhelmed by false positives from standard browser activity. ### Blind Spots This hunt relies on endpoint process and file visibility. It cannot see activity on unmanaged hosts or legacy systems without an agent. Additionally, while the hunt identifies the content.js script drop, it does not analyze the internal commands of obfuscated JavaScript in memory. Organizations should ensure script block logging is enabled to supplement this visibility. ### Running the Hunt This hunt is an open hunt.md playbook. You can import it into Huntbase or any compatible runtime. The flow includes parameters for lookback periods and specific indicator lists from the Talos research. Practitioners can adjust the prevalence thresholds in the file activity step to suit their environment's baseline.
