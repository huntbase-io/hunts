Persistent implant using repurposed update utilities

An attacker has established persistence through a scheduled task that executes a randomized binary from a world-writable path, which then uses a legitimate update utility to communicate with Alibaba OSS infrastructure.

Brief

Why Now

Microsoft's recent analysis, Counterfeit installers to system compromise: Tracking a deceptive software download campaign (https://www.microsoft.com/en-us/security/blog/2026/09/01/counterfeit-installers-system-compromise-tracking-deceptive-software-download-campaign/), details how the Silver Fox campaign uses legitimate update utilities to maintain persistence. Attackers deliver these payloads via spoofed sites, eventually staging randomized binaries in directories like ProgramData.

How the Hunt Flows

This hunt flows in three distinct phases. First, we scope the environment by querying the hb_scheduled_job surface. We look for any task configured to run an executable from c:\programdata or c:\users\public. These paths are commonly accessible to low-privileged processes and serve as the primary staging area for this campaign. We filter for .exe extensions to find the initial implant entry point. The second phase runs three queries in parallel to gather evidence. We use the hb_process_activity surface to stack-count processes running from those same writable paths. By calculating the host-level rarity, we isolate unique or rare binaries that appear on only a handful of systems. This step distinguishes a legitimate, fleet-wide administrative tool from a targeted implant. Simultaneously, we inspect hb_dns_activity and hb_http_activity for connections to specific Alibaba Cloud Object Storage Service (OSS) buckets and other campaign domains like pc-razerzone.com.cn. These queries provide the network context needed to confirm C2 activity. Next, an automated agent triages the results. The agent examines the intersection of the scheduled task, the rare process execution, and the cloud storage connections. It attempts to link these events by hostname and timestamp to determine if they represent a single infection chain. This correlation is necessary because legitimate software also uses Alibaba OSS and world-writable paths. The agent provides a verdict for each host, citing the specific telemetry rows that support its conclusion.

What the Hunt Cannot See

This hunt has two primary blind spots. First, if an implant was established before the telemetry lookback window, the initial task creation event may be missing. We rely on the current state of the Task Scheduler, but we may lack the forensic context of when the persistence was first established. Second, we face limited visibility into encrypted C2 traffic. While we can see the connection to the Alibaba OSS domain, we cannot see the specific payload paths or HTTP headers without TLS inspection.

# Persistent implant using repurposed update utilities

This hunt identifies post-compromise activity associated with the Silver Fox (Yinhu) campaign. It focuses on the persistence stage where the malware stages randomized binaries in ProgramData or Public directories and launches them via the Windows Task Scheduler. The hunt identifies these implants by their unusual execution paths, host-level rarity, and subsequent DNS and HTTP requests to the attacker's Alibaba Cloud infrastructure. An agent weighs these independent behavioral signals to distinguish the implant from legitimate administrative tools and update mechanisms.
