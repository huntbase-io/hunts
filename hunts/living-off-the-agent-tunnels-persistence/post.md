# Hunting for Unauthorized Remote Access via AI Coding Agents

### Why this hunt? \n\nElastic Security Labs recently published a detailed analysis titled \"Living off the coding agent: Two tales of tunnels and LaunchAgents\" (https://www.elastic.co/security-labs/threat-command/coding-agent-launchagent-tunnel-detection). Their research demonstrates how signed AI coding agents, which developers increasingly trust with high-level system access, can be manipulated to execute shells, establish reverse tunnels, and even install persistence. Because these agents are often signed and widely used, traditional alerts based on process name or signature can be noisy. This hunt provides a structured way to verify that your developer workstations haven't been turned into remote access points through the very tools meant to increase productivity. \n\n### Hypothesis \n\nOur hypothesis is that an adversary is utilizing the execution capabilities of trusted AI agents—specifically Claude Code and Cursor—to run malicious payloads. By leveraging these agents as living-off-the-land (LotL) proxies, an attacker can bypass standard security controls to establish encrypted reverse tunnels using brokers like Cloudflare or ngrok and maintain access via macOS LaunchAgents. \n\n### How the hunt flows \n\nThe hunt begins with a scoping phase using the `hb_software_inventory` surface. We look for the presence of known AI agents like Claude and Cursor. This allows us to focus our analysis on the specific population of developer machines where this threat is most relevant, rather than scanning the entire fleet for generic shell activity. \n\nNext, we pivot to `hb_process_activity` to identify suspicious execution patterns. We look for shells (zsh, bash) or utility binaries (curl, cloudflared) where the parent process is the coding agent. We specifically look for dangerous flags mentioned in the source article, such as `--allow-dangerously-skip-permissions`, which indicates the agent is operating with reduced guardrails. \n\nWe then examine `hb_network_connection` to identify connections to rare tunnel brokers. By stacking connections to domains like lhr.life, trycloudflare.com, or ngrok-free.app and filtering for low prevalence across the fleet, we can isolate specific workstations that are communicating with ephemeral remote management infrastructure. \n\nThe final technical step involves checking `hb_scheduled_job` for anomalous LaunchAgent persistence. We search for new plist entries or job definitions created within the last 14 days that reference tunnel binaries. This step is crucial for identifying sessions that have transitioned from interactive experimentation to a persistent foothold. \n\n### What the hunt cannot see \n\nThis hunt has two primary blind spots. First, if your EDR does not support deep process ancestry tracking or if the process tree is truncated, the link between the trusted agent and the malicious child shell may be lost. Second, because tunnel brokers use randomized subdomains, we can identify the use of the broker but cannot necessarily correlate specific tunnel instances without high-resolution DNS or HTTP logging. \n\n### How to run it \n\nThis hunt is provided as an open `hunt.md` playbook. It can be imported directly into Huntbase or any security runtime that supports the hunt.md specification. Analysts should focus their review on the command-line arguments of the agent-parented processes; look for credentials being passed in plaintext or commands that interact with the macOS keychain.
