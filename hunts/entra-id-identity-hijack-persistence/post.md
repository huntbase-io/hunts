# Entra ID Identity Hijack and Persistence Hunt

### Why Now Adversaries increasingly bypass MFA via Adversary-in-the-Middle (AiTM) attacks to steal session tokens. The 'M365 Token Spray and Replay Campaign Compromises Business Email Accounts' report by Huntress (https://www.huntress.com/blog/token-replay-spray) details a campaign that uses these tokens to establish directory-level persistence. This hunt provides a structured approach to identifying these sessions and the resulting modifications to the victim's Entra ID directory. ### Hypothesis An adversary replays session tokens stolen through AiTM relays to register rogue devices and establish persistent MFA methods in the victim tenant. ### How the Hunt Flows The scoping phase targets the initial evidence of the Adversary-in-the-Middle (AiTM) relay. The query scans hb_auth_signin for any successful logins that originate from the IP blocks associated with the 1337 Services GmbH infrastructure mentioned in the source. This surface is critical because it captures the moment the token is replayed after initial theft. By filtering for successful status IDs and cross-referencing with known malicious IP ranges, the hunt isolates a candidate list of compromised users and their associated hostnames. Behavioral analysis follows scoping to differentiate between legitimate user travel and automated session hijacking. This phase examines user agent strings within the hb_auth_signin data. The adversary often uses tools that leave signatures such as 'node' or a bare 'Mozilla/5.0' string without the usual platform or browser extensions. Parallel to this, the hunt identifies successful MFA events coming directly from known AiTM relay IPs. When a user account shows a successful MFA prompt from a relay IP followed by a scripted login from a replay IP, the probability of a hijack reaches its peak. Once a hijacked session is confirmed, the hunt pivots to persistence indicators within the directory. It monitors hb_devices for new registrations that match a specific naming pattern: DESKTOP- followed by an eight-character hexadecimal string. The hunt stacks these registrations across the fleet to find outliers. Simultaneously, it queries hb_cloud_api_activity for modifications to authentication methods. This includes the addition or deletion of MFA factors, such as 'strongAuthentication' method updates. These actions represent the adversary securing their foothold. ### Blind Spots The hunt requires Advanced Auditing in Microsoft 365 to see granular MFA modification details. Without this, some tampering events may appear as generic success records. Additionally, replayed tokens inherit the original session's MFA status, meaning the replay might look like a legitimate session resumption if telemetry cannot isolate the relay and replay IP addresses within the same session ID. ### How to Run Use this hunt as a hunt.md playbook. It imports into Huntbase or any compatible runtime for execution against Entra ID and cloud authentication logs.
