Microsoft 365 Service Health Impersonation and Account Abuse

High severity TLP:CLEAR Research by Microsoft Published 17 Nov 2026

Hypothesis

An intruder has gained initial access by sending phishing emails that impersonate Microsoft 365 outage notifications, inducing users to click tracking links that lead to credential theft and subsequent unauthorized cloud API activity.

Brief

Why now

Microsoft Security recently detailed a "High volume phishing campaign uses Microsoft 365 outage lures to target multiple industry sectors" (https://www.microsoft.com/en-us/security/blog/2026/11/16/high-volume-phishing-campaign-uses-microsoft-365-outage-lures-target-multiple-industry-sectors-2/). The adversary sends realistic notifications about service outages or security updates to induce users to click tracking links. These links lead to credential theft and subsequent business email compromise (BEC) activity.

How the hunt flows

The first phase uses a cheap lead query against Microsoft 365 mail telemetry. It searches for specific sender domains and subject lines associated with the service-health lures. This initial step gates the rest of the hunt to ensure we only spend resources on expensive telemetry when relevant lures exist in the environment.

If the lead query returns matches, the hunt fans out into a parallel search across two distinct surfaces. The first branch examines DNS activity to find hosts that resolved the campaign's known tracking and redirection domains. This provides evidence that a user actually clicked the link within the phishing email.

At the same time, the second branch searches cloud API logs for rare impact indicators. It looks for the creation of new inbox rules or OAuth application consents, filtering for operations that occur across only a small number of users. This step identifies the actual impact of the credential theft.

In the final phase, an analyst or automated agent correlates these three points: the delivery of the email, the interaction with the link, and the subsequent API abuse. This sequence confirms a successful account takeover rather than just a blocked phishing attempt.

What this hunt cannot see

This hunt relies on the Microsoft 365 Unified Audit Log. If logging is not centralized or certain mailbox types are excluded, the lead query will not see the incoming lures. Furthermore, the hunt uses a fixed lookback window. If the adversary waits longer than 14 days between the link click and the API abuse, the correlation may fail depending on your local log retention settings.

Steps

  1. Query, scoping

    Lead: Outage-themed phishing lures

    Identify suspicious emails using the campaign's specific sender domains and subject line patterns.

    sql, reads microsoft365_mail_message
    SELECT sender, "from", subject, sent_date_time, internet_message_id, tenant_idFROM microsoft365_mail_messageWHERE (instr(',' || '{{sender_domains}}' || ',', ',' || LOWER(SUBSTR(sender, INSTR(sender, '@') + 1)) || ',') > 0 OR subject LIKE 'Outage -%' OR subject LIKE 'Strengthen - Security%' OR subject LIKE 'Restore — 4 messages%')  AND sent_date_time >= datetime('now', '-{{lookback_days}} days')

    What a hit looks like. Rows identify specific phishing emails delivered to users. Silence suggests the campaign has not targeted the tenant in the current window.

  2. Agent triage

    Verify phishing campaign relevance

    Confirm if the detected emails match the high-volume outage campaign profile based on the reported lures.

  3. Decision

    Gate on phishing evidence

    Route to expensive telemetry queries only if phishing emails are confirmed.

  4. Query, enrichment

    Scoped DNS interaction with tracking domains

    Verify if scoped hosts resolved the campaign's tracking or redirection domains, indicating a link click.

    sql, reads hb_dns_activity
    SELECT device_hostname, query_hostname, answers, timeFROM hb_dns_activityWHERE (('{{scope_hosts}}' = '' OR instr(',' || '{{scope_hosts}}' || ',', ',' || device_hostname || ',') > 0))  AND instr(',' || '{{tracking_domains}}' || ',', ',' || LOWER(query_hostname) || ',') > 0  AND time >= datetime('now', '-{{lookback_days}} days')

    What a hit looks like. Resolution of tracking domains by a host suggests a successful link click from a phishing email.

  5. Query, detection candidate

    Rare cloud API inbox rule manipulation

    Detect account impact by finding users performing rare inbox rule operations or OAuth consents typical of BEC.

    sql, reads hb_cloud_api_activity
    SELECT api_operation, actor_user_name, COUNT(DISTINCT actor_user_name) AS user_count, MIN(time) AS first_seenFROM hb_cloud_api_activityWHERE provider = 'm365'  AND (api_operation IN ('New-InboxRule', 'Set-InboxRule', 'Consent to application'))  AND time >= datetime('now', '-{{lookback_days}} days')GROUP BY api_operation, actor_user_nameHAVING user_count <= 3

    What a hit looks like. Specific users creating inbox rules when such behavior is rare across the tenant. Silence suggests no automated rule manipulation has occurred.

  6. Agent triage

    Correlate email, interaction, and abuse

    An agent weighs the email receipt, DNS interaction, and rare API activity to confirm successful compromise.

  7. Decision

    Route on compromise verdict

    Initiate remediation if an active compromise is confirmed.

  8. Response action

    Isolate compromised account

    Contain the impact by revoking sessions and rotating credentials.

  9. Analyst task

    Forensic analyst review

    Verify the automated correlation and determine the extent of data access.

  10. Analyst task

    Close out hunt

    Finalize documentation and record any identified blind spots.

# Microsoft 365 Service Health Impersonation and Account Abuse

This hunt targets a coordinated phishing campaign using service-health lures. It employs a gated flow where a cheap lead query on mail telemetry determines if campaign-specific lures exist. If confirmed, the hunt fans out to verify user interaction via DNS tracking infrastructure and identifies post-compromise impact through rare cloud API operations, such as the creation of new inbox rules or OAuth application consents. An agent correlates the delivery, interaction, and impact to confirm an active intrusion.

## rare-cloud-api-impact
<!-- Rare cloud API inbox rule manipulation -->
Detect account impact by finding users performing rare inbox rule operations or OAuth consents typical of BEC.

```sqlite target=endpoint role=detection-candidate params=(lookback_days=lookback_days)
~~~yaml

  window: '{{lookback_days}}d'
expected: Specific users creating inbox rules when such behavior is rare across the
  tenant. Silence suggests no automated rule manipulation has occurred.
prevalence:
  by: actor_user_name
  key:
  - api_operation
  rare_below: 4
reads:
- api_operation
- actor_user_name
- time
silence: not_evidence_of_absence
```
