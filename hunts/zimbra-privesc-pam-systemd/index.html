Zimbra Privilege Escalation and Root Persistence

Hypothesis

Brief

Why this hunt

The Microsoft Security Response Center recently detailed CVE-2026-73570 in their post Unauthenticated command injection on internet-facing mail servers: tracking CVE-2026-73570. This vulnerability allows unauthenticated command injection, but the subsequent steps an adversary takes to secure root access are particularly dangerous. Our team published a new hunt.md playbook to track these specific post-exploitation maneuvers.

How the hunt flows

The hunt begins with a scoping phase. The first query identifies every host running Zimbra software by checking the software inventory. This narrows the focus and prevents unnecessary data processing on unrelated systems. Following scoping, the hunt executes two behavioral queries in parallel. The first query focuses on persistence by stacking every systemd service found in /etc/systemd/system/ across the fleet. It looks for rare services appearing on only one or two hosts, specifically watching for names like zimlog.service or services that mimic legitimate system components like rsync or sshd. The second query monitors file activity. It looks for the zimbra user interacting with /etc/pam.d/sudo or the zmmailboxd.out log file. This pattern suggests the adversary is attempting to hijack the sudo configuration by redirecting log writes to sensitive system files. An analyst or automated agent then correlates these findings. The hunt does not just look for a new file; it looks for the specific sequence where a log modification precedes the appearance of a rare service. This automated triage helps distinguish between routine Zimbra maintenance and an active compromise.

Blind spots

The hunt has specific blind spots. If the file activity telemetry does not explicitly capture symlink targets, the creation of the link between the log and the PAM config might appear as a generic file creation or write. Additionally, the hunt relies on identifying new or rare services. If an adversary successfully timestomps the service file to match the modification times of legitimate system files, it may evade filters that look for recently changed configurations.

Steps

  1. Query, scoping

    Identify Zimbra servers

    Define the scope by identifying hosts that have Zimbra software installed.

    sql, reads hb_software_inventory
    SELECT device_hostname, package_name, package_version, vendor_nameFROM hb_software_inventoryWHERE (LOWER(package_name) LIKE '%zimbra%' OR LOWER(vendor_name) LIKE '%zimbra%')

    What a hit looks like. A list of hosts running Zimbra. Silence indicates no Zimbra installation is visible in the current inventory.

  2. Query, baseline

    Rare systemd services

    Stack-count systemd services to find the 'zimlog.service' or other anomalies across the fleet.

    sql, reads hb_scheduled_job
    SELECT job_name, job_definition_path, job_cmd_line, COUNT(DISTINCT device_hostname) AS host_countFROM hb_scheduled_jobWHERE job_definition_path LIKE '/etc/systemd/system/%'  AND (('{{scope_hosts}}' = '') OR (instr(',' || '{{scope_hosts}}' || ',', ',' || device_hostname || ',') > 0))  AND time >= datetime('now', '-{{lookback_days}} days')GROUP BY job_name, job_definition_path, job_cmd_lineHAVING host_count <= 2

    What a hit looks like. A service found on only one or two hosts, specifically looking for 'zimlog.service'.

  3. Query, detection candidate

    PAM and Log Symlink Abuse

    Identify file activity where the zimbra account touches the PAM sudo configuration or its own log files abnormally.

    sql, reads hb_file_activity
    SELECT device_hostname, file_path, actor_user_name, process_name, timeFROM hb_file_activityWHERE (LOWER(file_path) LIKE '%/etc/pam.d/sudo%' OR LOWER(file_path) LIKE '%zmmailboxd.out%')  AND (('{{scope_hosts}}' = '') OR (instr(',' || '{{scope_hosts}}' || ',', ',' || device_hostname || ',') > 0))  AND time >= datetime('now', '-{{lookback_days}} days')

    What a hit looks like. Modifications to the PAM configuration by a non-root user (zimbra), or operations involving the zmmailboxd.out log file that precede sudo elevation.

  4. Agent triage

    Evaluate Escalation Evidence

    Correlate file-system manipulation with new, rare system services to confirm root privilege escalation.

  5. Decision

    Route on verdict

    Direct the response based on the agent's confidence in the privilege escalation findings.

  6. Response action

    Isolate Compromised Server

    Contain the threat by isolating the server where root access was established.

  7. Analyst task

    Forensic Review of Persistence

    Manually verify the symlink state and timestomping evidence that the telemetry might obscure.

  8. Analyst task

    Close out

    Document results and findings.

Blind spots

  • Needs hb_file_activity with symlink target tracking. If the EDR only logs a 'write' or 'create' but not the symlink target, the specific PAM hijacking technique may appear as normal log rotation or noise. It would answer: Was the file modification actually a symlink creation?

# Zimbra Privilege Escalation and Root Persistence

This hunt targets the complex post-exploitation chain observed in CVE-2026-73570. An adversary takes ownership of the sudo PAM configuration by symlinking application logs to sensitive system files. It then identifies rare systemd services created in /etc/systemd/system/, specifically focusing on services named zimlog.service or those whose timestamps have been modified to match legitimate system services like rsync or sshd. The hunt uses an agent to correlate these file and service anomalies, allowing an analyst to confirm root-level persistence.

## rare-systemd-services
<!-- Rare systemd services -->
Stack-count systemd services to find the 'zimlog.service' or other anomalies across the fleet.

```sqlite target=endpoint role=baseline params=(lookback_days=lookback_days, scope_hosts=scope_hosts)
~~~yaml
baseline:
  compare: first_seen
  window: '{{lookback_days}}d'
expected: A service found on only one or two hosts, specifically looking for 'zimlog.service'.
prevalence:
  by: device_hostname
  key:
  - job_name
  - job_definition_path
  rare_below: 3
reads:
- job_name
- job_definition_path
- job_cmd_line
- device_hostname
- time
silence: not_evidence_of_absence
source: hb_scheduled_job
verified: dry-run
verified_at: '2026-10-01'
~~~
SELECT job_name, job_definition_path, job_cmd_line, COUNT(DISTINCT device_hostname) AS host_count FROM hb_scheduled_job WHERE job_definition_path LIKE '/etc/systemd/system/%' AND (('{{scope_hosts}}' = '') OR (instr(',' || '{{scope_hosts}}' || ',', ',' || device_hostname || ',') > 0)) AND time >= datetime('now', '-{{lookback_days}} days') GROUP BY job_name, job_definition_path, job_cmd_line HAVING host_count <= 2
```
