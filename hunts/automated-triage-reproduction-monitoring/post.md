# Monitoring Automated Bug Bounty Triage for Sandbox Escapes

### The Risk of Automation 0a 0aElastic Security Labs recently detailed their Agents vs. Agents (https://www.elastic.co/security-labs/blog/ai-vulnerability-triage-bug-bounty-hackerone) approach to bug bounty triage. They use AI to reproduce reports in ephemeral sandboxes. While efficient, this process executes untrusted, researcher-provided code. We designed this hunt to ensure these reproduction environments do not become a vector for lateral movement or data exfiltration. 0a 0a### Hypothesis 0a 0aAn attacker submits an exploit within a HackerOne report that successfully escapes the ephemeral reproduction sandbox or bypasses network egress filters during automated triage. 0a 0a### Hunt Flow 0a 0aThe hunt begins at the ingestion point. The first phase queries the hb_vulnerability_finding surface to identify reports that reached the internal triage pipeline. We specifically look for findings tagged for validation within a defined lookback period. This step provides the timestamps and metadata necessary to scope the infrastructure search. 0a 0aThe second phase pivots to the cloud infrastructure and container logs. We examine hb_devices to find GCP VM provisioning events matching the triage machine types, such as e2-standard-2 or e2-standard-4 instances. Simultaneously, we query hb_process_activity for Docker Compose executions. This identifies the exact window when the reproduction container was active. 0a 0aAn automated assessment correlates the report ingestion time with the VM lifecycle. The triage pipeline strictly adheres to a 30-minute window for reproduction. We look for any session that exceeds this limit or lacks a corresponding report, which might indicate unauthorized infrastructure use. 0a 0aThe final analysis phase focuses on behavior within the VM. We query hb_script_activity for researcher-provided scripts that attempt environment discovery or container breakouts. This includes searches for access to /proc/, the Docker socket, or namespace entry commands. We also baseline hb_dns_activity to find rare domain lookups. By filtering against a strict whitelist of authorized destinations, we identify potential tunneling or exfiltration attempts. 0a 0a### Blind Spots 0a 0aThis hunt has two primary limitations. First, it lacks visibility into the internal processes of the reproduction container because the agent runs on the VM host. A kernel exploit or container escape might happen without triggering script-level logs. Second, if an adversary uses the GCP metadata service or local proxies to reach internal services, the hunt depends on host-level DNS logs. If these requests bypass DNS or if proxy logs are unavailable, the egress check remains incomplete. 0a 0a### Running the Hunt 0a 0aThis hunt is a hunt.md playbook. It imports into Huntbase or any hunt.md-aware runtime. Users must provide their specific HackerOne status tags and authorized domain whitelists as parameters before execution to ensure accuracy.
