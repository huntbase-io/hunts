# Atomic macOS Stealer: Hunting Deceptive Terminal Commands and Persistence

### Why this hunt? Recent research from Unit 42 titled "Atomic macOS (AMOS) Stealer Activity" (https://unit42.paloaltonetworks.com/atomic-macos-amos-stealer-activity/) highlights a surge in macOS malware delivered through deceptive browser-based instructions. Attackers trick users into copying and pasting commands that download and execute the AMOS stealer. This hunt helps analysts identify the complete infection chain on the endpoint. ### Hypothesis. An adversary has compromised a macOS host using deceptive Terminal setup commands to execute encoded shell scripts, establishing hidden persistence in Application Support and staging harvested data in temporary directories. ### How the hunt flows. The hunt first identifies the scope of the estate by listing all macOS devices. This allows the subsequent behavioral queries to run efficiently against relevant platforms. It ensures that analysts focus their investigation on the hosts capable of running the Mach-O and shell-based payloads associated with AMOS. The first execution phase looks for users piping curl results directly into a shell. While common in developer workflows, the hunt specifically flags these when initiated within Terminal or Zsh sessions. Simultaneously, it checks for DNS resolutions to known AMOS delivery domains. This dual-track check provides high-confidence evidence of the initial compromise attempt. The hunt then pivots to find evidence of persistent infection. It uses fleet-wide rarity analysis to identify hidden directories within the Application Support folder. Legitimate applications typically follow standard naming conventions and appear consistently across the fleet. The query flags hidden paths like .com.apple.accountsd that appear on five or fewer hosts, as the adversary uses these names to masquerade as system services. In the final phase, the hunt searches for data staging artifacts. The AMOS stealer aggregates stolen browser credentials, crypto wallets, and system information into a file named out.zip within the /tmp directory. Finding this archive, especially when linked to the earlier Terminal execution or hidden directory creation, provides strong evidence of a successful compromise and imminent exfiltration. The triage phase is critical for determining the final verdict. The analyst evaluates whether the identified Terminal activity and DNS patterns represent a likely AMOS deployment attempt. This is not a simple binary check; it requires looking at the user context and the sequence of events. If a user executes a curl pipe and then immediately we see a new hidden directory in Application Support, the confidence in the verdict increases significantly. This phased approach reduces the noise typically associated with monitoring developer environments where curl is a daily tool. ### What the hunt cannot see. This hunt has two primary blind spots. First, it depends on the endpoint agent's visibility into hidden directories within the user's Application Support folder. If the monitoring tool does not record file creations in hidden paths or lacks the necessary permissions to traverse these directories, the persistence artifacts will remain invisible. Second, the staging archive in /tmp is often ephemeral. If the malware deletes out.zip immediately after a successful upload to the command-and-control server, the file activity might not be captured unless the logging system operates in real-time. ### How to run it. This hunt is provided as an open hunt.md playbook. You can import this file directly into Huntbase or any other hunt.md-aware runtime. The playbook guides you through the scoping, parallel execution checks, and the automated triage of the results to confirm whether your macOS fleet has been affected by this stealer.
