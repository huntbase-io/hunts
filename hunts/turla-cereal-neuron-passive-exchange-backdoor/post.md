# Hunting Turla CerealNeuron Passive Exchange Backdoors

### Why this hunt? ESET Research recently published [Exchange for breakfast: Turla’s Cereal tricks are not for kids](https://www.welivesecurity.com/en/eset-research/exchange-for-breakfast-turlas-cereal-tricks-are-not-for-kids/), detailing Turla's use of CerealNeuron. This component acts as a passive listener rather than a standard beaconing implant. It sits within the IIS pipeline on Exchange servers and waits for specific requests. This makes traditional network alerts for suspicious outbound connections ineffective because the backdoor never initiates a connection. It only responds when an operator sends a correctly formatted and encrypted request to a monitored URI. The passive listener concept is a significant shift from the typical client-server model. Usually, defenders look for a host calling home. With CerealNeuron, the operator calls the host. This uses the target's own infrastructure as the command gateway. Because the traffic is directed at common services like Outlook Web Access, it blends with legitimate login attempts and synchronization requests. ### Hypothesis An adversary installs a passive .NET backdoor on a Microsoft Exchange server that intercepts commands via specific URI paths within standard Exchange web services. ### How the hunt flows The hunt first identifies every host running Microsoft Exchange Server. It uses software inventory data to create a narrow scope for high-volume web log analysis. Identifying these assets is a critical step because Exchange servers generate a massive volume of web traffic. By narrowing the scope, the analyst can run behavioral analysis without generating excessive false positives. The investigation then forks into two parallel checks on the identified Exchange hosts. The first query searches for known C2 paths like /owa/sdds/ or /autodiscover/proxyservice/. These are hardcoded markers for CerealNeuron command reception. The second query baselines source IP activity across Exchange namespaces. It targets rare external entities that only interact with one or two servers. This behavioral check identifies operators who have rotated their URI paths to avoid indicator-based detection. An analyst reviews the combined output to classify the traffic. This is a hunt rather than a detection because simple URI matching is brittle. A detection based only on specific paths would miss variations of the attack. By incorporating a prevalence baseline, the analyst can find new variations. This requires a human to verify the source IP reputation and the user-agent profile. If the triage confirms malicious activity, the analyst isolates the server. Before remediation, the hunt directs the team to capture a memory dump of the w3wp.exe process to preserve the backdoor running in volatile memory. This is necessary because the backdoor exists as a .NET assembly loaded into the IIS worker process. The forensic phase also looks for CerealHermit, which handles the execution of received commands. ### Blind spots The hunt cannot inspect URI paths if the traffic is encrypted and the EDR lacks visibility into the web server process. In environments without endpoint-level HTTP inspection or SSL termination logging, analysts must rely solely on source IP outliers. Additionally, if the adversary rotates URI paths frequently, simple indicator matching will fail. The hunt also assumes that the adversary uses the same source IP for multiple commands; if they use a unique IP for every request, the statistical baseline will not flag the activity. ### How to run This is a hunt.md playbook. It imports directly into Huntbase or any compatible runtime. You can run the scoping and investigative queries as a structured sequence to verify the integrity of your Exchange estate. The design ensures that even if specific indicators change, the behavioral patterns of rare access provide a secondary layer of detection.
