# Hunting Agentic Offensive Frameworks via Network Tempo and Browser Execution

### Why this hunt Elastic Security Labs recently published "Inside the loop: Five AI attack frameworks that never ask permission" documenting the evolution of agentic offensive tools. Frameworks like ARTEX and CyberStrikeAI move beyond simple scripts; they use LLMs to plan and execute commands autonomously. Because these agents can issue requests every few seconds, they operate at a speed that manual observation cannot match. This hunt provides a structured way to identify the footprints of these automated agents before they move from initial access to full lateral movement. ### Hypothesis An adversary uses agentic offensive frameworks to automate initial access and command execution. This behavior creates a detectable signal through high-frequency network bursts and browser processes that spawn system shells. ### How the hunt flows The hunt begins with a scoping phase focused on the external perimeter. We identify hosts running web-facing services that have high-severity vulnerabilities like remote code execution or injection. By focusing on these assets, we isolate the most likely entry points for an automated framework attempting to establish a foothold. Following the scoping, we run three behavioral checks in a parallel phase to gather evidence from both the network and the host. The first check focuses on network tempo. We group HTTP activity into 30-second windows and flag source IPs that exceed a density threshold of 20 requests. This high-frequency heartbeat is a primary indicator of an automated AI loop. The second check looks for DNS resolutions of domains known to be associated with these offensive frameworks, such as update.pentagi.com. The third check identifies browser processes like Chrome or Edge acting as the parent to system shells like PowerShell or Bash. This matches the known tradecraft of using malicious extensions to execute commands. The final phase is the triage correlation. An analyst or an automated agent examines the overlap of these three signals. We look for specific hosts that show both the network burst pattern and the corresponding browser-originated shell execution. This correlation is what distinguishes the hunt from a simple detection. While a browser spawning a shell might be a one-off anomaly, the alignment with high-tempo network windows provides the context needed to identify an active offensive agent. ### Blind spots This hunt has two primary blind spots. First, we do not have visibility into the HTTP request payloads. We rely on the tempo and timing of the traffic to identify the agent rather than the specific commands being sent. Second, while we identify the browser as the parent process, we do not have a direct inventory of the specific malicious extension ID. Confirming the responsible extension requires manual forensic investigation or additional endpoint telemetry like osquery extension logs. ### How to run this hunt We provide this hunt as an open hunt.md playbook. You can import this file directly into Huntbase or any runtime environment that supports the hunt.md standard. The playbook includes parameters for the lookback period, the burst threshold, and the target domains, allowing you to tune the logic to the specific traffic profiles of your network environment.
