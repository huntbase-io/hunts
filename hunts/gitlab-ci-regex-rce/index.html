GitLab CI/CD Regex Compiler RCE Detection

High severity TLP:CLEAR Research by Rapid7 Published 14 Oct 2026

An attacker exploited CVE-2026-97229 by planting a malicious .gitlab-ci.yml in a repository, causing an integer overflow in the Ruby Onigmo engine that executes arbitrary commands as the git user.

Brief

Why now

Rapid7 recently published a report on CVE-2026-97229 (https://www.rapid7.com/blog/post/etr-cve-2026-97229-critical-unauthenticated-remote-code-execution-in-gitlab), detailing a CVSS 10.0 vulnerability in self-managed GitLab Community and Enterprise editions. This flaw resides in the Ruby Onigmo regex engine used during CI/CD configuration parsing. An unauthenticated attacker can trigger an integer overflow by submitting a crafted .gitlab-ci.yml file, leading to remote code execution as the git user.

How the hunt flows

The hunt begins with a scoping phase using software inventory telemetry. It identifies every self-managed GitLab instance running the affected 19.2, 19.3, or 19.4 branches. This prevents the hunt from processing telemetry for patched or unrelated systems, ensuring the remaining queries focus only on vulnerable infrastructure.

After identifying targets, the hunt searches for delivery evidence through two parallel paths. The first query monitors file activity for writes to .gitlab-ci.yml files, while the second examines web traffic for unauthenticated project creation or IDE session initialization. These queries establish a timeline of configuration changes that could deliver the exploit payload.

The execution phase pivots to process telemetry to find signs of a successful overflow. It looks for rare shell spawns or network utility executions, such as bash, python, or curl, originating from GitLab worker processes like Sidekiq, Ruby, or Bundle. The query uses stack-counting across the estate to highlight commands that appear on three or fewer hosts, filtering out common developer hooks or maintenance tasks.

Finally, an automated agent reviews the findings from all previous steps. It correlates the presence of a vulnerable version with recent delivery indicators and anomalous process behavior. This multi-stage approach ensures that a verdict of malicious activity is based on a complete exploit chain rather than an isolated, potentially benign event.

What the hunt cannot see

This hunt requires endpoint telemetry from an agent installed on the GitLab host. If a server is not enrolled in process and file monitoring, the hunt cannot observe the execution or delivery phases. Additionally, the telemetry used here focuses on file paths and process command lines; it does not include the content of the .gitlab-ci.yml file itself. An analyst must manually inspect the repository contents if the hunt flags a suspicious configuration write to confirm the presence of the malicious regex.

    What a hit looks like. A hit identifies the timestamp and actor behind a configuration change. Normal DevOps activity will create noise here.

  3. Query, enrichment

    Suspicious project management traffic

    Identify HTTP requests indicating a new project or IDE session, preceding the planting of the exploit.

    What a hit looks like. Rows show IPs initiating project setup. High volumes from external or unknown IPs warrant closer inspection.

  4. Agent triage

    Assess delivery risk

    Determine if any vulnerable host is currently showing signs of exploit delivery.

  5. Query, detection candidate

    Rare processes spawned by GitLab workers

    Identify successful RCE by stack-counting rare shell and utility processes spawned by the Ruby application workers.

    sql, reads hb_process_activity
    SELECT LOWER(process_cmd_line) AS cmd, GROUP_CONCAT(DISTINCT device_hostname) AS hosts, COUNT(DISTINCT device_hostname) AS host_count, MIN(time) AS first_seenFROM hb_process_activityWHERE LOWER(user_name) = LOWER('{{git_user}}')  AND (LOWER(parent_process_name) LIKE '%ruby%' OR LOWER(parent_process_name) LIKE '%sidekiq%' OR LOWER(parent_process_name) LIKE '%bundle%')  AND (LOWER(process_name) LIKE '%/sh' OR LOWER(process_name) = 'sh' OR LOWER(process_name) LIKE '%/bash' OR LOWER(process_name) = 'bash' OR LOWER(process_name) LIKE '%/python%' OR LOWER(process_name) = 'python' OR LOWER(process_name) LIKE '%/curl' OR LOWER(process_name) = 'curl' OR LOWER(process_name) LIKE '%/wget' OR LOWER(process_name) = 'wget')  AND ('{{scope_hosts}}' = '' OR instr(',' || '{{scope_hosts}}' || ',', ',' || device_hostname || ',') > 0)  AND time >= datetime('now', '-{{lookback_days}} days')GROUP BY cmdHAVING host_count <= 3

    What a hit looks like. A rare shell command or network utility spawned by a GitLab worker is a high-fidelity indicator of successful RCE. Silence proves the absence of this specific behavior on the GitLab hosts during the window.

  6. Agent triage

    Review the complete exploit chain

    Correlate the delivery indicators with the execution indicators to confirm exploitation.

  7. Decision

    Route on verdict

    Direct the hunt to immediate isolation or manual review based on the agent's confidence.

  8. Response action

    Isolate and remediate

    Halt the attack and bring the server to a secure, patched state.

  9. Analyst task

    Analyst forensic review

    Verify the findings and identify the specific malicious project path.

  10. Analyst task

    Close out report

    Document the hunt results and any remediation taken.

# GitLab CI/CD Regex Compiler RCE Detection

This hunt covers the entire lifecycle of CVE-2026-97229 exploitation on self-managed GitLab instances. It begins by scoping the estate to vulnerable 19.2, 19.3, and 19.4 version branches. The hunt then moves through a phased flow: first identifying delivery evidence via configuration file writes and suspicious web activity, followed by a search for the successful execution phase where the GitLab worker process spawns rare shell or utility processes under the git account. An agent weighs the delivery and execution evidence together per host to provide a final verdict.

## rce-behavior-prevalence
<!-- Rare processes spawned by GitLab workers -->
Identify successful RCE by stack-counting rare shell and utility processes spawned by the Ruby application workers.

```sqlite target=endpoint role=detection-candidate params=(git_user=git_user, scope_hosts=scope_hosts, lookback_days=lookback_days)
~~~yaml

  compare: first_seen
  window: '{{lookback_days}}d'
```
