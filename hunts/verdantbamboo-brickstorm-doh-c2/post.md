# Hunting for VerdantBamboo DoH C2 and BRICKSTORM Implants

Recent research from Volexity, titled [VERDANTBAMBOO: Just Another BRICKSTORM in the Firewall](https://www.volexity.com/blog/2026/06/04/verdantbamboo-just-another-brickstorm-in-the-firewall/), highlights a sophisticated campaign targeting Linux-based edge appliances. The actors utilize a custom implant known as BRICKSTORM to establish C2 over DNS-over-HTTPS (DoH). Because the traffic is encrypted and directed toward legitimate public resolvers like Google (8.8.8.8), it often bypasses standard network filtering and perimeter logging.

### The Hypothesis
Our hunt is built on the premise that a compromised system will perform command-and-control over DoH to evade inspection. This behavior is characterized by persistent TLS connections to public DNS resolvers initiated by unusual system binaries. While browsers may legitimately use DoH, system daemons or utilities located in paths like `/usr/sbin/` or `/usr/local/libexec/` generally should not.

### How the Hunt Flows
The hunt begins by examining the `hb_network_connection` surface to identify any process making TLS connections (port 443) to a list of known public DoH providers, specifically focusing on 8.8.8.8 as noted in the source material. We look for connections that are long-lived or frequent, filtering for non-standard browser activity.

Next, the hunt performs a prevalence analysis across the fleet. We stack-count the binaries responsible for these connections to find outliers. A binary like `ssync` or `blacklist` appearing on only one or two devices in a system path is a high-fidelity pivot point for compromise. This step reduces the noise generated by legitimate administrative tools.

We then correlate this network activity with the `hb_dns_activity` surface. The goal is to identify 'DNS silence.' If a host is communicating extensively over the network but producing very few standard DNS queries (port 53), it suggests that DNS resolution has been redirected through an encrypted tunnel like BRICKSTORM. This correlation is what elevates the analysis from a simple detection to a behavioral hunt.

Finally, the hunt triages findings by looking for secondary persistence markers, such as specific crontab entries associated with the AGENTPSD implant or unusual `sudo` activity. This provides the forensic context needed to confirm a breach before moving to isolation.

### Blind Spots
This hunt relies heavily on the availability of network telemetry from edge appliances. If your pfSense, Synology, or other Linux-based VMs do not export connection logs, the primary indicator will be missed. Furthermore, if the threat actor rotates away from Google’s 8.8.8.8 to a less common or private DoH resolver, the scoping query may require adjustment.

### How to Run This Hunt
This hunt is provided as a `hunt.md` playbook. It is designed to be imported into Huntbase or any other runtime capable of parsing the hunt.md format. The queries are formatted in SQLite and intended to run against datasets that include process, network, and DNS telemetry. It is recommended to run this hunt periodically, particularly on DMZ-facing Linux infrastructure.
