# Hunting Unauthorized RMM Deployment and Service Persistence

### The Context
Recent analysis from Red Canary, titled [The dual-use dilemma: Rethinking detection for remote access tool abuse](https://redcanary.com/blog/security-operations/rmm-detection/), highlights the persistent challenge of distinguishing between legitimate IT administration and adversary activity. Adversaries increasingly favor Remote Monitoring and Management (RMM) tools like ScreenConnect, NetSupport, and Syncro because they are signed, functional, and often already permitted by security software. When these tools are used for persistence, they provide a reliable, stable backdoor that mimics standard support behavior.

### Hypothesis
We hypothesize that adversaries are deploying legitimate RMM tools to user-writable paths (e.g., `\Users\Public\` or `%AppData%`) or utilizing unusual process trees (e.g., Syncro spawning MSIExec for sideloading) to establish persistent access. These deployments will lack corresponding entries in the organization's authorized software inventory and will exhibit low prevalence across the estate.

### How the Hunt Flows
The hunt begins by establishing a baseline. We query the software inventory to identify which hosts have authorized RMM software installed. This allows us to focus our behavioral analysis on hosts where these tools should not be present, reducing the noise generated by legitimate IT operations.

Next, we examine process telemetry for RMM binaries running from suspicious locations. We look for known filenames like `client32.exe` or `syncrolive.agent.runner.exe` executing from user-writable directories. We also monitor for specific lure filenames identified in recent phishing campaigns that masquerade as MSTeams or IRS documents.

To catch renamed binaries, we perform stack-counting on all executables and MSI files in Public and Temp directories. By excluding binaries with metadata from known-good vendors and looking for those with very low host counts, we can isolate stealthy RMM installers that have been renamed to evade simple filename-based detections.

Finally, we enrich the investigation by searching PowerShell script logs for RMM installation cradles. This identifies the initial download phase, often occurring immediately after a user interacts with a phishing lure. The hunt concludes with an analyst review to triage these signals against the authorized inventory before taking containment actions.

### What the Hunt Cannot See
There are two primary blind spots. First, if PowerShell Script Block Logging is not enabled, we lose visibility into fileless download cradles that execute entirely in memory. Second, generic `msiexec.exe` activity is difficult to qualify as RMM abuse unless it is tied to a specific parent process like Syncro; standard application updates may create significant noise here.

### How to Run This Hunt
This design is formatted as a `hunt.md` playbook. It can be imported directly into Huntbase or any security platform that supports the `hunt.md` standard for automated execution and triage. Because this relies on environment-specific baselines (the authorized software list), it is structured as a hunt rather than a static detection.
