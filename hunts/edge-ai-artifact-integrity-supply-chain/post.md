# Hunting for Edge AI Model Tampering and Exfiltration Patterns

### Background\n\nAs organizations move AI execution to the edge, the responsibility for securing the models often shifts to customer-owned infrastructure. A recent article by Microsoft, [How to secure edge AI in customer-owned environments](https://www.microsoft.com/en-us/security/blog/2026/09/04/secure-edge-ai-customer-owned-environments/), highlights the importance of protecting the integrity of these environments. When model execution happens outside a controlled cloud provider, the artifact files—containing sensitive intellectual property—become targets for tampering or theft.\n\n### The Hypothesis\n\nWe hypothesize that an adversary might compromise the supply chain or the local file system to modify model weights (e.g., poisoning) or configurations. Furthermore, we expect such an adversary to utilize multi-hop proxies, such as Tor or Onion services, to mask the exfiltration of these multi-gigabyte artifacts or to hide command-and-control (C2) traffic.\n\n### How the Hunt Flows\n\nThe first phase involves scoping. We use software inventory telemetry to identify hosts running specific AI libraries and runtimes, such as PyTorch, TensorFlow, Ollama, and HuggingFace. This narrows our search to legitimate inference nodes and avoids noise from unrelated general-purpose servers.\n\nOnce the scope is established, the hunt pivots into parallel investigations across three surfaces. First, we examine file activity for writes or modifications to specific AI-related extensions like .safetensors, .pt, and .gguf. We specifically look for modifications performed by unauthorized or rare processes rather than standard update utilities.\n\nSimultaneously, we analyze network connections to identify high-volume outbound data transfers (exceeding 50MB) to destination IPs that are rare across the environment. This helps identify the physical transfer of large model files. We also monitor DNS activity for lookups related to known proxy networks like Tor or onion services, which are highly unusual for production AI workloads.\n\nThe final stage involves a triage agent that combines these signals. The goal is to determine if a specific host shows concurrent evidence of file tampering and suspicious network egress, which would suggest a high-confidence compromise.\n\n### Blind Spots and Limitations\n\nThis hunt relies on endpoint telemetry. If the Edge AI environment uses proprietary gateways or specialized IoT hardware where an agent cannot be installed, these systems remain invisible. Additionally, if an adversary exfiltrates data by blending into legitimate encrypted traffic—such as uploading to an authorized Azure Blob storage container—the volume-based checks may not trigger unless the process identity itself is identified as suspicious.\n\n### Running the Hunt\n\nThis hunt is provided as a hunt.md playbook. It can be imported into Huntbase or any other runtime that supports the hunt.md specification. Analysts can adjust the lookback period and the list of targeted AI software packages to match their specific deployment of edge models.
