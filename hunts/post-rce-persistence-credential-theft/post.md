# Hunting Post-Exploitation Activity Following PHP Core RCE Vulnerabilities

### Why this hunt?   Elastic Security Labs recently published an analysis of CVE-2026-109618 and CVE-2026-109619, titled "php2shell: Assessing Elastic detection coverage relevant to CVE-2026-109618 and CVE-2026-109619" (https://www.elastic.co/security-labs/threat-command/php2shell-php-rce-detection). These vulnerabilities allow unauthenticated remote code execution in the PHP core. While many detections focus on the initial HTTP request, network-level patterns are often obfuscated or missed by generic signatures. This hunt focuses on the post-exploitation outcomes where the attacker moves from the web request into the operating system.   ### The Hypothesis   An attacker has exploited a PHP core vulnerability and is using the web worker context to harvest credentials or establish persistence via reverse shells and web shells. The transition from a web worker process—such as php-fpm or apache2—to system-level actions like reading sensitive configuration files or spawning interactive shells provides a high-confidence signal of compromise.   ### How the Hunt Flows   The first phase identifies the scope of the hunt using the hb_software_inventory surface. The query searches for hosts running PHP, Apache, or Nginx. This step ensures the hunt focuses on assets capable of being exploited by the php2shell vulnerabilities and reduces the processing load on the rest of the estate.   Once the assets are identified, the hunt performs a parallel fan-out to examine two distinct types of malicious behavior. The first branch analyzes the hb_file_activity surface. It looks for web worker processes or their immediate children accessing sensitive files like .env, AWS credentials, or the system shadow file. It also identifies the creation of new PHP or phtml files on the web root, which often indicates the staging of a web shell. The query uses a prevalence filter to hide files accessed by many hosts, highlighting rare and potentially unauthorized actions.   The second branch of the fan-out monitors the hb_process_activity surface. It specifically looks for web workers spawning shell primitives and networking tools like netcat, socat, or mkfifo. It also checks command lines for /dev/tcp redirections and pty spawns. Because web workers rarely spawn these binaries in a production environment, any matches represent a high-priority triage event.   The final phase uses an automated agent to correlate these findings. The agent compares the file access events with the process spawns on a per-host basis. It looks for functional transitions where a web worker first accesses a credential file and then executes an outbound connection. An analyst then reviews the verdict to confirm if the activity aligns with a standard deployment or indicates a successful RCE.   ### Blind Spots   This hunt relies on comprehensive endpoint telemetry. If a Linux web node does not have an active agent, the process and file activity remain invisible to these queries. Additionally, an attacker may use fileless execution techniques within the PHP interpreter, such as eval() calls that do not spawn a sub-process. This hunt cannot see in-memory execution that avoids the process and file surfaces.   ### How to Run This Hunt   This playbook is provided as an open hunt.md file. You can import it directly into Huntbase or any hunt.md-aware runtime environment. The design allows for periodic execution to provide evidence of absence for these specific PHP vulnerabilities across your web-facing infrastructure.
