Processes Defender Scored but Never Alerted On

Medium severity TLP:CLEAR Part 2 of 5 Research by Protokol-7 Published 19 Nov 2026

Hypothesis

An intruder's tooling on a Windows host performed credential access, injection, persistence or defence-evasion behaviour that Microsoft Defender attributed to the process as ATT&CK techniques, but stayed below the threshold for a detection, so nothing reached Protection History or the SIEM.

Brief

Why This Hunt Matters

Microsoft Defender reasons about more than it reports. For each process, its behaviour monitoring keeps a running list of the ATT&CK techniques it has attributed, such as T1003.001 against a renamed procdump or T1547.001 against a rundll32. It raises a detection only when the combined score crosses a threshold. Everything below that line is never shown, in Protection History or anywhere else.

Protokol-7 found that these attributions live in the attack-scoring queues of Defender's encrypted database, mpenginedb.db, keyed by process ID and start time. The open-source osquery-defender-extension decrypts the database and exposes the queues as an osquery table. For the many Windows fleets that run Defender Antivirus without Defender for Endpoint, this is the only behavioural sensor they have, and its sub-threshold judgement was previously thrown away.

How the Hunt Flows

The first query reads the queues on every Windows host. For each process it returns the techniques Defender attributed or that the process inherited from its parent, how many fall in a list of high-signal techniques, and the running process's path and command line where the PID and start time still match. The hunt stacks the image and technique set across the fleet. An updater scored for the same techniques on 3,000 hosts drops away, and a binary in AppData scored for T1003.001 on one host stands out.

Three queries then ask whether Defender said anything about each process. The host's own threat queue shows the behaviour detections the engine named against specific PIDs. The low-fidelity queue shows files sent for a cloud verdict; Protokol-7 found hashcat modules there. Forwarded Defender detections show what reached the SIEM. An agent keeps only the scored processes with no alert of any kind and ranks them.

For those, the hunt rebuilds context from ordinary telemetry: the parent, command line, user and hash of each process, and the files it wrote. A .dmp file written by a process Defender scored for LSASS access settles the question quickly. A second agent gives a verdict per process. Malicious ones go to an approval-gated action that copies the Scans folder and a memory image before isolating the host. Unclear ones go to an analyst.

What the Hunt Cannot See

The technique queues keep entries for about an hour. A live run sees only the last hour; to hunt over days, schedule the extension's defender_mpengine_process_techniques pack query every 30 minutes and run the triage over its results. Without Defender detections in the SIEM, "never alerted" rests on the host's own threat queue alone. Microsoft does not document how techniques are attributed or where the threshold sits, so every row is treated as Defender's opinion, a lead rather than proof. Processes that have exited no longer join to the live process table and need process history from other telemetry.

Steps

  1. Query, baseline

    Processes Defender attributed techniques to

    Read the attack-scoring queues: for each process, the ATT&CK techniques Defender attributed to it or that it inherited from its parent, keyed by PID and start time, joined to the running process where the PID and start time still match. Defender keeps these entries for about an hour, so this is a view of the last hour unless the pack query has been collecting them.

    sql, reads defender_mpengine_rolling_queues
    SELECT (SELECT hostname FROM system_info) AS device_hostname, r.pid, r.process_start, CASE WHEN json_valid(r.entry_value) THEN json_extract(r.entry_value, '$.Process_Img') END AS scored_image, COUNT(DISTINCT r.technique_id) AS technique_count, GROUP_CONCAT(DISTINCT r.technique_id) AS techniques, SUM(CASE WHEN instr(',' || LOWER('{{high_signal_techniques}}') || ',', ',' || LOWER(r.technique_id) || ',') > 0 THEN 1 ELSE 0 END) AS high_signal_hits, MAX(CASE WHEN r.queue_type = 'inherited_techniques' THEN 1 ELSE 0 END) AS inherited, MIN(r.insert_time) AS first_scored, MAX(r.insert_time) AS last_scored, p.path AS live_path, p.cmdline AS live_cmdline, p.parent AS live_parent_pidFROM defender_mpengine_rolling_queues rLEFT JOIN processes p ON p.pid = r.pid  AND ABS(p.start_time - r.process_start) <= 2WHERE r.queue_type IN ('techniques', 'inherited_techniques')  AND r.technique_id != ''GROUP BY r.pid, r.process_startORDER BY high_signal_hits DESC, technique_count DESC

    What a hit looks like. Installers, updaters and management agents are scored every day and appear on many hosts with the same techniques. A user-space image, or a LOLBin with credential-access, injection or persistence techniques on one or two hosts, is the lead. live_path is empty once the process has exited.

  2. Query, enrichment

    Threats Defender recorded on the host

    Read the RecentThreatsOnMachine queue: the behaviour detections the engine named, with the PID and image they were raised against. A scored process with a threat record was noticed; one without was not.

    sql, reads defender_mpengine_rolling_queues
    SELECT (SELECT hostname FROM system_info) AS device_hostname, entry_key AS threat_name, pid, process_start, CASE WHEN json_valid(entry_value) THEN json_extract(entry_value, '$.Process_Img') END AS image, insert_timeFROM defender_mpengine_rolling_queuesWHERE queue_type = 'recent_threats'  AND insert_time >= (CAST(strftime('%s', 'now') AS INTEGER) - {{lookback_days}} * 86400)

    What a hit looks like. Behavior:Win32/... names against specific PIDs. Matching pid and process_start to scored-processes shows which scored processes Defender did act on.

  3. Query, enrichment

    Low-fidelity signature hits sent to the cloud

    List files that matched a low-fidelity signature and were sent for an asynchronous cloud verdict. These are Defender's maybes; Protokol-7 found hashcat modules here.

    sql, reads defender_mpengine_lowfi_async
    SELECT (SELECT hostname FROM system_info) AS device_hostname, file_name, sig_seq, sig_sha, sig_is_sync, instance_timeFROM defender_mpengine_lowfi_asyncWHERE instance_time >= (CAST(strftime('%s', 'now') AS INTEGER) - {{lookback_days}} * 86400)

    What a hit looks like. A LowFi hit on the scored image, or on a file beside it, strengthens the lead. Signature sequence numbers are not documented.

  4. Query, enrichment

    Defender detections that reached the SIEM

    List the Defender detections forwarded from these hosts in the window, to tell scored processes that alerted from those that did not.

    sql, reads hb_detection_finding

    What a hit looks like. Detections with a process_path or file_path matching a scored image mean the process alerted. No rows from a host with scored processes is either a real gap or detections not being forwarded.

Blind spots

  • Needs the defender_mpengine osquery extension loaded by osqueryd (running as SYSTEM) on every Windows host, with Microsoft Defender Antivirus as the active engine and defender_mpengine_status.error empty. Those hosts return no rows, which looks the same as a clean host. An attacker who has removed or stopped Defender also leaves an empty or stale database. It would answer: Did Defender record anything on hosts where the extension is missing, cannot decrypt the database, or Defender is passive behind another antivirus? Remediation: Deploy the extension through extensions.load on all Windows hosts and alert on defender_mpengine_status rows with a non-empty error.
  • Needs the pack query defender_mpengine_process_techniques scheduled every 30 minutes, with its results kept. Technique queue entries expire after about an hour. A live run sees only the last hour, so a burst of activity yesterday leaves no scoring rows. It would answer: What did Defender score more than an hour ago?
  • Needs Defender detections (Defender events 1116/1117 or MDE alerts) in hb_detection_finding. Without forwarding, 'never alerted' rests on the host's own threat queue only, and a process can be marked silent when it did alert. It would answer: Did a scored process alert somewhere this hunt cannot see?
  • Needs Microsoft documentation of how attack scoring attributes techniques and where the alert threshold sits. The attribution is Defender's opinion and is not documented; the hunt treats it as a lead, never as proof. It would answer: Why was this technique attributed, and how close was it to an alert?

# Processes Defender Scored but Never Alerted On

Defender does more reasoning than it reports. For each process it keeps a running list of the ATT&CK techniques its behaviour monitoring attributed, for example T1003.001 against a renamed procdump or T1547.001 against a rundll32, and it raises a detection only when the score crosses a threshold. Everything below the threshold stays in the attack-scoring queues of mpenginedb.db and is never shown.

This hunt reads those queues on every Windows host through the defender_mpengine osquery extension, joins each PID to the running process, and stacks the image and technique sets across the fleet so that software scored everywhere drops away. It then removes processes Defender did act on, using the host's own threat records, low-fidelity cloud lookups and the detections forwarded to the SIEM. The rest is a list of processes Defender suspected and never mentioned.

Each of those is put back in its process tree and checked for the files it wrote before an agent and an analyst decide what it was. The queues keep about an hour, so the hunt is most useful run often, or over results the pack query has been collecting.

