# Identifying PII Harvesting and Subsequent Remote Service Abuse

### Why this hunt ESET Research, "Is it safe to upload my passport or ID online?", explores how attackers trick users into submitting sensitive identification. This hunt addresses the risk where attackers use copycat portals to harvest passport scans and selfies. We focus on the sequence where a user interacts with a fake portal and then experiences unauthorized access to corporate resources. ### The Hypothesis An intruder redirects users to a copycat visa or identity portal to harvest passport scans and selfies. They subsequently use these stolen identities to authenticate to external remote services, such as VPNs or Citrix gateways, from unusual locations. ### How the Hunt Flows The first phase identifies leads through DNS activity. The lead query finds rare resolutions to domains that mimic legitimate government or travel portals. While we provide a list of identity-themed domains as a baseline, the hunt specifically highlights lookups that are infrequent within the environment. This rarity helps filter out common traffic and isolates potential victims. After an analyst or agent evaluates the legitimacy of these domains, the hunt proceeds to a scouting phase. This phase runs two queries in parallel to gather evidence of both data submission and subsequent abuse. The first query monitors outbound HTTP POST requests. It looks for body sizes exceeding 100KB, which is a proxy for the transmission of image files or scanned documents. Since passport scans are relatively large, this threshold eliminates smaller, routine web form submissions. The second parallel query examines authentication logs for the hosts identified in the DNS phase. It searches for successful sign-ins to remote services that originate from unfamiliar countries or use unexpected protocols. This step identifies the transition from identity theft to active exploitation of the stolen credentials. We prioritize remote interactive and network logons that align with the timing of the initial DNS lead. In the final triage phase, an analyst correlates these signals. A confirmed malicious chain shows a user visiting a suspicious domain, followed by a significant data upload, and ending with anomalous remote access. This progression provides the context necessary to distinguish a targeted attack from routine web browsing. The correlation minimizes the false positives inherent in looking at authentication anomalies or large uploads in isolation. ### Blind Spots This hunt has two primary limitations. If an adversary uses DNS-over-HTTPS (DoH) or a non-enrolled resolver, the initial DNS lead remains invisible. The hunt relies on endpoint or resolver logs to catch the redirection. Furthermore, without TLS inspection on the HTTP traffic, we cannot inspect the contents of the POST requests. We rely on the request body size as a proxy for biometric or document uploads, which may produce false positives from other encrypted data transfers. ### How to Run This Hunt This hunt is an open hunt.md playbook. You can import it into Huntbase or any runtime that supports the hunt.md format. The design allows practitioners to adjust the lookback period and the list of suspected domains to match current intelligence. Because it correlates multiple stages of the attack, it provides a higher fidelity verdict than isolated detection rules.
