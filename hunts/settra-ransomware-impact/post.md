# Hunting Settra Ransomware Local Impact and Recovery Inhibition

### Why this hunt Huntress recently detailed a Settra ransomware variant in "Ready, Settra, Go: New Settra Ransomware Variant Deploys MeshAgent RMM" (https://www.huntress.com/blog/new-settra-ransomware-variant). This threat demonstrates a clear progression from gaining initial access to crippling local recovery options. ### The Hypothesis An adversary executes Settra ransomware by deploying a domain-specific launcher and a Bring Your Own Vulnerable Driver (BYOVD) to disable security products. Once defenses are down, the attacker inhibits recovery mechanisms and encrypts files. ### How the hunt flows The hunt begins by inventorying active Windows hosts using the hb_devices surface. This scoping ensures the subsequent queries focus only on relevant endpoints where the ransomware is known to operate. The next phase looks for early-stage indicators. One query searches the hb_file_activity surface for the creation of gdrv.sys in common file paths. This vulnerable driver allows an attacker to gain kernel-level access and terminate antivirus or EDR processes that would otherwise block the encryption. Identifying this drop is a critical first step in flagging a high-severity intrusion. Simultaneously, another query identifies the execution of binaries named after the local domain on the hb_process_activity surface, typically with a _win64.exe suffix. This pattern is specific to the ransomware's deployment phase and helps filter out generic malware or automated tools. Following the early leads, the hunt searches for anti-recovery behaviors. It looks for rare commands involving reagentc /disable to turn off recovery environments and cipher /w: to wipe free space on the hb_process_activity surface. By baselining these commands across the fleet, the hunt flags instances where an attacker attempts to disable recovery partitions or wipe free space on only a few systems. This ensures that scheduled administrative tasks on servers do not trigger false positives. The final stage seeks evidence of successful impact on the hb_file_activity surface. It searches for artifacts like the .locked extension and the presence of the restore_files.txt ransom note. This correlates the preceding evasion and recovery inhibition with the actual encryption event, providing a complete attack timeline for responders. ### What the hunt cannot see This hunt lacks visibility into the specific instructions within diskpart scripts. While it flags the execution of diskpart, the exact partition changes remain hidden without the raw script content. Furthermore, if an adversary successfully kills the endpoint agent before it reports the driver drop or launcher execution, the hunt cannot see the compromise. There is also a risk of visibility loss if the attacker corrects typos in log paths which currently allow detection of event log clearing. ### How to run it This hunt is an open-source hunt.md playbook. It imports directly into Huntbase or any runtime that supports the hunt.md specification. Analysts should review the correlated results to verify the attack timeline before isolating hosts or initiating recovery procedures.
