# ClickFix DLL Sideloading and Infostealer Injection Hunt

### Why Now Elastic Security Labs recently detailed the ClickFix campaign in their article, "From 88 lines to 1: Detecting DLL hijacking with Elastic Defend." The campaign combines search-order hijacking with evasion techniques like process hollowing and security-blinding drivers. While a single detection rule might catch the final payload, understanding and hunting for the entire execution chain is necessary to confirm the scope of an intrusion. ### Hypothesis An adversary has deployed a ClickFix script to sideload a malicious library into a signed Microsoft binary, followed by hollowing a system process to run an infostealer and using a BYOVD driver to blind endpoint security. ### How the Hunt Flows The hunt begins with a scoping phase using the hb_software_inventory surface. We identify hosts that possess software frequently targeted for sideloading, such as Microsoft Visual Basic utilities or various upgrade tools. This step does not confirm an infection but narrows our search to systems where the attack surface is present. Following scoping, the hunt enters a parallel lead detection phase. The first query monitors the hb_module_activity surface for the library mscoree.dll. An adversary loads this library from paths other than the standard Windows System32 directory. We specifically filter for modules seen on three or fewer hosts to isolate rare activity. Simultaneously, the second query searches the hb_script_activity surface for PowerShell script blocks that contain hexadecimal flags like 0x8000004. The adversary uses these flags to create suspended processes, which is a prerequisite for hollowing. An analyst triages these leads by host. If a system shows both an unusual library load and the suspicious PowerShell staging content, the findings indicate a coordinated ClickFix staging event rather than a routine administrative task. Once an analyst confirms a staging lead, the hunt pivots to detect the impact of the intrusion. We query the hb_process_activity surface for the ServiceModelReg.exe process. The adversary hollows this process, leaving the binary reported as missing from disk. This on_disk equals zero state is a high-confidence indicator that the Remus infostealer is running in memory. In parallel, the hunt scans the hb_file_activity surface for the creation of .sys driver files in user-writable directories like Temp or Users. The adversary drops these files as vulnerable drivers to blind endpoint security products. The final triage step synthesizes the entire chain. An analyst reviews the evidence from the staging leads through to the active injection and driver deployment. This holistic view allows for a definitive verdict on the intrusion. ### Blind Spots This hunt has two primary blind spots. First, the detection of process hollowing in ServiceModelReg.exe relies on a snapshot of the process state. If the infostealer is ephemeral and terminates between collection intervals, the hunt misses the hollowed process. Second, the script activity query depends on PowerShell Script Block Logging. If IT Operations has not enabled this logging, the hunt cannot inspect the de-obfuscated content of the ClickFix scripts, which may hide the staging flags. ### How to Run it Practitioners run this hunt as an open hunt.md playbook. You can import this file into Huntbase or any hunt.md-aware runtime to execute the queries against your telemetry. The playbook includes parameters for lookback_days and specific target_dlls to allow for tuning based on your environmental baselines.
