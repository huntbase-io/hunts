# Axis RCE and Confluence Attachment Harvesting Hunt

### Why this huntaAdversaries currently exploit a critical remote code execution vulnerability in Apache Axis (CVE-2026-90436) to target Atlassian Confluence Data Center. Rapid7 reported this activity in their Rapid7 (https://www.rapid7.com/blog/post/etr-rapid7-detected-exploitation-of-cve-2026-90436-against-atlassian-confluence-data-center-n-able-n-central-also-exploited) analysis, noting that attackers use the vulnerability to gain initial access and then move to harvest sensitive data. This hunt provides a structured approach to identifying both the initial SOAP exploit and the subsequent post-exploitation behaviors that signify a successful breach.aa### The HypothesisaAn adversary exploits the Apache Axis SOAP vulnerability in Confluence to execute shell commands. Once they establish a foothold, they use automated scripts to discover and harvest credentials or sensitive documents from the Confluence attachment store, often exfiltrating this data through public tunneling or webhook services.aa### How the Hunt FlowsaThe hunt uses a gated execution model to reduce false positives and focus analyst attention on high-confidence leads. The process starts at the HTTP surface, searching for specific POST requests to the Axis SOAP endpoint that resulted in an Internal Server Error (500). This behavior matches the observed exploitation pattern where the server fails to process the malicious SOAP payload but executes the embedded commands.aaIf the scoping query identifies suspicious hosts, the hunt fans out into three parallel investigations. The first check monitors the process surface for Java spawning bash, sh, or curl. Because the Confluence service account rarely executes shell utilities directly from the Java process, this signal provides strong evidence of remote code execution. The second phase examines file activity for rare access to the Confluence attachment directory. Attackers often target the /attachments/v4/ path to find sensitive corporate data. By baselining normal file access across the fleet, the hunt highlights scripts or rare processes that interact with these files.aaThe final corroboration phase looks for DNS resolutions of tunneling services like Pinggy and Cloudflare Tunnels. Adversaries use these services to bypass firewall restrictions and establish command-and-control channels without requiring incoming connections. An analyst then triages the collected evidence from all four surfaces—HTTP, process, file, and DNS—to reach a final verdict. If the results confirm an intrusion, the hunt playbook provides instructions for server isolation and forensic collection.aa### What this Hunt Cannot SeeaThe effectiveness of the initial lead depends on the retention of HTTP access logs with response codes. If the environment lacks this telemetry, the hunt may fail to identify the entry point. Additionally, if an adversary uses a custom, low-prevalence tunneling tool not included in the provided parameters, the DNS query will not flag the exfiltration. The hunt also assumes the adversary uses the default Confluence attachment path; custom configurations may require manual adjustment of the file search parameters.aa### How to Run itaThis hunt is packaged as an open hunt.md playbook. You can import it into Huntbase or any hunt.md-aware runtime. This format allows you to run the queries directly against your telemetry and manage the multi-phase flow through a single interface.
