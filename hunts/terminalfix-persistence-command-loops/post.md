# Hunting TerminalFix Redundant Persistence and PowerShell Command Loops

This hunt is based on the Microsoft report, [TerminalFix campaign deploys a reverse tunnel through multistage intrusion](https://www.microsoft.com/en-us/security/blog/2026/08/28/terminalfix-campaign-deploys-reverse-tunnel-through-multistage-intrusion/). The campaign is characterized by its use of multistage intrusions that culminate in the deployment of reverse tunnels, but the critical middle phase involves establishing a reliable, asynchronous method for executing attacker commands. Our hunt focuses on this specific 'beachhead' state where the adversary has secured a foothold but has not yet fully pivoted into internal reconnaissance.  The hypothesis for this hunt is that adversaries maintain access via redundant persistence in ProgramData subdirectories while using a PowerShell-based file-watch loop to execute commands asynchronously. This design allows the attacker to execute arbitrary code simply by writing to a local text file, effectively bypassing traditional direct command-and-control traffic patterns during the execution phase.  The hunt flow begins with a scoping phase using `hb_process_activity`. We look for any execution occurring from non-standard subdirectories within ProgramData. While many legitimate applications use ProgramData, the campaign specifically stages its components here to masquerade as system services or content servers. This initial step provides a wide list of candidate hosts for deeper inspection.  Next, the hunt pivots into parallel evidence gathering across three distinct surfaces. We examine `hb_registry_activity` for the creation of Run keys containing the `LockScreenContentServer` identifier, and concurrently query `hb_scheduled_job` to identify rare tasks that execute from the same ProgramData paths. Using prevalence analysis on scheduled tasks helps distinguish the adversary's persistence from standard updater tasks that might also reside in ProgramData.  The third parallel branch investigates `hb_script_activity` for specific PowerShell behaviors. We look for script blocks that implement `FileSystemWatcher` or infinite `while` loops that poll for file content using `Get-Content` followed by `Invoke-Expression`. This pattern is the signature of the campaign's command-execution loop. Finding this behavior on a host already flagged for suspicious ProgramData execution significantly increases the confidence of the finding.  A primary blind spot for this hunt is the requirement for PowerShell Script Block Logging (v5+). Without this telemetry, we can identify the presence of a polling loop, but we cannot see the specific commands being executed via `Invoke-Expression`. Additionally, if your environment only provides registry snapshots rather than activity logs, you may see the persistence keys without the temporal context of when they were established.  To run this hunt, you can import the provided `hunt.md` playbook into Huntbase or any hunt.md-aware runtime. It uses a structured triage agent to correlate the findings across the registry, task, and script surfaces, providing a prioritized list of hosts for forensic review and isolation. This behavioral correlation is what makes this a hunt; it evaluates the state of the host across multiple telemetry streams to find a stealthy, persistent presence that single-signal detections often miss.
