# Hunting KeyDrift Framework Injection in Cisco SD-WAN Controllers

### Why now 1000a Cisco Talos recently published a detailed analysis of UAT-11473 activity in their article, [Inside KeyDrift: Analyzing historical UAT-11473 activity on Cisco SD-WAN](https://blog.talosintelligence.com/uat-11473-keydrift/). This actor uses the KeyDrift framework to compromise Cisco SD-WAN controllers, specifically targeting the vdaemon process to intercept sensitive control-plane keying material. Because the framework relies on memory-resident modules and transient configuration files, standard signature-based detection often misses the infection. 1000a ### The hypothesis 1000a An adversary uses the ptrace system call to inject malicious modules into the vdaemon process on a Cisco SD-WAN controller. This injection enables the adversary to hook internal functions and exfiltrate control-plane keys through encrypted staging files in temporary directories. 1000a ### How the hunt flows 1000a The hunt begins by scanning the hb_file_activity surface for high-fidelity indicators. It searches for specific staging and configuration files, such as /var/tmp/vdaemon.bin and /tmp/system-vdaemon, in temporary directories. These files serve as encrypted repositories for stolen data. Because KeyDrift frequently deletes these files after use, their presence acts as a high-priority trigger for the next phase. 1000a If lead indicators are present, an agent assesses the findings to decide if the activity matches the KeyDrift framework staging behavior. This gate ensures the hunt only proceeds to expensive behavioral analysis when evidence warrants it. If the agent confirms the files are suspicious, the hunt moves into a deep investigation phase. 1000a The investigation phase runs two queries in parallel to capture runtime behavior. The first query monitors the hb_linux_audit surface for rare processes invoking the ptrace syscall. While ptrace is a legitimate tool for debugging, its use on production SD-WAN controllers is unusual. The hunt baselines this activity across the fleet to highlight outliers that may be acting as injectors. 1000a Simultaneously, the hunt examines the hb_module_activity surface to inspect the memory maps of the vdaemon process. It lists all loaded shared objects and filters for rare modules that appear on only a few hosts. This allows an analyst to identify the PolyFlame and LittleFilch modules—often named libdssl.so or libcommon.so—even if the adversary successfully hides the initial injection process. 1000a In the final triage phase, an agent correlates the file activity, ptrace invocations, and rare module findings to reach a high-confidence verdict. A host showing a rare injector process and unauthorized shared objects in vdaemon memory receives a malicious verdict. This workflow provides the specific evidence needed to justify immediate isolation and forensic imaging. 1000a ### What the hunt cannot see 1000a KeyDrift is designed for stealth. It deletes configuration files immediately after reading them, meaning the initial file-based leads are highly transient. If an analyst runs the hunt after the actor cleans up the filesystem, these indicators will not appear. Additionally, if Linux syscall auditing is disabled for ptrace, the mechanism of injection becomes invisible to the telemetry. In such scenarios, the hunt must rely entirely on memory-resident module snapshots. 1000a ### How to run it 1000a This hunt is provided as an open hunt.md playbook. You can import it directly into Huntbase or any hunt.md-aware runtime to automate the multi-stage logic and gating. It is designed for use against Cisco Catalyst SD-WAN controllers (vSmart, vManage, and vBond) where the vdaemon process is active. Focus initially on internet-exposed controllers to maximize efficiency.
