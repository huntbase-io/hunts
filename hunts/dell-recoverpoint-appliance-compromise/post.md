# Hunting for Dell RecoverPoint Exploitation and SLAYSTYLE Persistence

Recent reporting from Google Cloud on UNC6201 (https://cloud.google.com/blog/topics/threat-intelligence/unc6201-exploiting-dell-recoverpoint-zero-day) details the exploitation of a zero-day vulnerability in Dell RecoverPoint for VMs. The vulnerability, tracked as CVE-2026-22769, involves hardcoded credentials within the Tomcat Manager interface, which allows an adversary to deploy malicious WAR files and establish deep persistence on the appliance. The hypothesis for this hunt assumes that an adversary is actively using these credentials to deploy the SLAYSTYLE web shell and subsequently modifying appliance-specific boot scripts, such as convert_hosts.sh, to ensure their presence survives a reboot. This is particularly dangerous because these appliances often sit with elevated privileges in the virtual environment. The hunt begins by identifying the Dell RecoverPoint appliances within your environment. Using software inventory data, we filter for relevant packages and hostnames to ensure the subsequent queries are focused on the correct targets and do not generate excessive noise from unrelated web servers. Next, the flow moves to the HTTP surface. We look for PUT requests directed at Tomcat Manager deployment endpoints. Successful exploitation in this campaign often involves the use of the admin account or other hardcoded users. While PUT requests to these endpoints can be part of legitimate maintenance, seeing them on an appliance that is not currently being updated is a primary indicator of initial access. The third phase involves a parallel check across file and script telemetry. We look for the creation of rare WAR files in Tomcat webapp or cache directories. Simultaneously, we examine script execution logs for specific Java logic, such as Runtime.getRuntime() calls, which are characteristic of the SLAYSTYLE web shell command execution mechanism. Finally, the hunt checks for persistence via boot script tampering. The UNC6201 group has been observed modifying specific shell scripts like convert_hosts.sh and rc.local. This step is high-confidence; these files are critical to the appliance and should rarely be modified outside of official patch cycles. There are significant blind spots to consider. Many management appliances are not enrolled in EDR, meaning file and script telemetry might be entirely absent. Furthermore, if the HTTP traffic is encrypted and not terminated at a point where the hunt platform can see the URL paths, the initial access attempts will be invisible. This hunt is provided as a hunt.md playbook. It is designed to be imported into Huntbase or any other hunt.md-aware runtime to automate the collection and correlation of these diverse telemetry points.
