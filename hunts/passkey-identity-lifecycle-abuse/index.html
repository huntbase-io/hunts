Passkey-Themed Phishing and Identity Lifecycle Abuse

High severity TLP:CLEAR Research by Huntress Published 15 Oct 2026

Hypothesis

An attacker uses social engineering lures themed around passkey enrollment to trick users into authorizing a device-code login flow, subsequently registering unauthorized authenticators and establishing persistence via cloud application grants or unapproved browser extensions.

Brief

Why Now

Passkeys represent a significant hurdle for attackers, but the security of the authenticator does not solve the security of the identity lifecycle. As detailed in the Huntress article Passkeys Raise the Bar. Here’s Where Attackers Can Still Get In., adversaries are already pivoting to exploit the moments when users enroll or recover their credentials. This hunt provides a structured way to find those pivots before an attacker establishes permanent residency in your environment.

How the Hunt Flows

The hunt starts by scoping the environment for successful logins using the Device Code flow. While this protocol is necessary for certain headless or IoT devices, it is rare in standard business operations and is a primary vector for session hijacking in campaigns like EvilTokens. The first query isolates these events to create a list of high-risk users and hosts.

Next, the hunt gathers evidence from the identity lifecycle. It looks for MFA enrollment changes, credential resets, or recovery updates that occur shortly after a Device Code login. By stacking authentication protocols, the hunt also identifies users whose sign-in patterns have shifted significantly from their baseline. An automated agent or analyst then triages these findings to determine if a specific user likely fell for a social engineering lure.

For users marked as high-risk, the hunt pivots to investigate post-authentication persistence. It audits cloud API activity for new inbox rules, automated forwarding, or OAuth application consents that grant external access. Simultaneously, it inspects the software inventory on the user's host to find unapproved browser extensions. These extensions can be used to intercept sessions or even tamper with WebAuthn responses in real-time.

Finally, the hunt correlates the initial identity signal with the technical evidence of persistence. Connecting an unusual login protocol to a security modification and a subsequent cloud grant provides a high-confidence narrative of compromise that individual detection rules often miss.

What the Hunt Cannot See

This hunt relies on audit logs and software inventory, which introduces two specific blind spots. First, if an attacker established persistence more than 90 days ago, those events may fall outside the retention window of the cloud API activity logs. Second, while the hunt identifies installed browser extensions, it cannot see in-memory browser hooks injected via other processes that might be used for advanced session tampering.

  1. Query, scoping

    Identify device-code authentication users

    Identify users and hosts that use the Device Code flow, which is a primary vector for session hijacking in passkey-themed phishing campaigns.

    sql, reads hb_auth_signin
    SELECT actor_user_name, device_hostname, src_endpoint_ip, auth_protocol, timeFROM hb_auth_signinWHERE (LOWER(auth_protocol) LIKE '%device%code%' OR LOWER(event_type) LIKE '%device%code%')  AND status_id = 1  AND time >= datetime('now', '-{{lookback_days}} days')

    What a hit looks like. Rows identify users who successfully authorized a device code flow. In most enterprises, this flow should be rare.

  2. Query, triage

    Recent MFA enrollment and recovery changes

    Detect when a user adds a new authenticator or resets credentials, which often follows a hijacked session.

    sql, reads hb_account_change
    SELECT user_name, activity_name, actor_user_name, device_hostname, timeFROM hb_account_changeWHERE activity_id IN (3, 4, 99)  AND (LOWER(activity_name) LIKE '%mfa%' OR LOWER(activity_name) LIKE '%authenticator%' OR LOWER(activity_name) LIKE '%credential%')  AND time >= datetime('now', '-{{lookback_days}} days')

    What a hit looks like. Modifications to account security settings shortly after a login event. Silent means no such changes were recorded.

  3. Query, baseline

    Rare authentication protocol usage

    Stack sign-ins by protocol and user to isolate anomalous shifts to phishing-prone flows like DeviceCode.

    sql, reads hb_auth_signin
    SELECT actor_user_name, auth_protocol, src_endpoint_ip, COUNT(*) as count, MIN(time) as first_seenFROM hb_auth_signinWHERE status_id = 1  AND time >= datetime('now', '-{{lookback_days}} days')GROUP BY actor_user_name, auth_protocol, src_endpoint_ipHAVING count < 5

    What a hit looks like. A list of users whose login protocol usage is anomalous compared to their historical patterns.

  4. Agent triage

    Early stage risk triage

    Weigh the initial authentication protocols against account changes to find likely social engineering successes.

  5. Query, enrichment

    Cloud persistence via API

    Find post-compromise activity such as new inbox rules or OAuth application consents.

    sql, reads hb_cloud_api_activity
    SELECT actor_user_name, api_operation, resource_name, status, timeFROM hb_cloud_api_activityWHERE (LOWER(api_operation) LIKE '%inboxrule%' OR LOWER(api_operation) LIKE '%forwarding%' OR LOWER(api_operation) LIKE '%approle%' OR LOWER(api_operation) LIKE '%consent%' OR LOWER(api_operation) LIKE '%add-mailbox%')  AND status = 'success'  AND time >= datetime('now', '-{{lookback_days}} days')

    What a hit looks like. Success events for operations that grant external access or automate mailbox exfiltration.

  6. Query, detection candidate

    Hunt unapproved browser extensions

    Identify browser extensions that might indicate session interception or WebAuthn tampering, focusing on hosts identified in the scoping step.

    sql, reads hb_software_inventory
    SELECT device_hostname, package_name, package_uid, package_version, vendor_nameFROM hb_software_inventoryWHERE package_type = 'extension'  AND ('{{approved_extension_ids}}' = '' OR instr(',' || '{{approved_extension_ids}}' || ',', ',' || package_uid || ',') = 0)  AND ('{{scope_hosts}}' = '' OR instr(',' || '{{scope_hosts}}' || ',', ',' || device_hostname || ',') > 0)

    What a hit looks like. A list of extensions on scoped hosts that are not in the enterprise allow-list.

  7. Agent triage

    Correlate full identity-to-endpoint chain

    Integrate the early identity signals with the technical persistence mechanisms to verify the full attack lifecycle.

  8. Decision

    Route on verdict

    Direct the response based on the agent's full-chain correlation.

  9. Response action

    Contain identity compromise

    Immediately terminate the attacker's access by revoking sessions and removing malicious authenticators.

  10. Analyst task

    Manual cleanup verification

    Verify that all persistence mechanisms, including inbox rules and browser extensions, have been fully remediated.

  11. Analyst task

    Hunt close out

    Document findings and lessons for future training.

# Passkey-Themed Phishing and Identity Lifecycle Abuse

This phased hunt targets the abuse of identity lifecycles during transition to phishing-resistant authentication. The first phase identifies users who use rare alternative authentication flows, such as the Device Code flow seen in the EvilTokens campaign, and correlates this with immediate MFA enrollment changes. The second phase follows these high-risk identities to find post-authentication persistence mechanisms, including malicious inbox rules and unauthorized browser extensions capable of tampering with WebAuthn responses. The hunt concludes by connecting the initial social engineering signal to the technical persistence evidence.
