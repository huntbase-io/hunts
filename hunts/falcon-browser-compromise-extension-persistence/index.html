Falcon Browser Compromise and Extension Persistence

An adversary has established persistence via a malicious browser extension and is using it to communicate with a C2 framework via specific /config/ path structures and POST requests.

Brief

Why Now

Unit 42 recently published research titled The XG Files: Falcon C2 Flying Under The (Browser) Radar, detailing a sophisticated campaign targeting government and defense sectors. The adversary uses malicious browser extensions to maintain persistent access and tunnel command-and-control (C2) traffic through standard web protocols. Traditional host-based detection often misses these extensions because they reside within the user’s browser profile and mimic legitimate analytics traffic.

How the Hunt Flows

The first phase establishes a behavioral lead by querying HTTP activity. The hunt searches for rare POST requests directed at /config/ paths or specific C2 domains like fonts.tarotfree101.top or robot.avbliud.com. It also looks for the presence of the hm_lvt_ query parameter, which the framework uses to mimic Baidu tracking. By focusing on the rarity of these requests across the fleet, an analyst isolates suspicious communication before checking for local artifacts. This behavioral lead is stronger than searching for a single static IP address because it captures the framework tasking logic. Once the hunt identifies a lead, an analyst or automated agent assesses the network traffic against known Falcon indicators. This assessment is a gate. If the traffic aligns with the reported framework behavior, the hunt opens the second phase to gather more expensive endpoint telemetry. This prevents running high-impact file searches across every host in the environment. The third phase runs in parallel to find the local persistence mechanism. One query checks the software inventory for the specific Falcon extension ID mbidcmlcbgbphpoacojjbmfpohcimjji or names containing falcon. A second query monitors file activity in browser profile directories, looking for core JavaScript files like analytics-core.js or background.js being touched within extension folders. This dual-check identifies both registered extensions and those sideloaded manually. Finally, the hunt correlates the network, inventory, and file findings. An analyst reviews the combined evidence to determine if the extension activity matches the unauthorized network communication. This link between the /config/ POST traffic and the specific user profile directory provides a high-confidence verdict. If confirmed, the hunt provides instructions to isolate the host and remove the malicious files.

What the Hunt Cannot See

Visibility depends on the ability to inspect HTTP metadata. If the adversary uses encrypted WebSockets or custom TLS without a proxy or inspection point, the /config/ URI paths remain hidden. Additionally, this hunt relies on a 14-day lookback. If the adversary established persistence and remained dormant before this window, the initial installation and configuration activity will not appear in the results.

How to Run the Hunt

This hunt is an open hunt.md playbook. This format allows you to import the logic directly into Huntbase or any hunt.md-aware runtime. It uses a gated logic structure to ensure expensive file-system searches only run on hosts already showing suspicious network behavior, reducing the overall performance impact on the fleet.

# Falcon Browser Compromise and Extension Persistence

This hunt identifies the Falcon (XG) browser-based C2 framework by searching for its characteristic /config/ URL patterns and rare POST traffic using Baidu-mimicking tracking markers. When a behavioral match is found, the hunt gates more expensive inventory and file telemetry searches to locate the specific malicious Chrome extension and its core JavaScript components within browser profile directories. This gated approach prioritizes robust behavioral indicators over static extension IDs while ensuring file-level corroboration within the user's extension folder.

## http-config-path-lead
<!-- Identify Falcon Behavioral HTTP Activity -->
Establish a behavioral lead by finding rare POST requests or Baidu-mimicking query parameters directed at /config/ paths or known C2 domains.

```sqlite target=web role=detection-candidate params=(c2_domains=c2_domains, lookback_days=lookback_days)
~~~yaml
baseline:
  compare: first_seen
  window: '{{lookback_days}}d'
expected: Rare HTTP POSTs to /config/ paths or query parameters mimicking Baidu analytics.
  Silence indicates no active framework-style communication was captured during the
  window.
prevalence:
  by: device_hostname
  key:
  - url_hostname
  - url_path
  rare_below: 5
reads:
- device_hostname
- url_hostname
- url_path
- http_method
- url_query
- time
silence: not_evidence_of_absence
source: hb_http_activity
verified: dry-run
verified_at: '2026-11-12'
~~~
SELECT device_hostname, url_hostname, url_path, http_method, url_query, COUNT(*) AS requests, MIN(time) AS first_seen FROM hb_http_activity WHERE (LOWER(url_path) LIKE '/config/%' OR instr(',' || '{{c2_domains}}' || ',', ',' || LOWER(url_hostname) || ',') > 0) AND (LOWER(http_method) = 'post' OR LOWER(url_query) LIKE '%hm_lvt_%') AND time >= datetime('now', '-{{lookback_days}} days') GROUP BY 1, 2, 3, 4, 5 HAVING COUNT(DISTINCT device_hostname) <= 5 ORDER BY requests DESC
```
