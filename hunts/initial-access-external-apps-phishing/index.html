Initial Access via External Applications and Phishing

An adversary has gained initial access by either exploiting a critical vulnerability in a public-facing application or by use of stolen credentials from a phishing campaign, resulting in anomalous application crashes or high-risk authentication events on perimeter assets.

Brief

Why this hunt

The research article When confusion reigns, trusted vendors must guide their SMB customers describes how SMBs are targeted as initial entry points for broader supply-chain attacks. These organizations often provide a path into larger enterprise environments. This hunt addresses the two most common vectors for this initial breach: the exploitation of public-facing applications and the use of stolen credentials.

How the hunt flows

The first phase uses the hb_vulnerability_finding surface to scope the environment. We search for devices with active vulnerabilities that have a severity rating of critical. By identifying these assets first, we create a high-priority list of hosts that are most likely to be targeted for inbound exploitation.

The second phase performs a parallel fan-out across two different behavioral surfaces. On the hb_application_error surface, the hunt searches for rare crashes in web-facing services like IIS, Apache, and Nginx. We specifically look for process faults that occur on fewer than three hosts, as these are strong indicators of memory corruption or failed exploit attempts. Simultaneously, on the hb_auth_signin surface, the hunt identifies authentication events flagged for risk by the identity provider, including brute-force indicators and MFA failures.

The third phase involves a triage agent that correlates these disparate signals. The agent reviews the vulnerability status of the scoped hosts and checks for corresponding crashes or identity risks. This allows the hunt to find "living off the land" access where an adversary uses an exploit or stolen credentials that might not trigger a standard malware detection.

The final phase provides a structured decision path for the analyst. If the correlation suggests a successful breach, the hunt guides the user through isolating the host and revoking user sessions. This transition from detection to containment ensures that a confirmed beachhead is neutralized before the adversary can move laterally into the network.

What the hunt cannot see

This hunt has two main blind spots. First, it depends on standard OS error logging for application crashes. If an adversary exploits a legacy or proprietary application that does not report its errors to the system service, the hunt will not detect those exploitation attempts. Second, if the identity provider does not provide granular logging for the specific MFA methods used during a login, the hunt cannot distinguish between a legitimate session and an MFA bypass.

Steps

  1. Identify vulnerable perimeter assets

    Query · scoping

    Identify devices with critical active vulnerabilities that could serve as the initial entry point for an adversary.

    reads hb_vulnerability_findingsql
    SELECT device_uid, resource_uid AS device_hostname, cve_uid, severity, cvss_score FROM hb_vulnerability_finding WHERE severity_id >= 4 AND status = 'active' AND resource_type = 'device' ORDER BY cvss_score DESC

    What a hit looks like. A list of hostnames with critical CVEs. Silence indicates no active critical vulnerabilities are reported in the scanner inventory.

  2. Rare application crashes on vulnerable hosts

    Query · baseline

    Find rare application failures in web services that could indicate memory corruption or exploit attempts.

    reads hb_application_errorsql
    SELECT device_hostname, app_name, exception_code, COUNT(DISTINCT device_hostname) AS host_count, MIN(time) AS first_seen FROM hb_application_error WHERE (LOWER(app_name) LIKE '%w3wp%' OR LOWER(app_name) LIKE '%httpd%' OR LOWER(app_name) LIKE '%nginx%' OR LOWER(app_name) LIKE '%sql%') AND ('{{scope_hosts}}' = '' OR instr(',' || '{{scope_hosts}}' || ',', ',' || device_hostname || ',') > 0) AND time >= datetime('now', '-{{lookback_days}} days') GROUP BY app_name, exception_code HAVING host_count < 3 ORDER BY host_count ASC

    What a hit looks like. A crash in a web server or database process occurring on fewer than 3 hosts. Silence suggests no rare fatal application errors occurred.

  3. High-risk authentication and credential abuse

    Query · detection candidate

    Identify sign-ins flagged by providers as high-risk or indicating brute-force/MFA exhaustion.

    reads hb_auth_signinsql
    SELECT dst_endpoint_hostname AS device_hostname, actor_user_name, src_endpoint_ip, risk_state, status_code, event_type, time FROM hb_auth_signin WHERE (risk_state != 'none' OR status_code IN ('50126', '50053', '500121')) AND ('{{scope_hosts}}' = '' OR instr(',' || '{{scope_hosts}}' || ',', ',' || dst_endpoint_hostname || ',') > 0) AND time >= datetime('now', '-{{lookback_days}} days')

    What a hit looks like. Successful or failed sign-ins with 'atRisk' states or codes for brute force/MFA failure. Silence indicates no high-risk identity alerts.

  4. Triage initial access signals

    Agent triage

    Determine if the identified vulnerabilities, application crashes, and identity risks together indicate a successful perimeter breach.

  5. Route based on intrusion verdict

    Decision

    Direct the hunt to containment if successful initial access is confirmed.

  6. Isolate the compromised host

    Response action

    Contain the threat and prevent lateral movement from the beachhead.

  7. Forensic lead analysis

    Analyst task

    Analyze the crash and authentication evidence to confirm the root cause.

  8. Close the gaps

    Analyst task

    Patch vulnerabilities and improve resilience based on the hunt findings.

# Initial Access via External Applications and Phishing

Following research that suggests SMBs are frequently targeted as supply-chain beachheads, this hunt identifies assets with known critical vulnerabilities. The hunt then launches parallel queries to find rare application faults in web services and high-risk authentication flags from identity providers. Finally, an agent correlates these disparate signals to determine if a perimeter breach has occurred, and an analyst reviews the evidence to confirm the intrusion vector.

## vulnerable-device-scoping
<!-- Identify vulnerable perimeter assets -->
Identify devices with critical active vulnerabilities that could serve as the initial entry point for an adversary.

```sqlite target=endpoint role=scoping
~~~yaml
expected: A list of hostnames with critical CVEs. Silence indicates no active critical
  vulnerabilities are reported in the scanner inventory.
reads:
- device_uid
- resource_uid
- cve_uid
- severity
- cvss_score
- severity_id
- status
- resource_type
silence: not_evidence_of_absence
source: hb_vulnerability_finding
verified: dry-run
verified_at: '2026-11-03'
~~~
SELECT device_uid, resource_uid AS device_hostname, cve_uid, severity, cvss_score FROM hb_vulnerability_finding WHERE severity_id >= 4 AND status = 'active' AND resource_type = 'device' ORDER BY cvss_score DESC
```

## rare-application-crashes
<!-- Rare application crashes on vulnerable hosts -->
Find rare application failures in web services that could indicate memory corruption or exploit attempts.

```sqlite target=endpoint role=baseline params=(lookback_days=lookback_days, scope_hosts=scope_hosts)
~~~yaml
baseline:
  compare: first_seen
  window: '{{lookback_days}}d'
expected: A crash in a web server or database process occurring on fewer than 3 hosts.
  Silence suggests no rare fatal application errors occurred.
prevalence:
  by: device_hostname
  key:
  - app_name
  - exception_code
  rare_below: 3
reads:
- device_hostname
- app_name
- exception_code
- time
silence: not_evidence_of_absence
source: hb_application_error
verified: dry-run
verified_at: '2026-11-03'
~~~
SELECT device_hostname, app_name, exception_code, COUNT(DISTINCT device_hostname) AS host_count, MIN(time) AS first_seen FROM hb_application_error WHERE (LOWER(app_name) LIKE '%w3wp%' OR LOWER(app_name) LIKE '%httpd%' OR LOWER(app_name) LIKE '%nginx%' OR LOWER(app_name) LIKE '%sql%') AND ('{{scope_hosts}}' = '' OR instr(',' || '{{scope_hosts}}' || ',', ',' || device_hostname || ',') > 0) AND time >= datetime('now', '-{{lookback_days}} days') GROUP BY app_name, exception_code HAVING host_count < 3 ORDER BY host_count ASC
```

## initial-access-triage
<!-- Triage initial access signals -->
```agent target=hunter

- vulnerable-device-scoping
- rare-application-crashes
- suspicious-identity-events
max_iterations: 4

  with any rare application crashes or high-risk authentication events on those same
  hosts. Decide if the timing and nature of these signals represent a successful intrusion.

  crashes or sign-in risks.

```

## intrusion-decision
<!-- Route based on intrusion verdict -->
if~: "the initial-access-triage verdict is malicious for at least one host" (confidence: high, judge=hunter)
then: → isolate-compromised-host
indeterminate: → incident-response-task
unavailable: → incident-response-task (blind_spot: no-identity-logging)
else: → remediation-task

## isolate-compromised-host
<!-- Isolate the compromised host -->
```action target=endpoint
~~~yaml
approval: required
~~~
Isolate the host identified as malicious and revoke all active sessions for the involved users in the identity provider (Entra ID/Okta).
```
→ incident-response-task

## incident-response-task
<!-- Forensic lead analysis -->
```manual target=analyst
Review the application errors and authentication logs. If an application crash was found, correlate with hb_http_activity to find the URI and source IP that triggered the fault. If auth risk was found, check for subsequent hb_process_activity or hb_file_activity that indicates hands-on-keyboard activity.
```
→ remediation-task

## remediation-task
<!-- Close the gaps -->
```manual target=analyst
Immediately patch the CVEs identified on any malicious or suspicious hosts. Review the conditional access policies for any accounts flagged for risk to ensure phishing-resistant MFA is required for perimeter access.
```
→ end
