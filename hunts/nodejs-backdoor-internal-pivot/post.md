# Hunting Node.js Implants and WinRM Pivots in IT Support Scams

Recent reporting by Microsoft in "Impersonating IT support: how threat actors turn a remote session into enterprise-wide access" (https://www.microsoft.com/en-us/security/blog/2026/09/02/impersonating-it-support-threat-actors-turn-remote-session-into-enterprise-wide-access/) describes a social engineering flow where attackers leverage Microsoft Teams and tools like Quick Assist to gain initial access. The technical pivot occurs when they deploy a portable Node.js runtime to establish a command-and-control channel. This hunt is designed to find that implant and the subsequent lateral movement attempts.

The hypothesis assumes that an intruder is maintaining command-and-control through a Node.js runtime located in a user-writable directory and is using WinRM for internal discovery or movement toward sensitive infrastructure. Because Node.js is a legitimate administrative and development tool, this hunt relies on behavioral correlation rather than simple indicators of compromise.

The hunt begins by scoping for suspicious file creations in the LocalAppData directory. Attackers often use non-standard extensions like .tmp, .cfg, or .dat for their loaders and configuration files. This stage identifies hosts that have recently received new, unusual files in user profiles that might serve as the staging area for the implant.

Next, we examine the execution of the Node.js runtime itself. We focus on instances where node.exe (or a binary with the original filename node.exe) is running from LocalAppData rather than standard Program Files paths. We then apply stack-counting to these paths across the environment. Legitimate developer tools and internal applications typically appear across many hosts, whereas a targeted implant will appear on a very small subset of the estate.

The third phase involves looking for active pivots originating from the flagged hosts. We examine outbound network connections on port 5985 (WinRM). We also inspect script telemetry for Active Directory Service Interfaces (ADSI) queries or WMI commands used to map the network or identify installed security software. These actions are highly characteristic of an operator-led intrusion.

There are two primary blind spots to consider. First, if script block logging is not enabled, the specific discovery commands issued by the attacker will be invisible, and the hunt must rely solely on process and network metadata. Second, if an attacker renames the Node.js binary and the endpoint security solution does not capture the original filename, a hunt based on the runtime's identity may fail to see the execution.

This hunt is provided as a hunt.md playbook. It can be imported into Huntbase or any environment that supports the hunt.md specification. By automating the correlation of these different surfaces, the hunt identifies the breach before the attacker successfully pivots to the domain controller or other critical infrastructure.
