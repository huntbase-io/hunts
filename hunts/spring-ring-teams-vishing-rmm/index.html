Spring Ring: Teams Support Impersonation and Initial Discovery

An adversary is impersonating internal IT support via external Microsoft Teams accounts to trick users into running remote support tools and conducting initial environment reconnaissance.

Brief

Why This Hunt Matters\n\nUnit 42 recently published an analysis of \"Spring Ring,\" an operation where adversaries leverage the inherent trust in Microsoft Teams to impersonate internal IT help desks. You can find their detailed reporting in Spring Ring: An Inside Look at Voice Phishing Campaigns in Microsoft Teams. Unlike traditional phishing, this campaign relies on vishing (voice phishing) within the Teams ecosystem to trick users into installing legitimate remote monitoring and management (RMM) tools. Once the attacker gains control via the RMM, they conduct rapid environment discovery.\n\n### The Hypothesis\n\nWe hypothesize that we can identify these campaigns by looking for the technical residue of the social engineering lure—specifically, endpoint DNS lookups to known attacker-controlled .onmicrosoft.com tenants—and linking them temporally to the execution of RMM tools and manual reconnaissance commands that are atypical for the specific host.\n\n### How the Hunt Flows\n\nThe hunt begins by scoping the environment to hosts that actively use Microsoft Teams. This ensures we are focusing our telemetry analysis on the relevant attack surface. We leverage software inventory data to identify these systems before moving into behavioral analysis.\n\nIn the second phase, we perform a parallel check across DNS and process activity. We look for resolutions of specific .onmicrosoft.com domains known to masquerade as IT support. Simultaneously, we baseline RMM tool usage across the fleet. The goal is to find \"rare\" executions—instances where QuickAssist, AnyDesk, or ScreenConnect appear on only one or two hosts, suggesting a user-initiated install rather than a centralized IT deployment.\n\nFinally, we pivot to process command-line data to look for interactive discovery. We look for patterns like 'net group /dom' or 'whoami /groups' occurring shortly after the RMM tool execution. By correlating the DNS lead, the rare binary, and the discovery commands within a short time window, we build a narrative of compromise that a single static alert would likely miss or mark as low-priority noise.\n\n### What This Hunt Cannot See\n\nThere are two primary blind spots to consider. First, if your organization routes endpoint DNS traffic through a proxy that does not preserve the source endpoint ID in logs, the initial lure phase will be invisible at the host level. Second, this hunt looks at the technical aftermath; without ingestion of M365 Unified Audit Logs, we cannot see the actual chat content or the specific external identity that initiated the Teams call.\n\n### How to Run It\n\nThis hunt is packaged as a hunt.md playbook. It is designed to be imported into Huntbase or any runtime that supports the hunt.md specification. It uses portable SQL logic to query software inventory, DNS logs, and process activity. Because this hunt relies on fleet-wide rarity and temporal correlation, it is best run as a proactive exercise rather than a real-time detection.

  1. Identify Hosts with Microsoft Teams

    Query · scoping

    Scope the hunt to systems where Microsoft Teams is likely installed to identify the primary attack surface for external vishing lures.

    reads hb_software_inventorysql
    SELECT DISTINCT device_hostname FROM hb_software_inventory WHERE (LOWER(package_name) LIKE '%microsoft teams%' OR LOWER(vendor_name) LIKE '%microsoft%') AND asset_scope = 'endpoint'

    What a hit looks like. A list of hostnames. None found means the software inventory is either incomplete or the organization does not use Microsoft software.

  2. DNS Lookups to Attacker Teams Tenants

    Query · detection candidate

    Identify potential vishing victims by finding lookups to the specific .onmicrosoft.com domains used for attacker identities.

    reads hb_dns_activitysql
    SELECT device_hostname, query_hostname, process_name, time FROM hb_dns_activity WHERE instr(',' || '{{attacker_tenants}}' || ',', ',' || LOWER(query_hostname) || ',') > 0 AND ('{{scope_hosts}}' = '' OR instr(',' || '{{scope_hosts}}' || ',', ',' || device_hostname || ',') > 0) AND time >= datetime('now', '-{{lookback_days}} days')

    What a hit looks like. A host resolving one of the report's domains. This confirms an external Teams connection attempt occurred.

  3. Rare RMM Tool Execution

    Query · baseline

    Identify hosts running remote support software that is rare across the fleet, suggesting execution prompted by a vishing lure rather than standard IT deployment.

    reads hb_process_activitysql
    SELECT LOWER(process_name) AS rmm_binary, COUNT(DISTINCT device_hostname) AS host_count, MIN(time) AS first_seen FROM hb_process_activity WHERE (instr(',' || '{{rmm_tools}}' || ',', ',' || LOWER(process_name) || ',') > 0 OR LOWER(process_name) LIKE '%quickassist%') AND ('{{scope_hosts}}' = '' OR instr(',' || '{{scope_hosts}}' || ',', ',' || device_hostname || ',') > 0) AND time >= datetime('now', '-{{lookback_days}} days') GROUP BY 1 HAVING host_count <= 3 ORDER BY host_count ASC

    What a hit looks like. A remote support binary running on very few hosts. Legitimate IT tools should have high host counts; vishing lures will stand out as rare outliers.

  4. Interactive Host and Domain Discovery

    Query · enrichment

    Detect the specific discovery commands observed in Spring Ring campaigns that suggest manual reconnaissance by an attacker after gaining remote access.

    reads hb_process_activitysql
    SELECT device_hostname, process_name, process_cmd_line, parent_process_name, time FROM hb_process_activity WHERE (LOWER(process_cmd_line) LIKE '%whoami /groups%' OR LOWER(process_cmd_line) LIKE '%net group /dom%' OR LOWER(process_cmd_line) LIKE '%net group "domain admins" /dom%') AND ('{{scope_hosts}}' = '' OR instr(',' || '{{scope_hosts}}' || ',', ',' || device_hostname || ',') > 0) AND time >= datetime('now', '-{{lookback_days}} days') ORDER BY time DESC

    What a hit looks like. Rows indicating manual reconnaissance. These are suspicious when following a DNS lookup to an attacker tenant or if launched by an RMM tool.

  5. Spring Ring Triage Agent

    Review all gathered telemetry to determine if a host was successfully lured into a vishing session and subsequent discovery activity.

  6. Route on Triage Verdict

  7. Isolate Compromised Host

    Response action

    Prevent immediate follow-on malware delivery or lateral movement after a confirmed vishing-led remote access session.

  8. Analyst Review and RAT Search

    Analyst task

    Review the interactive session and search for secondary payloads (PowerShell RATs) that often follow the discovery phase.

  9. Hunt Close-out

    Analyst task

# Spring Ring: Teams Support Impersonation and Initial Discovery

This hunt identifies the early stages of the 'Spring Ring' campaign by targeting the vishing lure phase and subsequent interactive control. It monitors for DNS lookups to known attacker-controlled .onmicrosoft.com tenants designed to mimic internal help desks. To corroborate, it identifies rare executions of remote monitoring and management (RMM) tools and stack-counts manual discovery commands (e.g., net group /dom) that follow the vishing lure, allowing an agent to correlate the lure with the technical aftermath.
