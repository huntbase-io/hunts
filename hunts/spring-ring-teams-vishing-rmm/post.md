# Spring Ring: Identifying MS Teams Vishing and RMM Discovery

### Why This Hunt Matters\n\nUnit 42 recently published an analysis of \"Spring Ring,\" an operation where adversaries leverage the inherent trust in Microsoft Teams to impersonate internal IT help desks. You can find their detailed reporting in [Spring Ring: An Inside Look at Voice Phishing Campaigns in Microsoft Teams](https://unit42.paloaltonetworks.com/spring-ring-voice-phishing-campaigns/). Unlike traditional phishing, this campaign relies on vishing (voice phishing) within the Teams ecosystem to trick users into installing legitimate remote monitoring and management (RMM) tools. Once the attacker gains control via the RMM, they conduct rapid environment discovery.\n\n### The Hypothesis\n\nWe hypothesize that we can identify these campaigns by looking for the technical residue of the social engineering lure—specifically, endpoint DNS lookups to known attacker-controlled .onmicrosoft.com tenants—and linking them temporally to the execution of RMM tools and manual reconnaissance commands that are atypical for the specific host.\n\n### How the Hunt Flows\n\nThe hunt begins by scoping the environment to hosts that actively use Microsoft Teams. This ensures we are focusing our telemetry analysis on the relevant attack surface. We leverage software inventory data to identify these systems before moving into behavioral analysis.\n\nIn the second phase, we perform a parallel check across DNS and process activity. We look for resolutions of specific .onmicrosoft.com domains known to masquerade as IT support. Simultaneously, we baseline RMM tool usage across the fleet. The goal is to find \"rare\" executions—instances where QuickAssist, AnyDesk, or ScreenConnect appear on only one or two hosts, suggesting a user-initiated install rather than a centralized IT deployment.\n\nFinally, we pivot to process command-line data to look for interactive discovery. We look for patterns like 'net group /dom' or 'whoami /groups' occurring shortly after the RMM tool execution. By correlating the DNS lead, the rare binary, and the discovery commands within a short time window, we build a narrative of compromise that a single static alert would likely miss or mark as low-priority noise.\n\n### What This Hunt Cannot See\n\nThere are two primary blind spots to consider. First, if your organization routes endpoint DNS traffic through a proxy that does not preserve the source endpoint ID in logs, the initial lure phase will be invisible at the host level. Second, this hunt looks at the technical aftermath; without ingestion of M365 Unified Audit Logs, we cannot see the actual chat content or the specific external identity that initiated the Teams call.\n\n### How to Run It\n\nThis hunt is packaged as a hunt.md playbook. It is designed to be imported into Huntbase or any runtime that supports the hunt.md specification. It uses portable SQL logic to query software inventory, DNS logs, and process activity. Because this hunt relies on fleet-wide rarity and temporal correlation, it is best run as a proactive exercise rather than a real-time detection.
