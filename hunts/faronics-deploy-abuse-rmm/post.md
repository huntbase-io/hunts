# Hunt for Faronics Deploy Abuse and ScreenConnect Persistence

### Why this hunt? The security team at Huntress recently documented a sophisticated attack chain in Daisy-Chaining Trust: Investigating Faronics Deploy Abuse (https://www.huntress.com/blog/faronics-deploy-abuse). The adversary uses the inherent trust in signed software management platforms to establish persistence. By delivering a legitimate Faronics agent via a phishing lure, they bypass traditional file-based detections and gain a foothold capable of executing remote PowerShell scripts. This hunt ensures that your management tools are not serving as a bridge for unauthorized access. ### Hypothesis The adversary delivers a signed Faronics Deploy installer masquerading as an Adobe product to an unsuspecting user. After the user executes the file, the adversary uses the platform's native script runner to deploy a ScreenConnect instance, securing persistent remote access through a secondary, trusted remote monitoring and management (RMM) tool. ### How the hunt flows The first phase uses the software inventory surface to identify every host running a Faronics Deploy package. This scoping step defines the target population for deeper behavioral analysis. We focus on workstations that have Faronics Deploy installed but are not typically managed by that specific RMM solution. The hunt then searches for indicators of the initial infection. We use the DNS activity surface to find resolutions for known phishing domains used for fingerprinting. Simultaneously, we inspect the process activity surface to identify Faronics-signed binaries that use Adobe or Reader file names to deceive users. Correlation between these network and endpoint events provides the first high-confidence signal of compromise. Next, we pivot to network telemetry to identify the specific attacker instance. We inspect HTTP activity for requests to the Faronics deployment domain. The analyst specifically looks for the ck parameter in the query string, which represents the unique customer identifier. Captured ck values allow us to cluster related activity and identify exactly which attacker-controlled environment the hosts joined. Finally, the hunt checks for the deployment of ScreenConnect. The process activity surface reveals installations or executions of the RMM tool. We confirm the unauthorized daisy-chain abuse if the parent process of the ScreenConnect installer originates from the Faronics agent or its associated script-running components. This links the initial phish to the final persistence mechanism. ### What the hunt cannot see This hunt cannot see the specific GitHub URLs used to download payloads because it does not ingest the content of the ScriptRunner.log file. The hunt identifies that the script runner executed, but an analyst must manually collect the logs for full forensic reconstruction of the remote commands. Additionally, the hunt lacks visibility into the browser-side fingerprinting data sent in POST bodies during the initial lure phase. We see the connection to the phishing infrastructure but not the internal attributes the attacker used to filter analysis environments. ### How to run it This hunt is an open hunt.md playbook. You can import it into Huntbase or any hunt.md-aware runtime to execute the queries across your fleet. Because this is a hunt, not a single detection, it allows you to correlate initial access, legitimate tool misuse, and persistence to distinguish an active intruder from authorized IT operations. Running this hunt helps you verify that your legitimate management agents are not being used against you.
