Power BI Phishing to ScreenConnect RMM

An adversary is using legitimate Microsoft Power BI dashboard links to bypass email security and deliver rogue ScreenConnect installers via staging domains.

Brief

Identifying the Power BI Phishing Chain

Recent research from Huntress titled "Phishing Campaign Abuses Microsoft Power BI to Deploy Rogue RMMs" (https://www.huntress.com/blog/screenconnect-power-bi) highlights a campaign where attackers bypass email security by hosting lures on trusted Microsoft infrastructure. The adversary uses legitimate Power BI dashboard links to redirect victims to external staging domains. These domains then serve rogue ScreenConnect installers to the victim. We published this hunt to help teams find these specific delivery steps before the attacker gains full control.

How the Hunt Flows

The hunt begins with the HTTP surface. The first query scopes the environment for any hosts visiting the Power BI view path or the known staging domains like dailylifeproject.site. Because the Power BI link is legitimate, we filter for specific path structures identified in the source research to reduce noise. This step provides a list of potentially compromised hosts that interacted with the lure.

Once we have a list of candidate hosts, the hunt runs two corroboration queries in parallel. One query monitors the file activity surface for writes of the ScreenConnect installer. It looks for the default client setup filename and a specific file hash in user-writable paths. The second query examines the DNS surface to stack-rank ScreenConnect relay subdomains across the fleet. We look for "rare" relays—instances seen on only a few hosts—which helps distinguish a rogue attacker-controlled tenant from a standard corporate deployment used by your IT department.

In the final phase, an analyst or automated agent triages the findings. A host that visited a staging domain and subsequently downloaded the RMM installer or connected to a rare relay receives a malicious verdict. This correlation allows us to move beyond simple detection and understand the context of the RMM usage. If the verdict is malicious, the hunt triggers an isolation action to prevent the adversary from executing further commands through the rogue RMM.

Blind Spots and Limitations

This hunt relies heavily on web and DNS telemetry. If your environment lacks HTTP activity logs or proxy data, you cannot see the initial redirect from Power BI to the staging domain. The hunt then depends entirely on finding the ScreenConnect file write or the DNS relay connection. Additionally, if the host uses DNS-over-HTTPS (DoH) to resolve staging domains or ScreenConnect relays, standard endpoint DNS monitoring will miss that traffic. In those cases, you must rely on process and file monitoring to catch the RMM installation after the fact.

Steps

  1. Query, scoping

    Visits to phishing staging infrastructure

    Identify hosts that visited the Power BI phishing link or the subsequent redirect staging domains.

    sql, reads hb_http_activity
    SELECT device_hostname, url_hostname, url_path, url_full, user_agent, timeFROM hb_http_activityWHERE (instr(',' || '{{staging_domains}}' || ',', ',' || LOWER(url_hostname) || ',') > 0 OR (LOWER(url_hostname) = 'app.powerbi.com' AND LOWER(url_path) LIKE '/view%'))  AND time >= datetime('now', '-{{lookback_days}} days')

    What a hit looks like. Rows showing specific hosts visiting staging domains. Silence suggests the lure was not clicked or filters blocked the traffic.

  2. Query, triage

    ScreenConnect installer file writes

    Find where ScreenConnect installers were written to disk, particularly in user downloads or temp directories.

    sql, reads hb_file_activity
    SELECT device_hostname, process_name, file_name, file_path, file_hash_sha256, timeFROM hb_file_activityWHERE activity_id = 1  AND (LOWER(file_name) LIKE 'screenconnect.clientsetup%' OR file_hash_sha256 = '5956f9afb3ba610c38b2cfda88dd15be98783963769a12020c93ce05e749b3c3')  AND ('{{scope_hosts}}' = '' OR instr(',' || '{{scope_hosts}}' || ',', ',' || device_hostname || ',') > 0)  AND time >= datetime('now', '-{{lookback_days}} days')

    What a hit looks like. Installer files written by browsers in writable paths. Silence means the payload was not saved to these monitored paths.

  3. Query, baseline

    Rare ScreenConnect relay subdomains

    Stack-count ScreenConnect relay subdomains to surface rogue or unapproved tenants across the fleet.

    sql, reads hb_dns_activity
    SELECT query_hostname, COUNT(DISTINCT device_hostname) AS host_count, MIN(time) AS first_seenFROM hb_dns_activityWHERE LOWER(query_hostname) LIKE '%.screenconnect.com'  AND ('{{scope_hosts}}' = '' OR instr(',' || '{{scope_hosts}}' || ',', ',' || device_hostname || ',') > 0)  AND time >= datetime('now', '-{{lookback_days}} days')GROUP BY query_hostnameHAVING host_count <= 3ORDER BY host_count ASC

    What a hit looks like. A ScreenConnect tenant seen on very few hosts. Corporate instances usually show high prevalence.

  4. Agent triage

    Triage RMM delivery chain

    Evaluate if the phishing visit and subsequent RMM indicators represent a successful compromise.

  5. Decision

    Route on verdict

    Decide the next course of action based on the agent's triage.

  6. Response action

    Isolate host

    Immediately contain the host to prevent command execution by the rogue RMM.

  7. Analyst task

    Analyst review

    Verify the findings and determine if the ScreenConnect instance is unapproved.

  8. Analyst task

# Power BI Phishing to ScreenConnect RMM

This hunt identifies the delivery chain of a campaign where trusted Microsoft domains (app.powerbi.com) are used to host phishing lures. It finds hosts that visited known staging domains or specific Power BI dashboard views, then corroborates this activity by looking for ScreenConnect installer writes and rare ScreenConnect relay DNS traffic that deviates from standard corporate usage.

<!-- Visits to phishing staging infrastructure -->


## rare-screenconnect-relays
<!-- Rare ScreenConnect relay subdomains -->

```sqlite target=endpoint role=baseline params=(lookback_days=lookback_days, scope_hosts=scope_hosts)
~~~yaml

  compare: first_seen
  window: '{{lookback_days}}d'

  show high prevalence.

  by: device_hostname

  rare_below: 3

- query_hostname
- device_hostname
- time
```
