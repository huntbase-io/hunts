VMware vCenter Directory Service Authentication Bypass Exposure

High severity TLP:CLEAR Research by Rapid7 Published 26 Nov 2026

Hypothesis

An unauthenticated attacker is attempting to exploit a critical authentication bypass in the VMware Directory Service (vmdir) by sending malicious LDAP or RPC traffic to exposed vCenter instances.

Brief

Why This Hunt?

0 0 Rapid7 recently detailed CVE-2026-123903, a critical authentication bypass in the VMware Directory Service (vmdir) at https://www.rapid7.com/blog/post/etr-cve-2026-123903-critical-vmware-directory-service-authentication-bypass-affects-vcenter. This vulnerability allows unauthenticated attackers to bypass security controls by sending crafted LDAP or RPC traffic. Because vCenter serves as the core of the virtualization fabric, exploitation provides an attacker with full control over the virtualization environment. We designed this hunt to identify exposed instances and look for signs of active exploitation. 0 0

How the Hunt Flows

0 0 The hunt begins by scoping the estate to identify vulnerable vCenter servers. The first step queries hb_vulnerability_finding for existing security scan results matching the targeted CVEs. Simultaneously, a query against hb_software_inventory enumerates all vCenter installations and their versions. This dual approach ensures we catch known vulnerable systems and those that scans might have missed. 0 0 The second phase focuses on network telemetry. Using hb_network_connection, the hunt baselines inbound traffic to LDAP ports 389 and 636. We stack-count source IP addresses per host to find rare or unknown external sources. In a typical environment, only a few administrative workstations or load balancers communicate with these ports. Any outlier suggests a potential probe or exploitation attempt. 0 0 Next, the hunt examines host-level telemetry for post-exploitation evidence. We query hb_process_activity for the vmdir process and its children. The VMware Directory Service rarely spawns child processes like shells or unexpected binaries. If an attacker successfully bypasses authentication, their subsequent commands often appear as child activity of this service. 0 0 Finally, an automated agent triages the results. It weighs the vulnerability findings against the observed network prevalence and process anomalies. This provides a prioritized list of hosts that are not just vulnerable, but potentially compromised or actively targeted. This approach moves beyond simple CVE alerts by correlating vulnerability status with actual traffic patterns and process anomalies to find exposure that a single alert misses. 0 0

Blind Spots

0 0 The hunt relies on network connection logs. If inbound logging is disabled on the vCenter host or at the network boundary, we cannot see the source of the traffic. Additionally, LDAPS traffic on port 636 is encrypted. While we can see the connection itself, we cannot inspect the payload for specific malicious LDAP attributes without decryption or application-level audit logs. 0 0

  1. Query, scoping

    Identify vulnerability findings

    Filter the estate for hosts already flagged by scanning products with the targeted vCenter CVEs.

    sql, reads hb_vulnerability_finding

    What a hit looks like. Rows identify specific devices and resources (vCenter instances) known to be vulnerable. Silence means no findings are recorded for these CVEs.

  2. Query, scoping

    Enumerate vCenter software versions

    Locate vCenter installations that may be vulnerable based on their reported version, providing a list of hostnames for subsequent steps.

    sql, reads hb_software_inventory
    SELECT device_hostname, package_name, package_version, vendor_nameFROM hb_software_inventoryWHERE LOWER(package_name) LIKE '%vcenter%'

    What a hit looks like. A list of hostnames and vCenter versions. Any version below the fixed releases (e.g., 9.1.2, 9.0.2.0300, 8.0 U3m) is vulnerable.

  3. Query, baseline

    Analyze inbound LDAP traffic prevalence

    Detect anomalous inbound connections to vCenter LDAP ports (389/636) by stack-counting source IPs per host.

    sql, reads hb_network_connection
    SELECT device_hostname, src_endpoint_ip, dst_endpoint_port, COUNT(*) as connection_count, MIN(time) as first_seen, MAX(time) as last_seenFROM hb_network_connectionWHERE (dst_endpoint_port = 389 OR dst_endpoint_port = 636)  AND direction = 'inbound'  AND time >= datetime('now', '-{{lookback_days}} days')  AND ('{{scope_hosts}}' = '' OR instr(',' || '{{scope_hosts}}' || ',', ',' || device_hostname || ',') > 0)GROUP BY device_hostname, src_endpoint_ip, dst_endpoint_portORDER BY connection_count ASC

    What a hit looks like. Rare source IPs connecting to LDAP ports on a vCenter instance. Administrative workstations and known load balancers should be the only frequent sources.

  4. Query, detection candidate

    Check vmdir process behavior

    Identify any unusual child processes or commands associated with the VMware Directory Service, which may follow a successful bypass.

    sql, reads hb_process_activity
    SELECT device_hostname, process_name, process_cmd_line, parent_process_name, user_name, timeFROM hb_process_activityWHERE (LOWER(process_name) LIKE '%vmdir%' OR LOWER(parent_process_name) LIKE '%vmdir%')  AND time >= datetime('now', '-{{lookback_days}} days')  AND ('{{scope_hosts}}' = '' OR instr(',' || '{{scope_hosts}}' || ',', ',' || device_hostname || ',') > 0)

    What a hit looks like. The vmdir process should have minimal child activity. Any shell launch or unusual binary run by vmdir is highly suspicious.

  5. Agent triage

    Triage vCenter exposure and traffic

    Evaluate whether the confirmed vulnerable hosts are receiving anomalous LDAP traffic and if the directory service shows suspicious behavior.

  6. Decision

    Route on exposure risk

    Direct the analyst to remediation if the agent finds evidence of exposure or suspicious activity.

  7. Analyst task

    Remediate vulnerable vCenter instances

    Address the vulnerability by applying updates and reviewing access controls.

  8. Analyst task

    Close out hunt

    Finalize documentation and findings.

Blind spots

  • Needs hb_network_connection logs for inbound traffic. Without inbound connection logs, we cannot distinguish between a vulnerable but idle instance and one being actively probed or exploited. It would answer: whether an external attacker connected to the LDAP service
  • Needs LDAPS decryption or vmdir application audit logs. Encrypted LDAP (LDAPS) traffic prevents inspection of the request body, meaning we rely on connection prevalence rather than payload analysis. It would answer: whether the content of an LDAP request on port 636 was malicious

# VMware vCenter Directory Service Authentication Bypass Exposure

This hunt identifies VMware vCenter instances exposed to the critical authentication bypass vulnerabilities CVE-2026-123903 (LDAP) and CVE-2026-123890 (RPC). The hunt scopes the estate using vulnerability findings and software inventory, baselines inbound LDAP/RPC traffic to identify anomalous source IPs, and examines vCenter directory service process behavior for signs of post-exploitation activity. An agent weighs the exposure against the observed traffic patterns to prioritize remediation of the virtualization fabric.

```sqlite target=network role=baseline params=(lookback_days=lookback_days, scope_hosts=scope_hosts)

  workstations and known load balancers should be the only frequent sources.

  key:

  rare_below: 5
reads:
- device_hostname
- src_endpoint_ip
- dst_endpoint_port
- direction
- time
```

## route-on-verdict
<!-- Route on exposure risk -->
if~: "the triage verdict identifies at least one vulnerable vCenter instance or suspicious inbound traffic from unknown source IPs" (confidence: medium, judge=hunter)
then: → remediation-task
indeterminate: → remediation-task
unavailable: → remediation-task (blind_spot: missing-network-logs)
else: → close-out

## remediation-task
<!-- Remediate vulnerable vCenter instances -->
```manual target=analyst
Apply VMware patches urgently for all instances identified as vulnerable (fixed in 9.1.2, 9.0.2.0300, 8.0 U3m, or 5.2.5). Review the ownership of anomalous source IPs identified in the network prevalence step. Restrict LDAP (389/636) and RPC traffic to trusted administrative network segments.
```
→ close-out

## close-out
<!-- Close out hunt -->
```manual target=analyst
Document all vulnerable instances discovered and confirm patch application. Update the asset management system to reflect current software versions and ensure the hunt is scheduled for periodic review.
```
→ end
