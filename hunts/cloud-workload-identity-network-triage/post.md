# Hunting Cloud Workload Compromise via Identity and Network Triage

### Why this hunt. The Microsoft named a Leader in the Frost Radar: Cloud Workload Protection Platforms, 2026 report emphasizes that protection must move beyond static scanning. In cloud-native environments, the most dangerous threats involve the abuse of legitimate identities to modify running infrastructure. When an adversary gains control of a cloud identity with excessive permissions, they can bridge the gap from the control plane to the workload itself. This hunt identifies that transition by looking for the behavioral footprints left behind during and after such a compromise. ### The hypothesis. An adversary uses over-permissioned cloud identities to compromise container workloads, establishing persistence through rare outbound network channels that bypass standard scanning. The adversary first secures administrative access to the cloud environment. From there, they pivot into the orchestration layer to modify or deploy malicious containers. Finally, they establish outbound communication to a command-and-control server using domains that are unique to the compromised hosts. ### Scoping the container fleet. The first phase of the hunt defines the container attack surface. Rather than scanning every host in the environment, we use software inventory data to find machines running Docker, Kubelet, or Containerd. This scoping step is vital for performance and accuracy. It allows the analyst to narrow the focus to the specific infrastructure where containerized workloads reside. By identifying these hosts first, the hunt ensures that subsequent network stack-counting is relevant to the container orchestration layer. ### Parallel investigation of identity and egress. Once we define the scope, the hunt executes two parallel queries to gather evidence. The first query focuses on the cloud control plane by searching authentication logs for successful sign-ins to providers like AWS, Azure, and GCP. We look for administrative users and anomalous source IPs. Simultaneously, the second query analyzes DNS activity across the previously identified container hosts. It uses stack-counting to find hostnames queried by very few hosts across the fleet. These rare domains are prime candidates for command-and-control infrastructure. ### Correlating the risk. The core of this hunt is the triage and correlation phase. An automated agent or a manual analyst reviews the findings from both parallel branches. The objective is to find temporal or spatial overlaps. For instance, if an administrative account logs in from a new IP address shortly before a container host starts querying a rare domain, the risk of compromise is high. This pivot from identity to network behavior provides a unified view of the incident that isolated alerts might miss. By linking the who at the cloud level to the what at the network level, we can confirm post-exploitation activity. ### What the hunt cannot see. No hunt is exhaustive. This playbook has two primary blind spots. First, it relies on DNS telemetry to find outbound connections. If an adversary uses hardcoded IP addresses for direct communication or employs sophisticated domain-fronting, these connections will not appear in rare DNS stacks. Second, there is a visibility gap in the orchestration plane. If an attacker uses stolen Kubernetes service account tokens to modify a workload without a traditional cloud provider login, the identity query will not capture the initial entry. Analysts should consider supplementing this hunt with Kubernetes audit log analysis for deeper coverage. ### How to run it. This hunt is provided as a hunt.md playbook. It is a structured, machine-readable format that you can import into Huntbase or any other hunt.md-compatible runtime. To start, configure the lookback parameter to define how many days of history to search and specify your cloud providers. The playbook will then walk you through the scoping, evidence gathering, and correlation steps to identify compromised workloads in your environment.
