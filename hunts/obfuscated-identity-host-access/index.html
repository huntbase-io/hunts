Obfuscated Identity and Host Access

An adversary is using multi-hop proxies or tunnels to mask their origin during authentication to cloud identity providers, subsequently using that access to reach internal hosts and execute local commands.

Brief

Why this hunt

Adversaries often hide behind proxies to reach cloud-managed identity providers. This technique allows them to blend in with a global workforce and bypass geographic or IP-based restrictions. The recent research by Elastic Security Labs, titled How a team of entity maintainers monitors, connects and scores entities in Elastic Security (https://www.elastic.co/security-labs/blog/entity-resolution-identity-scoring-elastic-security), highlights how tracking entities requires connecting disparate identifiers. This hunt bridges the gap between network-level obfuscation and identity-level activity to find hidden threats.

Hunt Flow

The first phase uses the hb_auth_signin surface to identify successful logins. We scope the hunt to authoritative identity providers like Okta, Entra ID, or Microsoft 365. By identifying the source IPs and user names associated with these successes, we establish the foundation for our investigation. We focus on logins occurring within the last 14 days to capture active sessions and ignore stale data. The second phase runs two queries in parallel to identify signs of origin masking. One query monitors hb_dns_activity for requests to known tunneling domains such as ngrok or Tor hidden services. We specifically filter for these requests coming from sensitive authentication processes like lsass.exe or securityd. At the same time, we baseline hb_auth_signin to find source IPs that have authenticated only one or two unique users across the fleet. This identifies potential single-use proxy nodes that are not part of known corporate infrastructure or public carrier gateways. In the third phase, we pivot to internal activity using the hb_network_connection surface. We look for outbound connections from the hosts identified in the previous steps to internal IP addresses. We target common administrative ports such as SSH (22), RDP (3389), SMB (445), and WinRM (5985). By stacking these connections, we isolate activity that is rare across the environment, which helps us ignore routine administrative noise and focus on potential lateral movement from a suspect entry point. The final phase examines hb_process_activity for local command execution. We search for processes running in a local user context that are rare across the fleet. This identifies the use of shells or specialized tools that an adversary might use once they have established a beachhead. By correlating the timing of this execution with the earlier identity provider logins and proxy DNS activity, an analyst can confirm a full intrusion chain. The hunt uses an automated synthesis agent to verify if these events occurred within 60 minutes of each other.

Blind Spots

The hunt has two primary blind spots. First, it lacks context on MFA disposition. If a user successfully passes a strong hardware MFA challenge from a proxy IP, the activity might be legitimate remote work. Without this data in the hb_auth_signin surface, the hunt may produce false positives for remote employees in unusual locations. Second, short DNS retention periods can hide the initial connection to tunneling infrastructure if it occurred more than 14 days ago, breaking the correlation chain.

# Obfuscated Identity and Host Access

This hunt correlates network obfuscation with identity provider authentication and subsequent internal host activity. It follows a phased flow: first, it identifies proxy usage by authentication processes and authoritative sign-in events from identity providers; second, it pivots to observe rare internal network connections on administrative ports and suspicious process execution in the local context. This traces the full chain from an external proxy-originating login to local host execution, providing the context necessary to distinguish a breach from normal administrative access.
