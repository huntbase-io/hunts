Blinder Tunnel .csproj Hijacking and C2

Medium severity TLP:CLEAR Research by Unit 42 Published 7 Oct 2026

Hypothesis

An intruder has delivered a weaponized Visual Studio project that uses MSBuild to stage malicious binaries into a local appdata path and initiate an AppDomainManager hijack for command-and-control.

Brief

Why hunt for Blinder Tunnel?

Unit 42 recently detailed the Blinder Tunnel Campaign Targets Iraqi Infrastructure, where adversaries target software engineers with weaponized archives. These archives contain .csproj files that, when opened, use MSBuild to execute malicious code. This technique bypasses traditional perimeter defenses by piggybacking on legitimate developer workflows. Because developers often possess high-level access and their activity often includes rare tool execution, identifying this specific hijacking chain requires more than a simple alert on MSBuild execution.

How the Hunt Flows

The first step focuses the estate. The query scans software inventory to identify hosts running Visual Studio or MSBuild. Since the campaign specifically targets engineers, this scoping prevents the analyst from drowning in noise by focusing on the most likely targets for this lure.

Once we have our target hosts, the hunt looks for evidence of staging and initial execution. A query identifies instances where msbuild.exe creates files in the \Microsoft\RuntimeBrokers\ subdirectory of a user's Local AppData. Parallel to this, the hunt baselines the execution of RuntimeBroker.exe. While this is a legitimate Windows process, it should not run from a user's AppData folder. The hunt flags any host where this rare execution occurs on the same machine that recently saw MSBuild staging activity.

If the first two phases return hits, the hunt pivots to network evidence. It searches for process-led connections to GitHub API domains originating from the suspected hijacked process. This is the primary C2 channel observed in the campaign. Additionally, the hunt checks for the execution of Chisel, an open-source tunneling tool often used for persistent access. The hunt looks for specific command-line arguments, such as client or reverse-proxy patterns (R:), that indicate active tunneling.

Finally, the hunt provides a triage point. An agent weighs the correlation between the MSBuild staging, the rare RuntimeBroker execution, and the network activity to provide a verdict. If confirmed, the hunt initiates host isolation and tasks an analyst to review the %LOCALAPPDATA%\Microsoft\RuntimeBrokers directory for a malicious .config file designed to disable Event Tracing for Windows (ETW).

What This Hunt Cannot See

This hunt has two primary blind spots. First, it cannot verify the malicious content of the XML configuration files without manual file collection. While it detects the creation of the file, it cannot see the specific tags used to disable ETW. Second, without full URI-level granularity in network proxy logs, the hunt identifies connections to GitHub but cannot distinguish between legitimate repository access and malicious C2 traffic without the process context.

    Focus the hunt on hosts with Visual Studio or MSBuild, as these are the primary targets for weaponized project files.

  2. Query, detection candidate

    MSBuild writing to AppData subfolders

    Identify instances where msbuild.exe creates files in the non-standard RuntimeBrokers path as specified in the report.

    sql, reads hb_file_activity

    What a hit looks like. Creation of RuntimeBroker.exe, RuntimeBroker.exe.config, or RuntimeBroker.dll in a local appdata folder by MSBuild.

  3. Query, baseline

    Rare RuntimeBroker execution from AppData

    Identify the execution of RuntimeBroker.exe from the non-standard Local AppData path used by the hijack.

    sql, reads hb_process_activity
    SELECT process_path, COUNT(DISTINCT device_hostname) AS host_count, COUNT(*) AS run_count, MIN(time) AS first_seenFROM hb_process_activityWHERE LOWER(process_path) LIKE '%\microsoft\runtimebrokers\runtimebroker.exe'  AND ('{{scope_hosts}}' = '' OR instr(',' || '{{scope_hosts}}' || ',', ',' || device_hostname || ',') > 0)  AND time >= datetime('now', '-{{lookback_days}} days')GROUP BY process_pathHAVING host_count <= 5ORDER BY host_count ASC

    What a hit looks like. A binary named RuntimeBroker.exe running from a user's Local AppData folder. Silence suggests no such hijack has occurred.

  4. Agent triage

    Early Stage Triage

    Assess whether the MSBuild file creation and the rare RuntimeBroker execution on the same host indicate an active infection.

  5. Query, enrichment

    Network connections to GitHub API

    Identify process-led connections to GitHub domains from the suspected hijacked process.

    sql, reads hb_network_connection
    SELECT device_hostname, process_name, dst_endpoint_hostname, timeFROM hb_network_connectionWHERE (LOWER(process_path) LIKE '%\microsoft\runtimebrokers\%' OR LOWER(process_name) = 'runtimebroker.exe')  AND instr(',' || '{{github_domains}}' || ',', ',' || LOWER(dst_endpoint_hostname) || ',') > 0  AND time >= datetime('now', '-{{lookback_days}} days')

    What a hit looks like. The suspicious RuntimeBroker process communicating with GitHub API domains.

  6. Query, enrichment

    Chisel execution and command lines

    Search for the open-source Chisel tunneling tool used for persistent access.

    What a hit looks like. Processes executing with Chisel-specific tunneling arguments. Silence means no active tunneling bridge was observed.

# Blinder Tunnel .csproj Hijacking and C2

The adversary targets software engineers with weaponized Visual Studio projects to gain a foothold in critical infrastructure. This hunt starts by finding developer workstations where MSBuild has been manipulated to create files in non-standard subdirectories of the Local AppData folder. It analyzes the execution of renamed binaries from these directories and correlates them with follow-on GitHub API traffic or Chisel tunneling. An agent weighs these phased results, and an analyst confirms the suppression of event tracing.
