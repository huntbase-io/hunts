# Hunting SSO Takeover and High-Impact Data Operations

### Why this hunt? Cisco Talos recently detailed the mechanics of identity-centric intrusions in their report, "The story behind the intelligence" (https://blog.talosintelligence.com/the-story-behind-the-intelligence/). Adversaries increasingly use vishing to bypass MFA or trick users into approving push notifications. Once inside the SSO provider, they have the keys to the entire cloud and on-premises kingdom. This hunt provides a structured way to find those who have already breached the perimeter. ### The Hypothesis An adversary has bypassed SSO protections using stolen credentials and is now performing bulk data exfiltration or deploying ransomware across the environment. ### Scoping the Identity Lead The hunt begins at the identity provider. The first phase queries the `hb_auth_signin` surface to identify successful Okta logins where the provider recorded no multi-factor authentication. This scoping query filters out the majority of legitimate traffic, focusing the investigation on accounts that might have been compromised through session hijacking or legacy protocol exploitation. This list of users and their associated source hosts provides the starting point for the rest of the hunt. ### Identifying Concurrent Impact Once the hunt identifies potential account takeovers, it branches into a parallel search for malicious intent. One branch monitors `hb_cloud_api_activity` for mass data access. It looks for users who execute over 1,000 read operations within the lookback window. This behavior often indicates automated scraping of S3 buckets or mailboxes. The query looks for high-volume API calls that deviate from standard administrative patterns. The second branch focuses on the endpoint via `hb_process_activity`. It searches the hosts identified in the login phase for two specific indicators: the use of known ransomware utilities like `vssadmin.exe` to delete shadow copies, and the presence of the specific "azim sucks" string in command lines. This string is a known marker from specific threat actors described in recent intelligence. By searching for these markers on hosts tied to weak logins, the hunt narrows the focus to active threats. ### Correlating Evidence A triage agent ingests the results from both branches. It evaluates whether the users identified in the MFA-less login phase are the same actors performing bulk cloud reads or executing suspicious processes. This correlation is critical. Detecting a new login location is often a false positive, but a new login followed by 5,000 API calls for data access constitutes a high-confidence incident. The agent issues a per-host verdict to guide the final analyst review or automated isolation. ### Blind Spots and Limitations This hunt focuses on the "how" of the impact, not the "how" of the initial lure. It cannot see the vishing call or the social engineering interaction because it lacks access to VOIP or corporate phone logs. Additionally, if an adversary operates on a host without EDR coverage or process logging, the ransomware markers remain invisible. The hunt relies on `hb_process_activity` having command-line support to see the actor-specific strings. ### Running the Playbook This hunt exists as an open `hunt.md` playbook. You can import it into Huntbase or any runtime that supports the `hunt.md` standard. The playbook includes the necessary parameters to adjust the lookback window and refine the list of impact markers based on your environment's baseline. It provides a repeatable workflow to verify the integrity of your SSO sessions and detect high-impact data theft or system destruction.
