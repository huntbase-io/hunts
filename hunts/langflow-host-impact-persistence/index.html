Langflow Host Impact and Persistence

High severity TLP:CLEAR Part 2 of 2 Research by Rapid7 Published 18 Nov 2026

Hypothesis

An attacker has exploited a code-injection vulnerability in Langflow to execute arbitrary Python code, resulting in interactive shell access and persistence through unauthorized modifications to the application database.

Brief

Rapid7 recently highlighted new Metasploit modules for Langflow in their Metasploit Wrap Up (https://www.rapid7.com/blog/post/pt-metasploit-wrap-up-langflow-mongodb-and-more). These modules exploit unauthenticated code injection vulnerabilities, such as CVE-2026-10134, allowing attackers to execute Python and gain shell access. This hunt provides a playbook to identify these impacts and subsequent persistence.

How the Hunt Flows

The hunt begins with a scoping phase to minimize performance impact. The first query identifies hosts where Langflow is installed using software inventory data. This step acts as a gate. By narrowing the focus to confirmed Langflow hosts, the hunt avoids running expensive behavioral queries across the entire fleet. Once the hunt confirms Langflow presence, it executes two parallel behavioral checks. The first check identifies rare process relationships where a Python process spawns a command shell like bash or powershell. While Python-to-shell activity occurs in many developer environments, the hunt isolates rare instances on Langflow hosts to find suspicious code execution. This is a hunt rather than a standard detection because Python-to-shell activity is often too noisy for a global rule. By gating the query and correlating it with database tampering, we make the signal actionable. The second parallel check targets the datastore. Langflow uses an internal database to store tool configurations and secrets. Attackers can modify the tool_code fields to create persistent backdoors. The hunt queries datastore activity logs for any operations touching these fields or secret tables on the identified hosts. This correlation between shell activity and database changes provides the evidence needed for a high-confidence verdict. The triage phase requires an analyst to compare the identified process and database activity. The hunt provides a per-host verdict of malicious, suspicious, or benign based on the frequency of the process spawns and the nature of the database modifications. For instance, an update to the tool_code table that coincides with a shell launch from a Python process is a strong indicator of a compromised instance.

What the Hunt Cannot See

This hunt has three primary blind spots. It relies on host inventory, so it misses Langflow on unmanaged or shadow-IT systems. If Langflow runs in a container, the host-level agent might not see the internal Python-to-shell transitions unless it has visibility into the container namespace. Finally, the hunt requires datastore logs that include the actual SQL message content. If the logs only show connections without the query text, the persistence mechanism remains hidden.

# Langflow Host Impact and Persistence

This hunt targets the post-exploitation phase of multiple Langflow vulnerabilities (CVE-2026-0768, CVE-2026-0769, CVE-2026-10134). It follows a gated approach designed to minimize performance impact: an initial cheap scoping query identifies hosts running Langflow, and only then are deeper, more expensive queries triggered to find rare Python-to-shell process relationships and suspicious datastore activity. By correlating rare child processes with database-level tampering, the hunt identifies persistence mechanisms that standard detection rules often overlook.
