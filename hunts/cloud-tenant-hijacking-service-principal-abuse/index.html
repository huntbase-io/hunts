Cloud Tenant Hijacking and Service Principal Abuse

An adversary uses stolen application secrets for application-only authentication to hijack M365 tenants, subsequently escalating privileges via the Graph API to host phishing infrastructure on SharePoint and OneDrive.

Brief

Why now

Recent research titled The hidden network: Inside the phishing infrastructure ecosystem powering global cybercrime (https://www.microsoft.com/en-us/security/blog/2026/10/14/the-hidden-network-inside-the-phishing-infrastructure-ecosystem-powering-global-cybercrime/) details how adversaries hijack legitimate M365 tenants to host phishing materials. These actors, such as Storm-3119, bypass standard user-level detections by abusing application-only authentication. Once they control a service principal, they scale their operations across SharePoint and OneDrive. We published this hunt to help practitioners find the specific trail left during this takeover process.

How the hunt flows

The hunt begins with a scoping phase to identify every active M365 tenant within the environment. This step uses the hb_cloud_api_activity surface to narrow the investigation to active accounts and services, ensuring the analyst only triages relevant telemetry.

In the second phase, the hunt identifies anomalous access patterns. It queries the hb_auth_signin surface for two specific signals: logins originating from known proxy or anonymizing infrastructure and authentication flows that use application secrets or client credentials rather than user sessions. An analyst then assesses whether these principals represent known service accounts or unexpected beachheads.

Third, the hunt pivots to privilege escalation and resource abuse. It returns to hb_cloud_api_activity to find evidence of the adversary self-provisioning the PnP Management Shell or granting sensitive directory permissions like AppCatalog.ReadWrite.All. These actions allow the attacker to control organizational storage for malicious hosting.

Finally, the hunt monitors for persistence and manipulation. It looks for service principals performing high-volume administrative tasks that are rare for the environment, such as bulk password resets or license assignments. The process concludes by correlating the initial access anomalies with these administrative abuses to confirm a persistent takeover.

What the hunt cannot see

This hunt faces two primary blind spots. First, if an adversary steals an application secret months before they begin manipulation, the initial access may fall outside the 90-day retention limit of most cloud audit logs. Second, the telemetry often shows which application authenticated but does not always specify which client secret ID the actor used. This makes it difficult to confirm if a specific secret was leaked until the app is audited.

How to run the hunt

This hunt is an open hunt.md playbook. You can import it directly into Huntbase or any runtime that supports the hunt.md standard. The playbook includes the logic to scope your tenants, triage the authentication flows, and analyze the full attack chain. Because this is a hunt rather than a static detection, it focuses on the correlation of events that indicate a systematic environment hijacking.

  1. Identify active M365 tenants

    Query · scoping

    Find the M365 tenant IDs currently active in the API logs to narrow the investigation.

    reads hb_cloud_api_activitysql
    SELECT DISTINCT cloud_account_uid, api_service_name FROM hb_cloud_api_activity WHERE provider = 'm365' AND time >= datetime('now', '-{{lookback_days}} days')

    What a hit looks like. A list of cloud account UIDs representing active tenants. Silence suggests no M365 activity.

  2. Proxy and Anonymized sign-ins

    Query · triage

    Identify sign-ins coming from known proxies or anonymizing infrastructure.

    reads hb_auth_signinsql
    SELECT actor_user_domain, actor_user_name, src_endpoint_ip, user_agent, src_location_country, time FROM hb_auth_signin WHERE provider = 'm365' AND is_proxy = 'true' AND ('{{scope_hosts}}' = '' OR instr(',' || '{{scope_hosts}}' || ',', ',' || actor_user_domain || ',') > 0) AND time >= datetime('now', '-{{lookback_days}} days')

    What a hit looks like. Sign-in events flagged as originating from proxy infrastructure. Silence proves no such logins were detected.

  3. Application-only authentication flows

    Query · detection candidate

    Identify logins using application secrets rather than user sessions, a prerequisite for the Storm-3119 takeover pipeline.

    reads hb_auth_signinsql
    SELECT actor_user_domain, actor_user_name, auth_protocol, src_endpoint_ip, time FROM hb_auth_signin WHERE provider = 'm365' AND activity_id = 1 AND (LOWER(auth_protocol) LIKE '%secret%' OR LOWER(auth_protocol) LIKE '%client_credentials%') AND ('{{scope_hosts}}' = '' OR instr(',' || '{{scope_hosts}}' || ',', ',' || actor_user_domain || ',') > 0) AND time >= datetime('now', '-{{lookback_days}} days')

    What a hit looks like. Successful application-only logins. Benign service accounts will appear, but new or unexpected principals are suspicious.

  4. Assess early access indicators

    Agent triage

    Determine if the sign-in anomalies and application flows together suggest an active tenant takeover attempt.

  5. Graph escalation and PnP Shell

    Query · triage

    Find the specific privilege escalation tradecraft: self-provisioning the PnP Management Shell and granting sensitive directory permissions.

    reads hb_cloud_api_activitysql
    SELECT api_operation, resource_name, actor_user_name, cloud_account_uid, time FROM hb_cloud_api_activity WHERE provider = 'm365' AND (LOWER(resource_name) LIKE '%pnp management shell%' OR LOWER(api_operation) LIKE '%addapproleassignment%' OR LOWER(resource_name) LIKE '%appcatalog%') AND ('{{scope_hosts}}' = '' OR instr(',' || '{{scope_hosts}}' || ',', ',' || cloud_account_uid || ',') > 0) AND time >= datetime('now', '-{{lookback_days}} days')

    What a hit looks like. Granting of sensitive AppCatalog or Graph roles to the PnP Shell or new apps. Silence suggests no documented privesc attempt.

  6. Rare silent password and license changes

    Query · baseline

    Identify high-volume manipulation of accounts and licenses by service principals that are new to the environment.

    reads hb_cloud_api_activitysql
    SELECT actor_user_name, api_operation, MIN(time) AS first_seen, COUNT(DISTINCT cloud_account_uid) AS tenant_count, COUNT(*) AS total_ops FROM hb_cloud_api_activity WHERE provider = 'm365' AND (LOWER(api_operation) LIKE '%resetpassword%' OR LOWER(api_operation) LIKE '%assignlicense%') AND time >= datetime('now', '-{{lookback_days}} days') GROUP BY actor_user_name, api_operation HAVING tenant_count <= 1 ORDER BY total_ops DESC

    What a hit looks like. A service principal performing password resets or license assignments that is new or rare in the environment.

    Agent triage

    Connect the initial anomalous access to the follow-on resource manipulation to confirm a persistent takeover.

  8. Route on takeover verdict

    Decision

    Direct the response based on the agent's confidence in a tenant hijacking.

  9. Revoke App Access

    Response action

    Halt the hijacking by disabling the identified service principal and its secrets.

  10. Remediate and Audit

    Analyst task

    Perform manual verification of modified accounts and cleanup of malicious storage.

    Analyst task

    Finalize findings and record tuning notes.

# Cloud Tenant Hijacking and Service Principal Abuse

This hunt identifies the lifecycle of cloud tenant hijacking as observed in the Storm-3119 ecosystem. It begins by identifying anomalous application-level authentication flows and sign-ins from proxy infrastructure (T1090.003). It then follows the chain to find privilege escalation through the self-provisioning of the PnP Management Shell and the abuse of sensitive directory permissions like AppCatalog.ReadWrite.All (T1098.003). By correlating initial access with follow-on resource manipulation, the hunt distinguishes between routine automation and the systematic hijacking of organizational storage for global phishing operations.
