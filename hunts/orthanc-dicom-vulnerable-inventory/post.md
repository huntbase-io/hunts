# Identifying and Prioritizing Vulnerable Orthanc DICOM Servers

The CISA recently published an advisory regarding the Orthanc DICOM Server (https://www.cisa.gov/news-events/ics-medical-advisories/icsma-26-253-02), highlighting a critical vulnerability, CVE-2026-87020. This vulnerability allows for a heap-based buffer overflow that can lead to remote code execution or a denial-of-service condition. Because Orthanc is a common open-source DICOM server used throughout the healthcare sector for managing medical images, the potential impact on clinical availability is significant.

Our team has published a hunt.md playbook to help practitioners identify these vulnerable systems across their estate. This is not a simple detection for a single exploit attempt; rather, it is a hunt designed to provide a comprehensive inventory and risk-based prioritization of Orthanc instances that require immediate attention.

The hypothesis for this hunt assumes that while many Orthanc servers may be unpatched, those at highest risk are either exposed to the internet or are already experiencing instability from potential exploitation attempts. We look for a combination of vulnerable software versions (below 1.13.0) and behavioral signals like high-frequency process restarts that suggest the server is crashing after receiving malformed packets.

The hunt begins with a scoping phase. We query the software inventory (hb_software_inventory) to identify any host with Orthanc installed and then cross-reference these hosts with specific records in hb_vulnerability_finding for CVE-2026-87020. This provides the initial footprint of the problem, identifying which systems are technically susceptible based on installed package records and scanner data.

In the second phase, the hunt pivots into enrichment and behavioral analysis across three surfaces simultaneously. We check external exposure data (hb_exposed_assets) to see if these Orthanc instances are reachable from the public internet. We also analyze process activity (hb_process_activity) telemetry, specifically counting process terminations and launches. Because the heap-overflow often results in a crash, a vulnerable server that is frequently restarting is a primary candidate for exploitation. Finally, we use software inventory again to establish a version prevalence baseline to identify rare, older versions.

The final phase involves a triage step where an agent correlates these data points. A system that is both unpatched and internet-exposed is immediately flagged for isolation. Similarly, a system that is unpatched and showing high-frequency crashes is treated as a critical risk, regardless of its exposure, as it indicates active instability. This automated triage helps analysts focus on the assets most likely to affect patient care and clinical operations.

There are limitations to what this hunt can see. If Orthanc is running on an unmanaged IoMT device or legacy medical equipment without an endpoint agent, it will not appear in the software inventory or process telemetry queries. Additionally, if the server is exposed on a non-standard port not covered by your external scanning parameters, it may remain hidden from the exposure check. These blind spots require supplementary network-level traffic analysis to fully address.

This hunt is delivered as a hunt.md playbook. You can import it into Huntbase or any other runtime that supports the hunt.md format to begin assessing your environment. By focusing on the combination of vulnerability, exposure, and behavior, you can move from a long list of unpatched servers to a prioritized action plan that protects your clinical operations.
