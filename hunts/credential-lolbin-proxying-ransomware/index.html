Credential-driven LOLBin Proxying and Ransomware

An intruder has used stolen credentials to gain initial access and is now using signed system binaries to proxy execution and encrypt files across the estate.

Brief

Why This Hunt

Ransomware remains a primary threat to business continuity. Many defenders rely on signature-based alerts that trigger too late in the attack lifecycle, often after encryption starts. This hunt focuses on the gap between initial access and impact as described in the Huntress article Threat Hunting: What It Is, How It Works, & Why It Matters. We want to catch the adversary while they still use legitimate tools to prepare their final payload.

How the Hunt Flows

The first phase identifies successful network or remote interactive sign-ins. This query uses the hb_auth_signin surface to find accounts that might be under external control. Because authentications happen constantly, an agent evaluates these results to find anomalies—such as unusual source IPs or login types for a specific user—before proceeding to more resource-intensive endpoint searches.

If the first phase yields suspicious leads, the hunt gates into a parallel investigation of endpoint behavior. One branch searches hb_process_activity for Living off the Land Binaries (LOLBins) like rundll32.exe, mshta.exe, or powershell.exe running with suspicious arguments. These arguments include DLL loading, HTTP requests, or encoded commands that suggest a proxy binary is executing a malicious payload to evade simple process name filters.

Simultaneously, the hunt monitors hb_file_activity for high-volume file operations. It counts renames, writes, and creates per host within a one-hour window. If a host exceeds a specific threshold, like 500 operations, it indicates a high probability of mass encryption.

The final phase correlates the initial authentication lead with these endpoint findings. An agent triages the combined evidence to determine if the same account associated with a suspicious login is also the one driving LOLBin abuse or file encryption. If the pattern matches, the hunt provides an immediate action to isolate the host and revoke the compromised credentials.

What the Hunt Cannot See

This hunt has three primary blind spots. First, it relies on integrated authentication logs; a sign-in through an unmonitored identity provider will not trigger the lead query. Second, if an attacker operates on a host without a security agent, the process and file activity will remain invisible even if the initial login was captured elsewhere. Finally, the hunt uses file operation counts as a proxy for ransomware behavior. It does not calculate file entropy, meaning it cannot distinguish between high-volume legitimate writes (like a backup process) and actual encrypted content without further analyst review.

Blind spots

  • Needs hb_auth_signin coverage for all identity providers. A sign-in on an unmonitored provider would bypass the lead query, preventing the gated investigation from starting. It would answer whether a user signed in via a provider not currently integrated.
  • Needs hb_process_activity on all workstations. Attackers can hide within unmonitored hosts; file operations may still alert us, but the source process would remain unknown. It would answer whether a LOLBin was used on a host without an agent.
  • Needs file content entropy calculation. A high count of file writes can be benign (e.g., updates or backups); without entropy, we rely on count alone as a behavioral proxy. It would answer whether the file writes are actually encrypted content.

# Credential-driven LOLBin Proxying and Ransomware

This hunt follows a gated flow to first identify anomalous successful sign-ins as a cheap lead. If an account shows signs of takeover, the hunt opens an expensive search for behavioral evidence: the use of signed system binaries (LOLBins) to proxy malicious execution and high-volume file operations characteristic of ransomware encryption. An agent then correlates the initial access with the endpoint activity to isolate the host before encryption completes.

## auth-lead-query
<!-- Suspicious successful sign-ins -->
Identify successful authentications from network or remote interactive sessions as a lead for potential credential abuse.

```sqlite target=identity role=scoping params=(lookback_days=lookback_days)
~~~yaml

  in the window.
reads:
- actor_user_name
- device_hostname
- logon_type
- src_endpoint_ip
- status_code
- status_id
- time
silence: not_evidence_of_absence
source: hb_auth_signin

SELECT device_hostname, actor_user_name, src_endpoint_ip, logon_type, status_code, status_id, time FROM hb_auth_signin WHERE status_id = 1 AND logon_type IN ('Network', 'Remote Interactive') AND time >= datetime('now', '-{{lookback_days}} days')
```
