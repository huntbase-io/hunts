# Hunting for Persistence and Sniffing on SonicWall SMA Appliances

# Post-Exploitation Hunting on SonicWall SMA  The recent investigation by Volexity, titled Proxying to Compromise: SonicWall SMA 0-day Exploitation (https://www.volexity.com/blog/2026/07/17/proxying-to-compromise-sonicwall-secure-mobile-access-0-day-exploitation/), has shed light on the sophisticated post-exploitation tradecraft of UTA0533. This threat actor has demonstrated a high level of proficiency in maintaining persistence on SonicWall SMA 1000 series appliances. Our team has developed a new hunt design to address these specific behaviors, focusing on the period after an initial breach has occurred. The goal is to identify Python-based backdoors and internal network collection efforts that might otherwise go unnoticed. This hunt is formalized as an open hunt.md playbook for security practitioners to use in their own environments.  ## The Hypothesis  The core hypothesis of this hunt is that an adversary has established persistence on a VPN gateway and is performing internal network collection by sniffing LDAP traffic. This hypothesis is rooted in the observations that UTA0533 modifies system-level Python directories and executes network capture tools. These actions are highly anomalous for a security appliance and provide a strong signal for compromise. The hunt looks for these artifacts across multiple telemetry surfaces.  ## How the Hunt Flows  The hunt begins by establishing the scope. We identify all SonicWall SMA appliances within the environment using software inventory data and exposed asset scanners. This ensures that both managed and unmanaged instances are accounted for before the analysis begins.  Once the scope is defined, the hunt performs three parallel checks. The first check involves baselining POST traffic to the appliance. By looking at a thirty-day window, we can identify URIs that have recently received POST requests for the first time. This is a critical step because attackers often deploy webshells at rare or custom endpoints like /__api__/login which do not appear in normal operational traffic.  The second check focuses on file system integrity. On a VPN appliance, system-level directories should remain immutable. We search for any creations or modifications within Python site-packages or binary paths like /usr/bin and /usr/sbin. These surfaces are where UTA0533 has historically planted backdoors to intercept authentication logic or maintain access.  The third check looks for the execution of sniffing tools. The presence of tcpdump or tshark, especially when running in the background or writing to temporary directories, indicates that an attacker is likely harvesting credentials from internal traffic. On a stable appliance, these tools should only be present during active, authorized troubleshooting sessions.  ## Blind Spots and Limitations  There are limitations to what this hunt can see. We have identified two primary blind spots. First, if the appliance is a black box that does not support an EDR agent or osquery, we lose visibility into direct file and process events. In such cases, we must rely entirely on secondary evidence from HTTP logs. Second, UTA0533 has been known to use WebSockets to tunnel traffic. Standard HTTP logs may only show the initial protocol switch, leaving the tunneled commands opaque to this specific hunt.  ## Running the Hunt  To run this hunt, you can import the provided hunt.md playbook into Huntbase or any compatible runtime. This allows for the automated execution of the SQL queries across your fleet, followed by an agent-assisted triage of the results. This structured approach moves beyond simple static detections by correlating rare traffic patterns with anomalous system changes, providing a comprehensive view of the appliance's integrity. We recommend running this hunt against all edge gateways to ensure that no persistence mechanisms have been established in the wake of recent 0-day exploitations.
