Aeternum Botnet: Persistence and Payload Deployment

An adversary has established persistence via a startup shortcut pointing to a binary in a user-writable directory, which then executes multi-stage loaders and miners.

Brief

The recent analysis by Unit 42, titled Analyzing Aeternum’s Blockchain-Based C2 Operations and Communications, highlights an emerging trend in botnet resilience: the use of blockchain-based command-and-control (C2). Because these C2 mechanisms are nearly impossible to dismantle at the network level, security teams must focus on identifying the infection on the endpoint. This hunt provides a structured approach to detecting Aeternum's host-side lifecycle, specifically focusing on its persistence and payload deployment phases.\n\nOur hypothesis is that an adversary has established persistence via a startup shortcut (.lnk) pointing to a binary in a user-writable directory (AppData), which subsequently executes multi-stage loaders or miners. This pattern is a classic indicator of botnet activity but is notoriously difficult to alert on directly because many legitimate applications use similar paths and persistence methods.\n\n### How the Hunt Flows\n\nThe hunt begins by scoping the environment to Windows-based assets. Since Aeternum is a Windows-centric threat, we identify hosts with Microsoft software inventories to ensure our subsequent queries are targeted at the correct surfaces and do not waste resources on irrelevant systems.\n\nOnce the scope is defined, the hunt moves into a parallel evidence-gathering phase. The first prong searches for new shortcut files created in the Startup directory. While many installers create shortcuts here, the hunt specifically looks for those created within a recent lookback window, providing a list of candidates for further investigation.\n\nSimultaneously, the hunt analyzes process activity to find rare binaries running from Local AppData paths. We define rarity as being seen on fewer than three hosts across the fleet. This effectively filters out common tools like Microsoft Teams or Discord while highlighting unique or newly dropped binaries that warrant closer inspection.\n\nThe third prong of the evidence gathering matches process names and command-line arguments against known indicators. This includes specific loader names mentioned in the Unit 42 research (such as build.exe or wmiframework.exe) and strings associated with XWorm or XMRig. This step serves as high-confidence enrichment for the behavioral signals identified in the other prongs.\n\nFinally, the hunt uses a triage agent to weigh the combined signals. By correlating the existence of a new startup shortcut with the execution of a rare binary in AppData and matching known threat names, we can provide a contextual verdict. This automated weighting is what makes this a hunt rather than a simple detection; it identifies the signal within the high-noise environment of user profiles.\n\n### Blind Spots and Limitations\n\nNo hunt is perfect, and there are two primary blind spots to consider. First, this hunt relies on process execution logs to infer the target of a startup shortcut. If the shortcut is created but the system is not rebooted, we may miss the link. Second, short-lived loaders that run and terminate quickly may be missed if the data source relies on periodic snapshots rather than real-time event streams.\n\n### Running the Hunt\n\nThis hunt is packaged as a hunt.md playbook. It can be imported into Huntbase or any other hunt.md-aware runtime. To run it, adjust the lookback_days parameter to fit your investigation window and provide a specific list of hosts if you wish to target a specific business unit. If results are found, the playbook includes an action to isolate the endpoint to stop C2 communication and further impact.

# Aeternum Botnet: Persistence and Payload Deployment

This hunt targets the host-side lifecycle of the Aeternum botnet. It begins by scoping to Windows-based assets, then simultaneously searches for the creation of startup shortcuts and rare process executions in user-writable paths like AppData. Finally, it corroborates these behavioral signals against known loader and impact binary names (XWorm, XMRig) mentioned in research.
