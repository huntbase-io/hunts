OpenShift Compliance Drift and Audit Correlation

Medium severity TLP:CLEAR Research by Elastic Security Labs Published 20 Nov 2026

Hypothesis

Unauthorized changes to OpenShift resources such as pods or service accounts trigger compliance violations that the hunt traces to a specific actor by correlating scan failures with Kubernetes API audit logs.

Brief

Context Elastic Security

Labs recently published an article titled From posture to root cause: Investigate OpenShift compliance with Elastic Agent Builder (https://www.elastic.co/security-labs/blog/openshift-compliance-elastic-agent-builder). The article describes how to move beyond simple posture alerts to find the root cause of compliance violations. This hunt translates those concepts into a structured playbook to automate the investigative flow by linking disparate data sources.

How the Hunt Flows

The hunt begins with a scoping phase that queries the hb_compliance_finding surface. This step identifies failed compliance controls reported by the OpenShift Compliance Operator, such as failures in CIS or NIST benchmarks. By starting with failed controls, the hunt ensures that the subsequent high-volume audit searches are targeted only at clusters with known issues. Next, the hunt employs a logic gate to assess the severity of these failures. An analyst reviews the findings to see if they impact sensitive resource types in production environments. This check prevents the fan-out of more expensive queries for development clusters or low-severity findings that do not justify a deep-dive audit investigation. If the violations are significant, the hunt proceeds to the correlation phase. The correlation phase runs two investigative paths in parallel. The first path queries the hb_cloud_api_activity surface for Kubernetes API operations, specifically looking for create or patch actions that occurred within the lookback window. This query targets the specific resources identified in the scoping phase. The second path examines hb_process_activity on the underlying nodes to find rare executions of tools like oc or kubectl. Interactive use of these tools on a worker node is a strong indicator of manual tampering that might not follow standard deployment workflows. In the triage phase, an analyst correlates the timing of these activities. By matching the timestamp of an API modification or a rare process execution with the timing of the compliance scan failure, the hunt identifies the specific actor or service account responsible for the drift. This correlation is what makes this a hunt rather than a simple detection rule, as it links data across compliance, cloud, and host telemetry surfaces to build a complete narrative.

What the Hunt Cannot See

There are several blind spots to consider. If the OpenShift Compliance Operator is disabled or fails to report, the lead query will show a clean environment even if drift exists. Furthermore, if Kubernetes audit logs are not configured with sufficient verbosity, the logs might record the API operation without the specific patch payload, requiring manual cluster inspection to see the exact change. Finally, visibility into interactive CLI tool usage depends on having the Elastic Agent installed on all worker nodes.

Steps

  1. Query, scoping

    Lead: Identify Failed Compliance Controls

    Find clusters and specific resources that have failed compliance checks according to the OpenShift Compliance Operator.

    sql, reads hb_compliance_finding
    SELECT resource_uid, resource_name, check_name, status, severity, framework_refsFROM hb_compliance_findingWHERE LOWER(provider) = 'openshift'  AND LOWER(status) = 'fail'

    What a hit looks like. Rows indicate failed CIS or NIST controls. Silence provides evidence that the operator reports no active violations across the estate.

  2. Agent triage

    Initial Assessment of Failures

    Evaluate whether the identified compliance failures represent a security risk worth investigating via expensive audit log analysis.

  3. Decision

    Gate: Proceed to Audit?

    Route the hunt to expensive audit queries only when the compliance lead shows active, relevant violations.

  4. Query, detection candidate

    Kubernetes API Resource Modifications

    Find recent create or patch operations on sensitive resources that likely caused the compliance drift.

    sql, reads hb_cloud_api_activity
    SELECT time, actor_user_name, api_operation, resource_type, resource_name, cloud_account_uid, src_endpoint_ipFROM hb_cloud_api_activityWHERE provider = 'kubernetes'  AND (LOWER(api_operation) = 'create' OR LOWER(api_operation) = 'patch')  AND instr(',' || '{{sensitive_resources}}' || ',', ',' || LOWER(resource_type) || ',') > 0  AND time >= datetime('now', '-{{lookback_days}} days')

    What a hit looks like. API activity identifying the actor who modified the resource. Signal is validated when it precedes the compliance scan failure.

  5. Query, baseline

    Rare CLI Tool Execution on Nodes

    Identify rare interactive usage of cluster tools like oc or kubectl directly on nodes, indicating manual tampering.

    sql, reads hb_process_activity
    SELECT LOWER(process_path) AS path, COUNT(DISTINCT device_hostname) AS host_count, MIN(time) AS first_seenFROM hb_process_activityWHERE (LOWER(process_name) = 'oc' OR LOWER(process_name) = 'kubectl')  AND ('{{scope_hosts}}' = '' OR instr(',' || '{{scope_hosts}}' || ',', ',' || device_hostname || ',') > 0)  AND time >= datetime('now', '-{{lookback_days}} days')GROUP BY 1HAVING host_count < 3

    What a hit looks like. A rare process execution path for a cluster CLI tool. Silence suggests normal automated operations.

  6. Agent triage

    Triage: Correlate Findings

    Link the timing of the compliance failure with the specific API modification or rare CLI execution to identify the root cause.

  7. Decision

    Route to Remediation

    Decide whether to revert the unauthorized change based on the triage verdict.

  8. Response action

    Revert Resource Modification

    Use the OpenShift Compliance Operator or direct API commands to revert the unauthorized resource state.

  9. Analyst task

    Analyst Review

    Review the actor's intent and verify that the remediation was successful.

  10. Analyst task

    Close Out

    Document findings and determine if a permanent detection rule is needed for the observed drift pattern.

Blind spots

  • Needs OpenShift Compliance Operator running and reporting to hb_compliance_finding. A failed scan process results in zero reported failures in the lead query, leaving drift completely unobserved. It would answer: Is the cluster passing, or is the compliance operator failing to report?
  • Needs hb_cloud_api_activity with full Kubernetes audit verbosity. Audit logs that record the action but not the patch payload require live cluster inspection to confirm the drift cause. It would answer: What specifically changed in the resource patch that triggered the violation?
  • Needs Elastic Agent coverage on every OpenShift node. Process execution on worker nodes remains invisible without node-level telemetry, masking interactive tampering. It would answer: Was a CLI tool executed interactively on a node without an agent?

# OpenShift Compliance Drift and Audit Correlation

This hunt identifies security posture drift in OpenShift environments by correlating Compliance Operator scan results with Kubernetes API audit logs and node-level process telemetry. It begins with a scoping query of the compliance findings to identify failures, then gates a more resource-intensive analysis of audit logs and rare process executions to determine the root cause of the unauthorized modification.

## compliance-drift-lead
<!-- Lead: Identify Failed Compliance Controls -->
Find clusters and specific resources that have failed compliance checks according to the OpenShift Compliance Operator.

```sqlite target=endpoint role=scoping
~~~yaml
expected: Rows indicate failed CIS or NIST controls. Silence provides evidence that
  the operator reports no active violations across the estate.
reads:
- resource_uid
- resource_name
- check_name
- status
- severity
- framework_refs
silence: evidence_of_absence
source: hb_compliance_finding
verified: dry-run
verified_at: '2026-11-20'
~~~
SELECT resource_uid, resource_name, check_name, status, severity, framework_refs FROM hb_compliance_finding WHERE LOWER(provider) = 'openshift' AND LOWER(status) = 'fail'
```

## triage-root-cause
<!-- Triage: Correlate Findings -->
```agent target=hunter
cite: required
context:
- analyze-compliance-status
- audit-api-modifications
- rare-cluster-ops
max_iterations: 6
objective: Determine if any resource modification in the audit results explains a
  failed control found in the lead status assessment.
success_criteria: A per-cluster verdict identifying the actor and the infringing resource
  change.
tools:
- endpoint
```

## route-remediation
<!-- Route to Remediation -->
if~: "the triage links a specific unauthorized modification to the timing of a compliance failure with high confidence" (confidence: high, judge=hunter)
then: → apply-remediation
indeterminate: → analyst-review
unavailable: → analyst-review (blind_spot: insufficient-audit-detail)
else: → close-out

## apply-remediation
<!-- Revert Resource Modification -->
```action target=endpoint
~~~yaml
approval: required
~~~
Revert the unauthorized pod, service account, or rolebinding configuration. If a compliance remediation object exists for the failed check, apply it.
```
→ analyst-review

## analyst-review
<!-- Analyst Review -->
```manual target=analyst
Verify the actor_user_name in audit logs against internal change requests. Ensure the scan status for the cluster moves back to PASS.
```
→ close-out

## close-out
<!-- Close Out -->
```manual target=analyst
Record the specific resource and actor that caused the drift. If the modification was a common vector, promote the audit query to a detection rule.
```
→ end
