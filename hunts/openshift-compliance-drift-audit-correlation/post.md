# Tracing OpenShift Compliance Drift to Root Cause with Audit Logs

### Context Elastic Security Labs recently published an article titled From posture to root cause: Investigate OpenShift compliance with Elastic Agent Builder (https://www.elastic.co/security-labs/blog/openshift-compliance-elastic-agent-builder). The article describes how to move beyond simple posture alerts to find the root cause of compliance violations. This hunt translates those concepts into a structured playbook to automate the investigative flow by linking disparate data sources. ### Hypothesis An actor makes unauthorized changes to sensitive OpenShift resources such as pods, service accounts, or cluster roles, triggering compliance violations that an analyst can trace back to the source by correlating scan failures with Kubernetes API audit logs and node-level activity. ### How the Hunt Flows The hunt begins with a scoping phase that queries the hb_compliance_finding surface. This step identifies failed compliance controls reported by the OpenShift Compliance Operator, such as failures in CIS or NIST benchmarks. By starting with failed controls, the hunt ensures that the subsequent high-volume audit searches are targeted only at clusters with known issues. Next, the hunt employs a logic gate to assess the severity of these failures. An analyst reviews the findings to see if they impact sensitive resource types in production environments. This check prevents the fan-out of more expensive queries for development clusters or low-severity findings that do not justify a deep-dive audit investigation. If the violations are significant, the hunt proceeds to the correlation phase. The correlation phase runs two investigative paths in parallel. The first path queries the hb_cloud_api_activity surface for Kubernetes API operations, specifically looking for create or patch actions that occurred within the lookback window. This query targets the specific resources identified in the scoping phase. The second path examines hb_process_activity on the underlying nodes to find rare executions of tools like oc or kubectl. Interactive use of these tools on a worker node is a strong indicator of manual tampering that might not follow standard deployment workflows. In the triage phase, an analyst correlates the timing of these activities. By matching the timestamp of an API modification or a rare process execution with the timing of the compliance scan failure, the hunt identifies the specific actor or service account responsible for the drift. This correlation is what makes this a hunt rather than a simple detection rule, as it links data across compliance, cloud, and host telemetry surfaces to build a complete narrative. ### What the Hunt Cannot See There are several blind spots to consider. If the OpenShift Compliance Operator is disabled or fails to report, the lead query will show a clean environment even if drift exists. Furthermore, if Kubernetes audit logs are not configured with sufficient verbosity, the logs might record the API operation without the specific patch payload, requiring manual cluster inspection to see the exact change. Finally, visibility into interactive CLI tool usage depends on having the Elastic Agent installed on all worker nodes. ### How to Run This hunt is delivered as a hunt.md playbook. You can import it into Huntbase or any compatible hunt.md-aware runtime. To run the hunt, specify the lookback_days for your audit history and provide the sensitive_resources list to focus the investigation on your most critical OpenShift components.
