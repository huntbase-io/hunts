Rogue RMM via BiTB Phishing

An adversary is using Browser-in-the-Browser (BiTB) phishing to trick users into installing rogue ScreenConnect clients from user-writable paths for persistence.

Brief

Why This Hunt Matters\nRecent research from Huntress, Phishing Attacks Serve Browser-in-the-Browser Pages, Rogue RMM Persistence, highlights a refined social engineering technique. Adversaries are using Browser-in-the-Browser (BiTB) templates—specifically faking Adobe Acrobat login prompts—to harvest credentials and trick users into downloading remote monitoring and management (RMM) tools. Because tools like ScreenConnect are frequently legitimate, simple binary alerts often fail to distinguish between a helpdesk session and an attacker establishing a foothold.\n\n### The Hypothesis\nWe hypothesize that an adversary is leveraging BiTB phishing pages to deliver ScreenConnect installers (MSI or EXE) into user-writable paths. If successful, these installers will be used to register new system services, often accompanied by activity-suppression tools designed to hide the remote session from the end user.\n\n### How the Hunt Flows\nThe investigation begins with scoping the environment for existing, authorized RMM and Adobe software. This provides the necessary context to identify which hosts already have a legitimate reason to run these binaries and which do not. We then pivot to DNS activity, looking for lookups to known BiTB landing pages and RMM relay infrastructure identified in the source report.\n\nThe core of the hunt examines process execution. We look for installers and command-line downloaders (like curl) operating out of user-writable directories such as \\Downloads\\ or \\Users\\Public\\. These paths are atypical for legitimate enterprise software deployments but common for user-initiated (or attacker-initiated) downloads.\n\nTo confirm the intrusion, we correlate these process leads with registry activity. We specifically search for the creation of new ScreenConnect services in the System\\CurrentControlSet\\Services key. Simultaneously, we perform a prevalence check across the fleet for binaries like HideCursor.exe and HideUL.exe. These tools are used to suppress UI indicators during remote sessions; seeing them on only one or two hosts provides a strong signal of unauthorized activity.\n\nFinally, an agent synthesizes these disparate signals—DNS, process, and registry—to provide a per-host verdict. This ensures that we are not just looking at a single suspicious file, but an entire behavioral chain.\n\n### Blind Spots\nThere are two primary limitations to this hunt. First, if the browser is configured to use DNS-over-HTTPS (DoH), the initial phishing domain resolution will not appear in host-level DNS telemetry, forcing us to rely entirely on process and registry artifacts. Second, the hunt depends on endpoint agent coverage; any host without an active telemetry provider will be invisible to the process and service registration checks.\n\n### How to Run This Hunt\nThis hunt is provided as an open hunt.md playbook. You can import this file directly into Huntbase or any hunt.md-aware runtime to execute the queries across your environment. Because it uses prevalence stacking and behavioral correlation, it is best run as a periodic check rather than a one-time detection rule.

# Rogue RMM via BiTB Phishing

This hunt follows the lifecycle of an intrusion starting with a phishing redirect to a fake Adobe Acrobat page. It identifies hosts resolving BiTB phishing domains and then pivots to find rogue RMM installers (ScreenConnect, MSI payloads) executing from user profile paths (Downloads, Public). It corroborates these leads by baseline-counting rare activity-suppression tools (HideCursor, HideUL) used to mask attacker presence and searching for new ScreenConnect service registrations. An agent synthesizes the cross-surface evidence to identify confirmed footholds.
