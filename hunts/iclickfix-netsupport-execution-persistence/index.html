iClickFix: NetSupport RAT Execution and Persistence

An intruder has used a ClickFix social engineering lure to execute a PowerShell downloader that installs NetSupport RAT and establishes persistent communication with a multi-hop proxy C2 infrastructure.

Brief

The iClickFix framework represents a significant evolution in the delivery of NetSupport RAT, using compromised WordPress sites to deploy social engineering lures. Researchers at Sekoia recently detailed this activity in their report titled iClickFix: WordPress-targeting framework using ClickFix (https://blog.sekoia.io/meet-iclickfix-a-widespread-wordpress-targeting-framework-using-the-clickfix-tactic/). The framework uses a fake CAPTCHA interface that convinces users to execute a malicious PowerShell command. This command is often delivered via the clipboard, bypassing many browser-based security controls. Our hunt focuses on identifying the specific execution patterns and subsequent persistence associated with this campaign. We treat this as a hunt because the individual components often mimic legitimate administrative activity, requiring a correlated view to confirm a threat.

Phase 1: Execution Lead

The hunt begins by querying hb_process_activity for instances of powershell.exe running with hidden windows and specific downloader cmdlets like iwr or Invoke-WebRequest. We focus on commands that target known delivery domains such as scottvmorton.com. This query captures the initial stage where the malware first enters the environment.

Phase 2: Lead Assessment

Not all hidden PowerShell commands are malicious. The hunt includes a gate where an agent evaluates the command-line arguments of the identified processes. It looks for the specific obfuscation and execution policy bypass flags used by iClickFix. Only if the agent determines the activity is suspicious does the hunt proceed to the more resource-intensive enrichment phases.

Phase 3: Persistence and C2

If the lead is confirmed, the hunt fans out to look for evidence of a successful RAT installation. One query searches for rare executable paths in the ProgramData directory, specifically looking for common NetSupport binaries like client32.exe in randomized subfolders. Simultaneously, another query checks hb_dns_activity for resolutions of known NetSupport gateway domains like pusykakimao.com. Legitimate software rarely operates from these paths while contacting these specific external hosts.

Phase 4: Final Triage

A second agent consolidates the findings from the execution, file, and network queries. By correlating a suspicious PowerShell download with the presence of a new binary in ProgramData and active DNS traffic to a C2 domain, the agent can provide a high-confidence verdict. If an infection is confirmed, the hunt initiates an isolation action to contain the host.

Blind Spots

This hunt relies on process command-line telemetry and DNS logs. If an adversary uses a different delivery mechanism that does not involve PowerShell or if they use a custom downloader that avoids standard cmdlets, the initial lead query will not fire. Additionally, the lack of full HTTP URI visibility means we can confirm contact with the C2 infrastructure but cannot inspect the specific data being exfiltrated.

# iClickFix: NetSupport RAT Execution and Persistence

The adversary uses compromised WordPress sites to deliver a fake CAPTCHA that tricks users into executing malicious PowerShell. This hunt identifies the initial hidden PowerShell downloader pattern. If the hunt finds suspicious execution, it fans out to look for rare NetSupport binaries in ProgramData and network traffic to the infrastructure named in recent research. An agent weighs the execution and post-exploitation evidence to identify compromised hosts for isolation.
