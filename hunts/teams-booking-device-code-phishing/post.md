# Hunting Microsoft Teams Booking Phishing and Session Replay

### Why NowaaRecent research from Huntress (https://www.huntress.com/blog/crafty-microsoft-teams-booking-flow-disguises-device-code-phishing) describes a campaign targeting organizations through convincing Teams booking lures. The adversary avoids traditional credential harvesting, opting for device code flows that bypass many MFA configurations. This hunt identifies the specific sequence of redirects and token replays used in these attacks.aa### The HypothesisaaAn attacker uses a multi-stage redirect chain and a Microsoft Teams booking lure to trick users into authorizing a device code, subsequently replaying stolen session tokens via residential proxies using programmatic tools like Python or Node.js.aa### Phase 1: Scoping the SurfaceaaThe hunt begins by identifying the potential targets within the environment. The analyst identifies hosts with Microsoft Teams installed via software inventory logs. This scoping ensures the subsequent telemetry focus remains on the systems where the lure is most likely to execute. While many organizations use Teams, focusing the search on these hosts reduces noise during the web-telemetry phase.aa### Phase 2: Redirection and Backend TrafficaaThe adversary uses a sequence of redirects involving Google short links and Railway domains to reach the phishing kit. The hunt queries DNS records for these specific redirectors and scans HTTP traffic for requests to the attacker’s backend API. It specifically flags any interaction with the /api/device/start endpoint, which signals the beginning of the device code flow. This phase identifies users who engaged with the lure before any identity-based activity occurs.aa### Phase 3: Identity Abuse and Rare AgentsaaOnce the analyst identifies interaction with the phishing site, the hunt transitions to the identity surface. The hunt searches M365 and Azure AD logs for the ‘Cmsi:Cmsi’ login flow. This tag appears during the device code process. Simultaneously, the query stacks user agents across the environment to find rare programmatic access from Python or Node.js scripts. This rarity indicates programmatic session replay rather than standard user activity from a browser.aa### Phase 4: Multi-Surface CorrelationaaA single sign-in or a single DNS query might appear as noise. The hunt uses an automated agent to correlate these disparate signals. It confirms a compromise when a user interacts with the phishing infrastructure and then exhibits anomalous identity activity within a specific timeframe. This correlation logic provides the high-confidence verdict required for a response, moving the workload from simple detection to a true hunt.aa### What This Hunt Cannot SeeaaThe hunt cannot see the kit's internal execution if it decrypts purely in memory on the client side. If the attacker routes their programmatic tools through high-reputation residential proxies, the source IP may look like a legitimate remote worker, making it difficult to detect based on location alone. The hunt relies on the specific Cmsi login flow and the presence of programmatic user agents.aa### How to Run This HuntaaThis hunt is an open hunt.md playbook. It imports into Huntbase or any runtime that supports the hunt.md specification. Analysts can adjust the lookback window or domain parameters based on their internal telemetry retention and local environment needs.a
