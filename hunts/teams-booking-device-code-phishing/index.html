Microsoft Teams Booking Device Code Phishing

High severity TLP:CLEAR Research by Huntress Published 14 Nov 2026

Hypothesis

An attacker is using a multi-stage redirect chain and a convincing Microsoft Teams booking lure to trick users into authorizing a device code, subsequently replaying the stolen session tokens via residential proxies using programmatic tools.

Brief

Why

NowaaRecent research from Huntress (https://www.huntress.com/blog/crafty-microsoft-teams-booking-flow-disguises-device-code-phishing) describes a campaign targeting organizations through convincing Teams booking lures. The adversary avoids traditional credential harvesting, opting for device code flows that bypass many MFA configurations. This hunt identifies the specific sequence of redirects and token replays used in these attacks.aa

The

HypothesisaaAn attacker uses a multi-stage redirect chain and a Microsoft Teams booking lure to trick users into authorizing a device code, subsequently replaying stolen session tokens via residential proxies using programmatic tools like Python or Node.js.aa

Phase 1: Scoping the

SurfaceaaThe hunt begins by identifying the potential targets within the environment. The analyst identifies hosts with Microsoft Teams installed via software inventory logs. This scoping ensures the subsequent telemetry focus remains on the systems where the lure is most likely to execute. While many organizations use Teams, focusing the search on these hosts reduces noise during the web-telemetry phase.aa

Phase 2: Redirection and Backend

TrafficaaThe adversary uses a sequence of redirects involving Google short links and Railway domains to reach the phishing kit. The hunt queries DNS records for these specific redirectors and scans HTTP traffic for requests to the attacker’s backend API. It specifically flags any interaction with the /api/device/start endpoint, which signals the beginning of the device code flow. This phase identifies users who engaged with the lure before any identity-based activity occurs.aa

Phase 3: Identity Abuse and Rare

AgentsaaOnce the analyst identifies interaction with the phishing site, the hunt transitions to the identity surface. The hunt searches M365 and Azure AD logs for the ‘Cmsi:Cmsi’ login flow. This tag appears during the device code process. Simultaneously, the query stacks user agents across the environment to find rare programmatic access from Python or Node.js scripts. This rarity indicates programmatic session replay rather than standard user activity from a browser.aa

Phase 4: Multi-Surface

CorrelationaaA single sign-in or a single DNS query might appear as noise. The hunt uses an automated agent to correlate these disparate signals. It confirms a compromise when a user interacts with the phishing infrastructure and then exhibits anomalous identity activity within a specific timeframe. This correlation logic provides the high-confidence verdict required for a response, moving the workload from simple detection to a true hunt.aa

What This Hunt Cannot

SeeaaThe hunt cannot see the kit's internal execution if it decrypts purely in memory on the client side. If the attacker routes their programmatic tools through high-reputation residential proxies, the source IP may look like a legitimate remote worker, making it difficult to detect based on location alone. The hunt relies on the specific Cmsi login flow and the presence of programmatic user agents.aa

  2. Query, enrichment

    DNS resolutions for phishing redirectors

    Identify hosts resolving domains used in the attacker's multi-stage redirect chain.

    What a hit looks like. Hosts resolving the known malicious or redirector domains. Silence means the lure was not triggered or used different domains.

  3. Query, detection candidate

    HTTP traffic to the phishing kit API

    Find direct HTTP requests to the attacker backend, specifically the /api/device/start endpoint described in the research.

    sql, reads hb_http_activity
    SELECT device_hostname, url_hostname, url_path, user_agent, timeFROM hb_http_activityWHERE (instr(',' || '{{phishing_backend}}' || ',', ',' || LOWER(url_hostname) || ',') > 0 OR LOWER(url_path) LIKE '%/api/device/%')  AND ('{{scope_hosts}}' = '' OR instr(',' || '{{scope_hosts}}' || ',', ',' || device_hostname || ',') > 0)  AND time >= datetime('now', '-{{lookback_days}} days')

    What a hit looks like. Traffic matching the known backend infrastructure and API patterns. Silence suggests no active engagement with the kit.

  4. Agent triage

    Triage early lure interaction

    Analyze the web telemetry to identify specific hosts or users who likely completed the phishing booking flow.

  5. Query, triage

    Sign-ins with Cmsi login flow

    Identify device code authentication events tagged with the Cmsi:Cmsi flow, as identified in the Huntress research.

    sql, reads hb_auth_signin
    SELECT actor_user_name, src_endpoint_ip, src_location_country, user_agent, event_type, status_detail, timeFROM hb_auth_signinWHERE provider IN ('m365', 'azure_ad')  AND (LOWER(event_type) LIKE '%cmsi:cmsi%' OR LOWER(status_detail) LIKE '%cmsi:cmsi%')  AND time >= datetime('now', '-{{lookback_days}} days')

    What a hit looks like. Logins explicitly using the device code flow pattern associated with the campaign. Silence means no successful device code flow was recorded with this specific tag.

  6. Query, baseline

    Prevalence of programmatic user agents in sign-ins

    Stack-count user agents to identify rare programmatic sign-ins (Python, Node) that stand out from standard browser traffic.

    sql, reads hb_auth_signin
    SELECT LOWER(user_agent) AS ua, COUNT(DISTINCT actor_user_name) AS users, COUNT(*) AS signins, MIN(time) AS first_seenFROM hb_auth_signinWHERE provider IN ('m365', 'azure_ad')  AND (instr(',' || '{{programmatic_uas}}' || ',', ',' || LOWER(user_agent) || ',') > 0 OR LOWER(user_agent) LIKE 'python%' OR LOWER(user_agent) LIKE 'node%')  AND time >= datetime('now', '-{{lookback_days}} days')GROUP BY LOWER(user_agent)HAVING users <= 3ORDER BY users ASC

    What a hit looks like. A programmatic user agent seen for only a few users, suggesting attacker automation replaying session tokens. Standard browser traffic should be common across the fleet.

  7. Agent triage

    Correlate attack chain across surfaces

    Link the web-based lure interaction from Phase 1 with the identity-based session abuse in Phase 2 for each user.

  8. Decision

    Route on evidence of compromise

    Route the investigation based on whether the agent found a correlated attack chain for any account.

  9. Response action

    Revoke sessions and isolate identity

    Terminate the attacker's replayed session and prevent further access.

  10. Analyst task

    Forensic analyst review

    Confirm the agent's findings and investigate the extent of post-compromise activity.

  11. Analyst task

    Close out hunt

    Document results and tune parameters for future runs.

# Microsoft Teams Booking Device Code Phishing

This hunt follows the lifecycle of a device code phishing attack identified in recent research. It identifies users who interacted with a typosquatted Teams booking site through a redirect chain involving Google short links and then correlates that web interaction with subsequent anomalous identity events. The follow-on phase looks for the specific 'Cmsi:Cmsi' login flow and session abuse by programmatic user agents (Python, Node) replaying tokens through residential proxies. An agent correlates these two surfaces to confirm successful compromise.
