# Mallox Affiliate: PureCrypter Loader Evasion and Persistence Hunt

### Background\n\nIn a recent report by Sekoia, [Mallox ransomware affiliate leverages PureCrypter in MSSQL exploitation](https://blog.sekoia.io/mallox-ransomware-affiliate-leverages-purecrypter-in-microsoft-sql-exploitation-campaigns/), researchers detailed how affiliates are moving from brute-forcing MS-SQL servers to deploying the PureCrypter loader. This loader is designed for evasion, using memory patching and environmental checks to avoid detection before the final ransomware stage.\n\n### Hypothesis\n\nAn adversary has established a foothold following a database compromise. They are using PowerShell \"echo\" redirection to stage payloads in the ProgramData directory and executing anti-analysis checks to detect virtual machines or sandboxes before establishing persistence via registry Run keys.\n\n### Hunt Flow\n\nThe hunt begins by scoping the environment for hosts running Microsoft SQL Server. Since these are the primary targets for the initial brute-force activity, focusing here allows us to prioritize telemetry on the most at-risk systems while still looking for behavioral patterns across the rest of the fleet.\n\nWe then look for specific staging behavior. The Mallox affiliates have been observed using `cmd.exe` or `powershell.exe` to \"echo\" script content directly into a `.ps1` file within `C:\\ProgramData\\` or `C:\\Users\\Public\\`. This is a low-noise way to drop a file without a direct download, which we detect by monitoring process command lines for redirection operators combined with suspicious file paths.\n\nThe third phase monitors for evasion and environment checks. PureCrypter frequently queries `Win32_BIOS` and `Win32_ComputerSystem` via WMI to check for VM-specific strings like \"VMware\" or \"VirtualBox\". It also attempts to release and renew IP addresses and add exclusions to Windows Defender. We cluster these events to identify suspicious behavior that deviates from standard administrative workflows.\n\nFinally, we address persistence and stealth. The hunt looks for rare registry Run keys pointing to binaries in user-writable paths. By stack-counting these registry values across the organization, we can isolate outliers that only appear on a few systems. Additionally, we examine script block content for strings associated with memory patching, specifically targeting attempts to disable the Anti-Malware Scan Interface (AMSI) or Event Tracing for Windows (ETW).\n\n### Blind Spots and Requirements\n\nThis hunt relies heavily on high-fidelity logging. Without PowerShell Script Block Logging (Event ID 4104), the attempts to patch AMSI or ETW in memory will be invisible to the `hb_script_activity` surface. Additionally, while we can find rare registry keys using a snapshot of the current state, process context (knowing which process created the key) requires active registry event logging.\n\n### How to Run This Hunt\n\nThis hunt is packaged as an open `hunt.md` playbook. It can be imported directly into Huntbase or any other hunt.md-aware runtime. Because it focuses on behavioral patterns like command-line redirection and registry stacking rather than fixed file hashes, it is effective against new or modified versions of the PureCrypter loader.
